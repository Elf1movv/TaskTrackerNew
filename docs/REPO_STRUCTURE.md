# Структура репозитория: за что отвечает какая часть

Репозиторий логически состоит из трёх независимых слоёв. Они физически
лежат в одном git-репозитории, но не зависят друг от друга по коду —
разделены только по смыслу (для чего используются и кем).

## 1. Приложение — `src/`, `server/`, Docker, CI/CD, корневые конфиги

Сам продукт и всё, что нужно, чтобы его собрать, протестировать и
задеплоить:
- `src/` — фронтенд, `server/` — бэкенд
- `Dockerfile`, `.dockerignore`, `docker-compose.yml` — контейнеризация
  (и приложение, и PostgreSQL — оба в Docker с 2026-09-17)
- `.github/workflows/deploy.yml` — CI/CD: сборка образа + автодеплой на
  VPS при пуше в `main`
- `package.json`/`package-lock.json`, `vite.config.ts`, `tsconfig*.json`,
  `eslint.config.js`, `postcss.config.mjs`, `steiger.config.js`,
  `index.html`, `.env`/`.env.example`, `.husky/`, `.prettierrc.json` —
  фронтенд-тулинг и тесты (`src/**/*.test.tsx`, `vitest`)
- `server/package.json`, `server/prisma/`, `server/vitest.config.ts` —
  то же самое для бэкенда (тесты — `server/src/**/*.test.ts`)

**Единственный слой, критичный технически.** Если убрать что-то отсюда —
приложение перестанет собираться, тестироваться, деплоиться или
запускаться. Всё остальное (слои 2 и 3) может исчезнуть без единой
ошибки сборки — просто исчезнет знание о проекте.

## 2. Инструменты Claude Code — `.claude/`

- `.claude/agents/` — `project-guide` (объясняет "почему так сделано"),
  `qa-tester` (тестирование через реальный браузер), `docs-writer`
  (поддерживает `docs/requirements/` в актуальном состоянии)
- `.claude/skills/coding-mentor/` — режим обучения для этого конкретного
  проекта и его владельца

**Что будет, если убрать**: ровно ничего в самом приложении — оно даже
не заметит. Пропадёт только специализированное поведение будущих
Claude Code сессий в этом репозитории: агентов нужно будет пересоздавать
заново, а новая сессия без `coding-mentor` скилла будет объяснять код в
дефолтном режиме, не зная, что тут нужен режим обучения для новичка.
Содержательное знание о проекте (почему что сделано) при этом не
теряется — оно живёт в слое 3, а не здесь. Агенты **читают** доки из
слоя 3, а не хранят знание в себе.

## 3. Документация — `docs/`, `PROJECT_BRAIN.md`, `LEARNING.md`

- `PROJECT_BRAIN.md` (корень репозитория) — самодостаточная входная
  точка: что за проект, весь стек и почему, как всё работает от клика
  до записи в базу, playbook на случай потери сервера/домена/данных/
  доступа к любому из аккаунтов
- `docs/ARCHITECTURE.md` — **почему** технически устроено именно так
  (паттерны, компромиссы, известные gotchas)
- `docs/DEPLOYMENT.md` — точная продовая инфраструктура (VPS, Docker,
  nginx, конфиги дословно)
- `docs/FILE_GUIDE.md` — построчный гайд по каждому файлу/папке в
  корне репозитория и на первом уровне `src`/`server` — что это, зачем,
  как использовать (этот файл, который ты сейчас читаешь, объясняет
  *группы* файлов; `FILE_GUIDE.md` объясняет *каждый файл* внутри них)
- `docs/ROADMAP.md` — что было слабым местом и что с этим сделали (или
  ещё предстоит) — журнал технических улучшений с датами
- `docs/BACKLOG.md` — продуктовые фичи в планах (авторизация и т.д.) —
  в отличие от `ROADMAP.md`, это не техдолг, а новая функциональность
- `docs/requirements/` — строгое дерево функциональных требований по
  фичам, `*-FRONTEND.md`/`*-BACKEND.md` на каждую (твой аналог MA/MW из
  корпоративной документации) — что именно должна делать каждая фича,
  достаточно подробно, чтобы восстановить поведение приложения только
  по этим файлам
- `LEARNING.md` — личный глоссарий терминов и журнал решений, в
  обучающем стиле (не то же самое, что `docs/ARCHITECTURE.md` — это
  хронологический конспект того, что уже объяснялось владельцу, а не
  справочник по системе целиком)

**Что будет, если убрать**: тоже ничего в рантайме приложения — это
чистое знание, не код. Но для человека (или для будущей AI-сессии) это
означает необходимость заново разбираться в проекте с нуля, читая только
исходный код и git-историю — то есть именно то, ради чего эта
документация и создавалась.

## Если реально захочешь физически разделить на отдельные репозитории

Технически возможно (например, вынести `.claude/` или `docs/` в свой
git-репозиторий и подключать как git submodule), но для сольного проекта
это добавляет постоянные накладные расходы (синхронизация сабмодулей,
отдельные PR в двух местах) без реальной выгоды, пока:
- никто другой не переиспользует эти агенты/доки в других репозиториях, и
- не стоит задача сделать код приложения публичным отдельно от
  внутренних заметок

Пока обеих причин нет — лучше оставить как один репозиторий с чёткой
папочной границей (как сейчас): это даёт то же самое разделение
ответственности, но без операционной сложности нескольких репозиториев.
Если один из этих поводов появится — возвращаемся к этому разделу и
меняем решение.
