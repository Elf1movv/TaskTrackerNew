# Переделка логики: общий план реализации

Основание: 18 решений в
[PRODUCT_LOGIC_DECISIONS.md](./PRODUCT_LOGIC_DECISIONS.md).
Состояние на 2026-10-06: реализация в ветке `feat/product-logic-redesign`;
модели/API, заметки, задачи, планы, цели и разбор старых данных добавлены.
Автоматические, локальные браузерные и API-проверки стенда пройдены.
https://test.mytracker.space доступен по HTTPS; регистрация, вход и
сохранение заметки проверены в публичном браузере. Следующий этап —
проверка владельцем. Деплой в main требует отдельного подтверждения
после неё и подготовки резервной копии/сценария возврата.

## Поведение готовой версии

| Раздел | Основное поведение |
|---|---|
| Главная | Актуальные заметки с описанием; предстоящие и архив доступны переключением. Привычки и напоминания сохраняют согласованное поведение. Обзор целей показывает активные цели. |
| Задачи | Общие дела по категориям. По умолчанию активные; в «Готово» вся история по 10 записей на страницу, последние выполненные первыми. |
| Календарь | Самостоятельные планы и интервалы существующих задач. День/время независимы от срока задачи. Есть «Без времени» и карман «Отложено». |
| Цели | Необязательная связь с задачами, общий статус каждой задачи, показатель «Выполнено X из Y задач». Достижение цели подтверждается отдельно. Есть активные и достигнутые. |
| Напоминания | Самостоятельные либо явно связанные с задачей/планом. Относительное время следует за переносом плана. Прошлые доступны в истории календаря. |

Новые записи не попадают в соседние разделы автоматически по факту
наличия даты. Отдельные календарные интервалы не создают копии задачи.

## Этап 1. Изоляция разработки и точки возврата

- Отдельная рабочая ветка от опубликованной версии eaf417d.
- В main остаётся нынешний рабочий сайт.
- Изменения схемы только новыми миграциями, существующие миграции
  не переписываем. Резервирование и проверка возврата перед выпуском.
- Сначала локальная изолированная тестовая БД; обычную локальную БД
  с пользовательскими записями не использовать для разрушительных тестов.

## Этап 2. Модель данных и сервер

Добавить самостоятельные модели Note и CalendarPlan, связь Task с
Goal и явный статус достижения Goal. Существующие поля расписания
Task и milestones Goal до подготовки перехода не удалять.

Note: владелец, заголовок, описание, необязательная дата появления,
архивирование, порядок и версии изменений. Сохранять прежний
паттерн Repository + optimistic updates + expectedUpdatedAt.

CalendarPlan: владелец, собственный заголовок/описание для
самостоятельных планов, необязательная ссылка на задачу, день,
время/конец, состояние «в расписании/отложено». Непривязанный план
может иметь собственную отметку выполнения; у связанного выполнение
читается из задачи. Окончание времени автоматически не завершает
ни задачу, ни план. Правило для самостоятельного плана сохраняет
существующую возможность явной отметки календарной записи.

Связанный план показывает текущее название исходной задачи.
Снимок заголовка/описания нужен для сохранения прошлой записи при
удалении задачи; снимок не становится второй редактируемой задачей.

Task: отдельный срок, необязательная цель, выполнение/completedAt.
Срок больше не используется как время календарного интервала.

Goal: явное achievedAt или эквивалентный статус; процент рассчитывать
по связанным задачам. Выполнение всех задач не меняет статус цели.
Цель без задач показывает пустое состояние, а не фиктивные 100%.

Reminder: необязательная ссылка на задачу/план и относительный
интервал для планов. У самостоятельных напоминаний прежние поля
и поведение. При On hold относительный сигнал временно неактивен;
после возврата в расписание время пересчитывается. Не добавлять
фоновые push или группу просроченных.

Сервер проверяет принадлежность каждой ссылки тому же пользователю;
чужой идентификатор не раскрывает существование чужой записи.
Сложные операции переноса/удаления выполняются атомарно.

Удаление цели отвязывает задачи. Удаление задачи убирает её будущие
планы и будущие связанные напоминания, а прошлые планы сохраняет
без неработающих ссылок. При определении будущего учитывать часовой
пояс пользователя и время начала: уже начавшийся интервал не
считать ещё не наступившим. Удаление одного плана сохраняет задачу,
остальные планы и отменяет только напоминания об удаляемом плане.

## Этап 3. Заметки и задачи в интерфейсе

- Заменить TodayTasksCard на самостоятельный блок заметок; кнопка
  добавления на главной создаёт заметку.
- Актуальные/предстоящие/архив: дата начала показа, архивирование
  и восстановление. Длинные списки не заполняют весь первый экран:
  использовать постепенное раскрытие в блоке.
- Название заметки и описание редактируются внутри блока. В свернутом
  состоянии компактный просмотр; раскрытое описание занимает ширину
  блока и растёт по высоте. Длинные слова и переносы не вызывают
  горизонтальный скролл. Поле ввода подстраивается под текст.
- При создании будущей заметки явно сообщать, что она сохранена в
  «Предстоящих», и давать перейти к ней.
- Убрать прогресс выполнения задач из блока заметок; постоянное
  преобразование заметки в задачу в эту версию не входит.
- В задачах оставить срок без пикеров календарного времени.
  Добавить необязательный выбор цели, «Запланировать», «Напомнить»
  и просмотр связанных интервалов с переходами к ним.
- История выполненных задач: пагинация по 10, completedAt descending,
  устойчивый дополнительный порядок по id; сброс страницы при смене
  фильтров, корректировка страницы после возврата задачи в активные.
- «Все / Без даты / С датой» оформить кнопками существующей дизайн-
  системы; подпись поясняет, что фильтруется именно срок задачи.

## Этап 4. Календарь

- Перевести календарные формы, сетки и часовые блоки на CalendarPlan.
  Новое создание не вызывает addTask без явного выбора существующей
  задачи. Формы позволяют самостоятельный план и привязку к задаче.
- Сохранить выбор дня по умолчанию и черновик при смене дня,
  перенос мышью/касанием, перенос между днями, растягивание
  длительности, сохранение длительности при переносе.
- Сверху дня/недели компактный блок «Без времени» при наличии таких
  планов. Сохранять доступ к ним в других видах календаря.
- Отдельный карман «Отложено» над календарём, в том числе доступный
  пустым как цель перетаскивания. Перенос выбранного плана в карман
  снимает дату, сохраняет длительность и ссылку; возврат задаёт новую
  дату/время. Срок и выполнение задачи не меняются.
- Будущие интервалы выполненной задачи приглушены с подписью
  «Задача выполнена»; эта подпись не означает, что работа в будущем
  уже состоялась. Действие очистки убирает только будущие интервалы.
- Сроки задач/целей, если видны в календаре, являются отдельными
  маркерами и не занимают время. Перенос рабочего блока не переносит
  срок. Показ дедлайнов не создаёт план автоматически.
- Чекбокс связанного блока завершает исходную задачу во всех
  представлениях; завершение по таймеру не вводим.

## Этап 5. Цели, напоминания и счётчики

- В цели отображать связанные задачи, переиспользовать их общие
  операции выполнения/редактирования. Добавлять задачу из цели можно
  с уже выбранной целью.
- Показатель выполнения и явное достижение цели. Фильтры активные/
  достигнутые, восстановление; главная и счётчики исключают достигнутые.
- Подтверждения удаления описывают действительные последствия
  и число затронутых будущих интервалов.
- Формы связанных напоминаний открываются по явному действию.
  Закрытие сигнала не завершает исходное дело. По умолчанию для
  задачи время сигнала выбирается явно; автоматической привязки
  к сроку без настройки пользователя не вводим.
- Статистика не удваивает одну задачу за несколько планов или за
  показ внутри цели. Заметки не учитываются как выполненные задачи.
- Сохранить расписание/историю привычек и принятое поведение прошлых
  напоминаний. Не включать несогласованные расширения из аудита.

## Этап 6. Одноразовый переход старых данных

- Пользователь видит только свои существующие записи и выбирает
  заметку, задачу со связанным прежним расписанием или только план.
- Предварительный просмотр показывает даты, поля и результат.
  Для заметки явно показать новый смысл даты. Не выполнять перенос
  по предположению «есть дата = план, нет даты = заметка».
- Для подцели создать связанную задачу с сохранением выполнения
  либо выбрать существующую. При несовпадении отметок показывать
  различие и состояние, которое сохранится, до подтверждения.
- Решение сохраняется. Повторное подтверждение/повторный запрос не
  создаёт копии. Проверять актуальные версии исходных записей.
- Пока запись не разобрана, она доступна в отдельном списке перехода;
  календарная дата также остаётся доступной для просмотра исходного
  плана. Не скрывать данные из всех разделов сразу при включении
  новой версии. Пользователь может отложить разбор и вернуться к нему.
- Исходные данные сохраняются в журнале перехода/снимках для
  проверки и отката; в новом интерфейсе нет независимых активных
  копий. Старые задачи и milestones не удалять физически без
  подготовленного сценария возврата.
- Изменение категории, удаление задачи и пересчёт цели должны
  учитывать результаты перехода, а не обходить правила новой модели.

## Этап 7. Тестовый стенд и выпуск

Отдельный Compose-проект, собственные контейнеры/сеть/том БД,
собственные env и секреты. Отдельный адрес с HTTPS и своими
настройками авторизации; сессии тестового и рабочего сайтов
изолированы. Тестовые email/feedback не отправляются автоматически
реальным получателям. Production-данные для тестирования не
копировать без отдельного согласования.

Сборка ветки получает собственный тег образа; тестовый процесс не
перезаписывает production latest. Подготовка тестового workflow,
адреса, DNS/TLS и нужных разрешений выполняется после готовности
локальной версии и проверки ресурсов сервера.

Проверки: frontend/backend typecheck, lint, fsd-lint, сборка, frontend
и backend тесты, браузерные проверки на десктопе и мобильном экране.
Для операций со связями и миграции нужны реальные API/БД-тесты,
а не только подставленные ответы браузера.

Обязательные сценарии: изоляция пользователей, конфликты двух
редактирований, независимость срока от расписания, несколько
интервалов одной задачи, On hold/возврат и относительные сигналы,
явное выполнение, история по 10, достижение/восстановление цели,
удаление с сохранением истории, каждое направление перехода старых
записей, повторный запрос, совпадающая существующая задача,
неразобранные записи, отсутствие потери содержания и дважды
учтённого выполнения.

Обновлять requirements, ARCHITECTURE, LEARNING и BACKLOG вместе с
каждым законченным функциональным этапом. До реализации исторические
требования не объявлять уже работающей новой функциональностью.

После проверки владельцем — отдельное подтверждение публикации
в main. Перед публикацией актуальный бэкап и проверенный сценарий
возврата к предыдущему образу. Старый код не умеет новые заметки и
несколько отдельных планов: новые записи физически сохраняются,
а для возврата к прежнему интерфейсу нужен проверенный экспорт/
преобразование, согласованное до выпуска. Восстановление старого
бэкапа не считать безопасным сохранением данных после его даты.

## Порядок проверки владельцем

1. Главная с заметками и их описанием, предстоящими и архивом.
2. Самостоятельный календарь, «Без времени», On hold и переносы.
3. Задача с несколькими интервалами, независимый срок и выполнение.
4. Цели со связанными задачами, прогрессом и явным достижением.
5. Напоминания и история, одноразовый разбор старых записей.
6. Только после положительного результата — выпуск на рабочий сайт.
