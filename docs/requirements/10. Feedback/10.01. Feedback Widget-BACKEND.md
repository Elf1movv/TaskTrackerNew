# 10.01. Feedback Widget [Backend]

# Где находится (файлы)

- `server/src/routes/feedback.ts` — единственный метод
- `server/src/validation/feedback.ts` — схема валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Feedback`
- `server/src/middleware/requireAuth.ts` — проверка сессии
- `server/src/lib/email.ts` — `sendEmail`, расширена поддержкой вложений
- `server/src/app.ts` — монтирование `/api/feedback`, увеличенный лимит
  `express.json`
- `server/.env.example` — переменная `FEEDBACK_EMAIL_TO`
- `server/src/routes/feedback.test.ts` — тесты метода

Это временная фича на период беты (см. комментарий в `schema.prisma:186-188`
и `LEARNING.md`) — модель и роут не планируются постоянной частью
продукта, план на удаление после беты не завязан на код бэкенда напрямую
(см. "Известные ограничения").

# Схема данных

1. `Feedback` — `'id'` (UUID), `'message'` (String), `'type'` (String,
   `"bug" | "suggestion"`, с 2026-09-25 — валидируется на уровне zod, как
   `Task.priority`, не отдельным Postgres-enum'ом), `'imageData'`
   (String?, опциональный base64 data URL прикреплённого скриншота,
   хранится как обычная колонка, не в отдельной файловой сущности —
   осознанный выбор для низкообъёмной временной фичи), `'page'` (String?,
   путь страницы, с которой отправлен отзыв), `'createdAt'`, `'userId'` +
   `'user'` (внешний ключ на `User`, `onDelete: Cascade`)
2. `@@index([userId])` — единственный индекс, под будущую выборку "все
   отзывы конкретного пользователя" (сейчас такой выборки в коде нет)
3. Миграция `20260925180000_add_feedback_type` добавила `'type'` строкам,
   существовавшим до этого поля, бэкфиллом в `'bug'` — комментарий в
   самой миграции прямо называет это предположением, не фактом (старые
   отзывы бета-периода не различали баг/предложение, `'bug'` выбран как
   разумный дефолт, потому что исходный текст плашки начинался со слов
   "Нашли баг"); DB-дефолт сразу снят (`DROP DEFAULT`) после бэкфилла —
   тот же паттерн, что у других аддитивных миграций этого проекта
   (например, `Category.color` тем же днём раньше)

# Методы

1. `feedbackRouter.use(requireAuth)` — весь роут требует сессию, тот же
   паттерн, что у `tasks`/`goals`/`habits`/`categories` (см.
   [09.01. Account Access-BACKEND](../09.%20Authentication/09.01.%20Account%20Access-BACKEND.md)):
   без сессии — `401`, `next()` не вызывается

2. При получении `POST /api/feedback` сервер должен:
   1. Провалидировать тело запроса схемой `createFeedbackSchema` —
      `'message'` (строка, 1–5000 символов), `'type'` (обязательно, одно
      из `"bug" | "suggestion"`, с 2026-09-25 — если поле отсутствует или
      содержит любое другое значение, запрос отклоняется, как и раньше
      отсутствующий/пустой `'message'`), `'imageData'` (опционально,
      строка до 7 000 000 символов — с запасом под base64-кодирование
      картинки до ~5MB плюс префикс `data:image/...;base64,`),
      `'page'` (опционально, строка до 200 символов) — если не прошло,
      `400 { error: "Invalid feedback", details }`
   2. Создать строку `Feedback` с `'userId' = req.userId` и остальными
      провалидированными полями как есть
   3. Сразу ответить `201 { id }` — до попытки отправить письмо (запись
      в базе уже сохранена, дальнейшая отправка не должна задерживать
      или ломать ответ клиенту)
   4. После ответа — если `process.env.FEEDBACK_EMAIL_TO` не задан,
      вывести в консоль сервера `userId` и текст сообщения и на этом
      остановиться, письмо не пытаться отправлять
   5. Если `FEEDBACK_EMAIL_TO` задан — асинхронно (без ожидания,
      `void (async () => {...})()`, тот же fire-and-forget принцип, что у
      `sendResetPassword` в `auth.ts`, см. `09.01. Account
      Access-BACKEND.md`) найти отправителя через `db.user.findUnique({
      where: { id: req.userId }, select: { name: true, email: true } })`
      и вызвать `sendEmail` с темой `"MyTracker — [${typeLabel}] new
      feedback"`, где `typeLabel` — `"Bug"` или `"Suggestion"`
      (`feedback.ts:44`, с 2026-09-25 — раньше тема была фиксированной
      `"MyTracker — new feedback"` без указания типа), и HTML, содержащим
      строку `"From": '${user.name} (${user.email})'` (`feedback.ts:39`)
      — если пользователь почему-то не найден, fallback на голый
      `req.userId`, как было до 2026-09-23 всегда; форма отправки отзыва
      (`FeedbackDialog`) своего поля имени/email не имеет — фидбек
      доступен только авторизованным, поэтому имя и email берутся из уже
      существующего аккаунта, а не запрашиваются повторно — далее в HTML
      также отдельная строка `"Type": Bug` (или `Suggestion`,
      `feedback.ts:50`, добавлена тем же днём), `'page'` (или
      `"unknown"`, если не прислан) и текст сообщения. Тег `[Bug]`/
      `[Suggestion]` вынесен именно в тему письма, а не только в тело —
      чтобы два типа отзыва можно было отличить и отфильтровать в списке
      входящих писем, не открывая каждое
   6. Если в теле был `'imageData'` — перед отправкой отрезать префикс
      `data:...;base64,` (если он есть) и передать оставшуюся
      base64-строку как вложение `{ filename: "screenshot.png", content
      }` в `sendEmail`; без `'imageData'` вложений нет

3. `sendEmail` (`server/src/lib/email.ts`) должна:
   1. Принимать опциональный `attachments?: { filename, content }[]` (в
      дополнение к уже существующим `to`/`subject`/`html`, см.
      [09.01. Account Access-BACKEND](../09.%20Authentication/09.01.%20Account%20Access-BACKEND.md))
      и прокидывать его как есть в `resend.emails.send({ ..., attachments })`
   2. Если `RESEND_API_KEY` не задан — не отправлять ничего, вывести в
      консоль тему, `to` и количество вложений вместо самой отправки —
      тот же принцип, что у остального email-флоу приложения

4. `express.json` в `server/src/app.ts` должен принимать тело запроса до
   `8mb` (`server/src/app.ts:42`) — дефолтный лимит Express в `100kb`
   специально увеличен под этот метод, единственный в приложении, куда
   может прийти base64-скриншот

# Известные ограничения

1. Нет ни одного метода для чтения/удаления отзывов (`GET`/`DELETE`) —
   фича строго "отправить и забыть" со стороны клиента; просмотр
   отправленных отзывов — только прямой запрос к таблице `Feedback` в
   БД или письма на `FEEDBACK_EMAIL_TO`, когда адрес будет задан.
   Админ-интерфейса нет
2. На момент написания `FEEDBACK_EMAIL_TO` в проде не задан (см.
   `LEARNING.md`, `docs/BACKLOG.md`) — реальный ящик для приёма отзывов
   ещё не создан, поэтому все отзывы сейчас оседают только в таблице
   `Feedback` и в логах сервера, email никуда не уходит. Как только
   переменная будет выставлена — отправка заработает сама, без изменений
   кода
3. `onDelete: Cascade` от `User` — удаление аккаунта пользователя удаляет
   и всю его историю отзывов, отдельного архивирования нет
4. У этой фичи нет серверного kill switch — единственный переключатель
   (`FEEDBACK_BETA_ENABLED`) чисто клиентский, отключает только плашку на
   фронтенде (см.
   [10.01. Feedback Widget-FRONTEND](./10.01.%20Feedback%20Widget-FRONTEND.md)).
   Отключение плашки не отключает сам эндпоинт `POST /api/feedback` — он
   остаётся доступным, если его вызвать напрямую
5. Тесты (`feedback.test.ts`) покрывают: `401` без сессии, `400` на
   пустое `'message'`, `400` на отсутствующий или невалидный `'type'`
   (с 2026-09-25), успешное создание записи с привязкой к пользователю,
   что `'type' = "suggestion"` сохраняется отдельно от `"bug"` (с
   2026-09-25), приём опционального `'imageData'`. Отправка письма
   (ветка с `FEEDBACK_EMAIL_TO`/`sendEmail`, включая тег `[Bug]`/
   `[Suggestion]` в теме) тестами не покрыта
