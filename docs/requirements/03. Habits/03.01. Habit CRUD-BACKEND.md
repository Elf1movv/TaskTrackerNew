# 03.01. Habit CRUD [Backend]

# Где находится (файлы)

- `server/src/routes/habits.ts` — все методы
- `server/src/validation/habit.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Habit`, поле `'activeDays'`,
  поле `'groupId'` (см. ниже и `03.03. Habit Groups-BACKEND.md`)
- `server/prisma/migrations/20260921134315_add_habit_active_days` —
  миграция, добавившая `'activeDays'`
- `server/prisma/migrations/20260923134206_add_habit_groups` — миграция,
  добавившая `'groupId'` (см. `03.03. Habit Groups-BACKEND.md`)
- `server/prisma/migrations/20260924090000_add_habit_today_order_and_group_color/` —
  миграция, добавившая `'todayOrder'` (см. ниже) и `HabitGroup.color`
  (см. `03.03. Habit Groups-BACKEND.md`)
- `server/src/middleware/requireAuth.ts` — проверка сессии

# Авторизация и разграничение по пользователю

Тот же паттерн, что у `Task` (см.
[01.01. Task CRUD-BACKEND](../01.%20Tasks/01.01.%20Task%20CRUD-BACKEND.md),
раздел "Авторизация и разграничение по пользователю"): `habitsRouter.use(requireAuth)`,
`401` без сессии, `'userId' = req.userId` на `GET`/`POST`, `userId` в
`WHERE` у `updateMany`/`deleteMany` для `PATCH reorder`/`PATCH :id`/
`DELETE :id` — привычка другого пользователя ведёт себя как
несуществующая (`404`, не `403`).

# Методы

Тот же паттерн, что у Task и Goal (см. `01.01. Task CRUD-BACKEND.md` —
здесь только отличия по полям):

1. `GET /api/habits` — все привычки по `'order'`, клиенту отдаются
   `'id'`, `'title'`, `'icon'`, `'color'`, `'completedDates'`,
   `'activeDays'`, `'groupId'`, `'todayOrder'`, `'updatedAt'`,
   `'createdAt'` (поле существовало в Prisma-схеме и раньше, клиенту
   стало отдаваться только с 2026-09-21 — используется годовым видом
   Habits history, чтобы не считать месяцы до создания привычки как "0%
   выполнено", см. `03.02. Habit History-FRONTEND.md`). `'groupId'` — с
   2026-09-23, см. `03.03. Habit Groups-BACKEND.md`. `'todayOrder'` — с
   2026-09-24 (см. ниже, "Порядок на Today"); это единственное
   исключение из правила "`order` никогда не отдаётся клиенту" —
   `'todayOrder'` отдаётся, потому что сервер умеет предсортировать
   список только одним способом (`GET` сортирует по `'order'`), а
   клиенту нужно построить и второй, независимый порядок из того же
   ответа
2. `POST /api/habits` — валидация `createHabitSchema` (включает
   обязательное `'groupId'` — `uuid`), `'order'` = текущий максимум
   среди своих же привычек плюс 1 (новая привычка — **последняя** в
   списке), код `201`. До 2026-09-21 было наоборот (минимум минус 1,
   новая привычка первая) — изменено вместе с `Task`/`Goal`, см. `01.01.
   Task CRUD-BACKEND.md`, `POST`. С 2026-09-24 `'todayOrder'`
   присваивается тем же образом и одновременно — текущий максимум среди
   `'todayOrder'` своих же привычек плюс 1, независимо от `'order'`, так
   что новая привычка оказывается последней сразу на обоих экранах
   (`server/src/routes/habits.ts:79-89`). Streak (серия дней подряд) на
   сервере не хранится и не вычисляется — это чисто клиентский расчёт по
   `'completedDates'` и `'activeDays'` (см. `03.01. Habit
   CRUD-FRONTEND.md`). Сервер дополнительно проверяет, что `'groupId'`
   принадлежит текущему пользователю — `400`, если нет (см. `03.03.
   Habit Groups-BACKEND.md`, раздел "Владение группой при операциях над
   `Habit`")
3. `PATCH /api/habits/reorder` — меняет только `'order'` (позиция
   привычки внутри своей группы на странице `/habits`), строки
   транзакции отсортированы по `'id'` перед сборкой (тот же приём, что у
   `Task` — детерминированный порядок блокировок, чтобы две
   перекрывающиеся транзакции не задедлочились друг с другом, реальный
   баг, исправлен 2026-09-21, см. `01.01. Task CRUD-BACKEND.md`, `PATCH
   /reorder` и `LEARNING.md`), зарегистрирован до `PATCH /:id`.
   Возвращает `200` с JSON-массивом `{ id, updatedAt }[]`
   (не `204` без тела) — Prisma's `@updatedAt` обновляет `'updatedAt'` у
   любой переставленной строки, даже когда меняется только `'order'`;
   без свежих значений следующий точечный `PATCH /:id` по одной из этих
   привычек ушёл бы со старым `'expectedUpdatedAt'` и получил бы ложный
   `409 "changed elsewhere"` (тот же баг и исправление, что у `Task`, см.
   `01.01. Task CRUD-BACKEND.md` и `LEARNING.md`, 2026-09-19)
4. `PATCH /api/habits/reorder-today` — с 2026-09-24, точная копия
   `PATCH /api/habits/reorder` выше (та же схема `reorderSchema`, тот же
   детерминированный порядок блокировок по `'id'`, тот же ответ `200` с
   `{ id, updatedAt }[]`), но пишет в `'todayOrder'` вместо `'order'` —
   позиция привычки внутри своей группы на карточке блока на странице
   Today (см. `03.04. Today Habit Groups-FRONTEND.md`), независимая от
   `'order'` на `/habits`. Зарегистрирован до `PATCH /:id`, как и
   `/reorder` (`server/src/routes/habits.ts:122-141`)
5. `PATCH /api/habits/:id` — атомарное условное обновление по
   `'expectedUpdatedAt'`, `404`/`409`/`200` — идентично Task. `'todayOrder'`
   не входит в `updateHabitSchema` — этим полем можно управлять только
   через `PATCH /reorder-today`, не через точечный патч. Если патч
   меняет `'groupId'`, сервер так же проверяет, что новая группа
   принадлежит текущему пользователю — `400`, если нет (см. `03.03.
   Habit Groups-BACKEND.md`)
6. `DELETE /api/habits/:id` — `404`/`204` — вместе с привычкой удаляется
   вся история `'completedDates'`, отдельно не хранится и не
   архивируется

# Порядок на Today (`'todayOrder'`)

1. `Habit.todayOrder` — `Int`, вторая, полностью независимая от `'order'`
   ось сортировки (`server/prisma/schema.prisma:73-78`): `'order'` —
   позиция привычки внутри своей группы на `/habits`, `'todayOrder'` —
   позиция той же привычки внутри той же группы на Today. Перетаскивание
   на одном экране не двигает привычку на другом — обе оси меняются
   только своим собственным reorder-роутом (`/reorder` и
   `/reorder-today` соответственно)
2. Миграция `20260924090000_add_habit_today_order_and_group_color`
   добавила колонку `NOT NULL` и забэкфилила её значением `'order'` на
   момент миграции — разумная стартовая точка, раз обе оси совпадают,
   пока никто ни разу не перетащил привычку отдельно на одном из экранов
3. Принадлежность к группе (`'groupId'`) при этом общая — это не второй
   `groupId`, меняющийся независимо, а один и тот же foreign key,
   используемый обеими осями сортировки одновременно (см. `03.03. Habit
   Groups-BACKEND.md`)

# Расписание (`'activeDays'`)

1. `Habit.activeDays` — `Int[]` в БД, значения `Date.getDay()` (`0` =
   воскресенье .. `6` = суббота). Дефолт на уровне схемы —
   `@default([0, 1, 2, 3, 4, 5, 6])` (`server/prisma/schema.prisma:71`) —
   все 7 дней, так что у привычек, созданных до этой миграции, поведение
   не меняется без явного действия пользователя
2. `habitFields` (`server/src/validation/habit.ts:9`) требует
   `'activeDays'` — массив целых чисел `z.number().int().min(0).max(6)`
   — и на `POST`, и внутри `PATCH`'s `patch` (через `.partial()`)
3. Сервер **не проверяет**, что `'activeDays'` непустой — пустой массив
   пройдёт валидацию (запрет "нельзя сохранить привычку без единого
   активного дня" — только на фронтенде, disabled-кнопка в `HabitForm`,
   см. `03.01. Habit CRUD-FRONTEND.md`)
4. Порядок значений внутри массива не имеет значения — обе стороны
   (клиент и сервер) читают его как множество дней, не как
   последовательность

# Известные ограничения

1. `'completedDates'` — массив строк без ограничения на формат/дубликаты
   на уровне схемы валидации (только на клиенте гарантируется формат
   `"YYYY-MM-DD"` и отсутствие дублей через `toggleHabit`) — сервер
   технически примет любые строки в этом массиве
2. `'activeDays'` можно сохранить пустым массивом через прямой запрос к
   API в обход `HabitForm` (см. выше, "Расписание", п. 3) — на клиенте
   `getStreak`/`selectTodayHabits` в этом случае просто не находят ни
   одного расписанного дня (`getStreak` возвращает `0`, привычка нигде
   не появляется на Today), без ошибки
