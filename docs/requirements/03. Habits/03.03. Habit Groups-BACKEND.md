# 03.03. Habit Groups [Backend]

# Где находится (файлы)

- `server/src/routes/habitGroups.ts` — все методы
- `server/src/validation/habitGroup.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `HabitGroup`, поле `Habit.groupId`,
  `User.habitGroupsSeeded`
- `server/prisma/migrations/20260923134206_add_habit_groups/` — ручная
  миграция (не сгенерированная `prisma migrate diff`), с бэкофиллом
- `server/prisma/migrations/20260924090000_add_habit_today_order_and_group_color/` —
  миграция, добавившая `'color'` (см. ниже; заодно добавила
  `Habit.todayOrder`, не относящееся к этой фиче — см. `03.01. Habit
  CRUD-BACKEND.md`)
- `server/src/middleware/requireAuth.ts` — проверка сессии

# Модель данных

1. `HabitGroup` — `id`, `'title'`, `'icon'`, `'color'` (с 2026-09-24, см.
   ниже), `'isGeneral'` (`Boolean`, дефолт `false`), `'order'`,
   `'createdAt'`, `'updatedAt'`, `'userId'`
2. `Habit.groupId` — **обязательное** поле, реальный foreign key на
   `HabitGroup` (`onDelete: Restrict`), в отличие от `Task.category`,
   который остаётся строкой без FK (см. `01.02. Categories-BACKEND.md`) —
   сделано намеренно, чтобы блок можно было безопасно переименовывать и
   переставлять без риска рассинхронизации по имени
   (`server/prisma/schema.prisma:91-93`)
3. `Habit.groupId` не может быть `null` — у каждой привычки всегда есть
   группа, включая привычки, не отнесённые пользователем ни к одному
   именованному блоку (они лежат в группе `isGeneral: true`, см. ниже)

# Авторизация и разграничение по пользователю

Тот же паттерн, что у `Habit`/`Task` (см. `01.01. Task
CRUD-BACKEND.md`, раздел "Авторизация и разграничение по пользователю"):
`habitGroupsRouter.use(requireAuth)`, `401` без сессии, `'userId' =
req.userId` на `GET`/`POST`, `userId` в `WHERE` у `updateMany`/
`deleteMany`/`findFirst` для остальных методов — группа другого
пользователя ведёт себя как несуществующая (`404`, не `403`).

# Группа "Общие" (`isGeneral: true`)

1. Это не `groupId: null` и не вычисляемый псевдо-блок на клиенте — это
   настоящая строка `HabitGroup` с флагом `'isGeneral' = true`, участвует
   в общей сортировке и drag-and-drop блоков наравне с остальными
2. Создаётся лениво — при первом `GET /api/habit-groups` для
   пользователя, у которого `User.habitGroupsSeeded === false`
   (`server/src/routes/habitGroups.ts:38-60`). Тот же паттерн, что и
   `Category` с `User.categoriesSeeded` (см. `01.02.
   Categories-BACKEND.md`): создание строки и обновление флага — в одной
   транзакции, чтобы сбой между ними не оставил пользователя без
   "Общих" при повторном запросе
3. `'title' = "General"`, `'icon' = "📋"`, `'color' = "#c97b3a"` — это
   заглушки на сервере (`GENERAL_GROUP_TITLE`/`GENERAL_GROUP_ICON`/
   `GENERAL_GROUP_COLOR`, `server/src/routes/habitGroups.ts:42-44`), не
   предполагаются показанными как есть: клиент подставляет свою
   локализованную подпись и иконку для строки с `'isGeneral' = true`, но
   только пока `'title'`/`'icon'` всё ещё равны этим заглушкам (см.
   `03.03. Habit Groups-FRONTEND.md`) — сервер сам никак это не
   принудительно поддерживает, это чисто клиентская проверка
4. `'order' = 999999` — так группа по умолчанию сортируется последней
   среди блоков пользователя, но это не хардкод "последней позиции": её
   можно перетащить на любое место, как и любую другую группу
5. `PATCH /api/habit-groups/:id` — с 2026-09-24 **разрешён** и для группы
   с `'isGeneral' = true`: можно поменять `'title'`, `'icon'` и `'color'`
   как у любой другой группы (`server/src/routes/habitGroups.ts:130-132`).
   До 2026-09-24 любой `PATCH` над "Общими" отклонялся кодом `400`
   (`"The General group can't be renamed"`) — снято по прямой просьбе
   пользователя, единственное ограничение, оставшееся у этой группы —
   её нельзя удалить (см. ниже)
6. `DELETE /api/habit-groups/:id` по-прежнему отклоняет операцию над
   группой с `'isGeneral' = true` кодом `400` (`"The General group can't
   be deleted"`) — её привычкам было бы некуда переехать (см. `DELETE`
   ниже)

# Методы

1. `GET /api/habit-groups` — сначала лениво сидирует "Общие" при
   необходимости (см. выше), затем возвращает все группы пользователя по
   `'order'` (`{ id, title, icon, color, isGeneral, updatedAt }[]` —
   `'color'` отдаётся с 2026-09-24)
2. `POST /api/habit-groups` — валидация `createHabitGroupSchema` (`id`
   — `uuid`, клиент генерирует сам, как и у `Habit`; `title` —
   непустая строка; `icon` — непустая строка; `color` — непустая строка,
   с 2026-09-24 обязательное поле). `'isGeneral'` **не**
   принимается из тела запроса — всегда `false` для созданных через
   `POST`, единственный способ получить строку с `'isGeneral' = true` —
   ленивый сид выше (`server/src/validation/habitGroup.ts:3-6`).
   `'order'` = текущий максимум среди своих же групп плюс 1 (новая
   группа — последняя), код `201`
3. `PATCH /api/habit-groups/reorder` — меняет только `'order'`, строки
   транзакции отсортированы по `'id'` перед сборкой (тот же приём, что у
   `Task`/`Habit` — детерминированный порядок блокировок, чтобы две
   перекрывающиеся транзакции не задедлочились). Группа "Общие" участвует
   в этой транзакции наравне со всеми, без спецкейса. Возвращает `200` с
   JSON-массивом `{ id, updatedAt }[]` (не `204` без тела) — по той же
   причине, что и у `Task`/`Habit`: `@updatedAt` бампает `'updatedAt'` у
   любой переставленной строки, даже когда меняется только `'order'`;
   без свежих значений следующий точечный `PATCH /:id` ушёл бы со старым
   `'expectedUpdatedAt'` и получил бы ложный `409`
4. `PATCH /api/habit-groups/:id` — атомарное условное обновление по
   `'expectedUpdatedAt'`, `404`/`409`/`200`, идентично `Task`/`Habit`,
   `patch` может менять `'title'`/`'icon'`/`'color'` (все — `.partial()`
   от тех же полей, что и `POST`). С 2026-09-24 **без** спецкейса для
   `'isGeneral'` — до этого здесь была та же проверка, что и в `DELETE`
   ниже (см. "Группа 'Общие'", п. 5)
5. `DELETE /api/habit-groups/:id` — с проверкой `'isGeneral'` (см. выше,
   п. 6).
   Для обычной группы — **не** удаляет её привычки: в одной транзакции
   (1) все привычки этой группы (`Habit.groupId`) переставляются на
   `id` группы "Общие" этого же пользователя, (2) сама группа удаляется.
   Код `204`. Транзакционность здесь обязательна — `Habit.groupId` не
   имеет `ON DELETE CASCADE`/`SET NULL` (см. схему), поэтому без явного
   переноса в одной транзакции удаление группы с привычками упёрлось бы
   в FK-ограничение и откатилось бы целиком

# Владение группой при операциях над `Habit`

1. `POST /api/habits` и `PATCH /api/habits/:id` (когда патч меняет
   `'groupId'`) — сервер явно проверяет, что переданный `'groupId'`
   существует и принадлежит текущему пользователю
   (`db.habitGroup.findFirst({ where: { id, userId } })`,
   `server/src/routes/habits.ts:69-73,153-159`) — без этой проверки
   Prisma сама по себе только убеждается, что строка с таким `id`
   существует где угодно, а не что она принадлежит вызывающему
   пользователю; без явной проверки один пользователь мог бы подставить
   `id` чужой группы. При нарушении — `400 "Habit group not found"`

# Известные ограничения

1. `HabitGroup.icon` — как и `Habit.icon`, произвольная непустая строка
   на уровне схемы валидации; ограничение "только один эмодзи из
   заранее заданного набора" — только на клиенте (`HABIT_ICONS`,
   `EmojiPicker`, см. `03.03. Habit Groups-FRONTEND.md`)
2. `HabitGroup.color` — как и `Habit.color`, произвольная непустая строка
   на уровне схемы валидации, без проверки на реальный hex-формат;
   ограничение "только один из 12 цветов палитры" — только на клиенте
   (`PALETTE_COLORS`, см. `03.03. Habit Groups-FRONTEND.md`). Сервер не
   знает, что это поле используется только Today-карточкой блока — он
   просто хранит и отдаёт строку
3. Перенос привычек в "Общие" при удалении группы — это **единственный**
   способ у привычки сменить `'groupId'` без явного действия
   пользователя; сервер никогда не создаёт новых групп и не удаляет
   привычки сам по себе при удалении блока
