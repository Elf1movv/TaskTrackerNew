# 09.01. Account Access [Backend]

# Где находится (файлы)

- `server/src/auth.ts` — конфигурация `betterAuth({...})`: адаптер
  Prisma, `emailAndPassword`, `emailVerification`, `trustedOrigins`,
  `hooks.before` (правила пароля, см. "Правила пароля" ниже)
- `server/src/lib/email.ts` — обёртка над Resend для отправки писем
- `server/src/middleware/requireAuth.ts` — проверка сессии, используется
  роутерами `tasks`/`goals`/`habits`/`categories` (не самим `/api/auth/*`)
- `server/src/types/express.d.ts` — объявляет `req.userId: string`
- `server/src/app.ts` — монтирование `/api/auth/*` в Express
- `server/prisma/schema.prisma` — модели `User`, `Session`, `Account`,
  `Verification`
- `server/prisma/migrations/20260918191743_add_better_auth_tables/` —
  миграция под эти 4 таблицы
- `server/src/test-utils/auth.ts` — тестовый хелпер
  `createAuthenticatedAgent`

Сами HTTP-методы (`/api/auth/sign-up/email` и т.д.) не реализованы
руками в этом репозитории — их целиком обрабатывает библиотека Better
Auth (`toNodeHandler(auth)`, `server/src/app.ts:37`); наш код только
настраивает её поведение через объект конфигурации в `auth.ts`. Ниже
описано наблюдаемое поведение этих методов, каким его определяет эта
конфигурация.

# Схема данных

1. `User` (`@@map("user")`) — `'id'`, `'name'`, `'email'` (`@unique`),
   `'emailVerified'`, `'image'`. Хэш пароля **не** хранится здесь
2. `Account` (`@@map("account")`) — одна строка на способ входа.
   Для email/password единственная строка на пользователя с
   `'providerId' = "credential"`, хэш пароля — в `'password'` на этой
   модели, не на `User`
3. `Session` (`@@map("session")`) — `'token'` (`@unique`, значение куки),
   `'expiresAt'`, `'userId'`
4. `Verification` (`@@map("verification")`) — короткоживущие токены:
   ссылка подтверждения почты и ссылка восстановления пароля, каждая —
   отдельная строка с `'expiresAt'`
5. Все 4 модели написаны в `schema.prisma` вручную, не через
   `npx auth generate` (CLI-генератор Better Auth) — известная история
   того, что генератор может перезаписать вручную поддерживаемые модели
   в той же схеме (`Task`/`Goal`/`Habit`/`Category`). По той же причине
   миграция `20260918191743_add_better_auth_tables` создана через
   `prisma migrate diff` (сравнение целевой схемы с текущей базой), а не
   через `prisma migrate dev`

# Методы

Всё под `/api/auth/*`, смонтировано **до** `express.json()`
(`server/src/app.ts:34-39`) — Better Auth сам читает тело запроса
потоком, миддлвар парсинга JSON, поставленный раньше, уже забрал бы этот
поток и сломал бы это.

1. При получении `POST /api/auth/sign-up/email` сервер должен:
   1. Провалидировать `'name'`, `'email'`, `'password'` — если `'email'`
      уже занят существующим пользователем, вернуть `422` с кодом
      `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL` ("User already exists. Use
      another email.") — в отличие от восстановления пароля (см. ниже),
      регистрация **не** скрывает существование почты в системе
   2. Провалидировать `'password'` двумя правилами — длина и состав, см.
      "Правила пароля" ниже; при нарушении регистрация не создаёт
      пользователя
   3. Создать строку `User` с `'emailVerified' = false` и строку
      `Account` с `'providerId' = "credential"` и хэшем пароля
   4. Не создавать активную сессию сразу — вызвать
      `emailVerification.sendVerificationEmail` (`auth.ts:31-37`), которая
      уходит в `sendEmail` (см. ниже) со ссылкой вида
      `{baseURL}/verify-email?token=...`
   5. Тело письма и тема — на русском, захардкожены в `auth.ts` (не через
      общий i18n-словарь фронтенда, см. "Известные ограничения")

2. При получении `GET /api/auth/verify-email?token=...` сервер должен:
   1. Найти `Verification` по токену, если не найден или истёк —
      вернуть ошибку (ссылка недействительна)
   2. Если токен валиден — выставить `User.emailVerified = true` и
      удалить использованный токен

3. При получении `POST /api/auth/sign-in/email` сервер должен:
   1. Провалидировать `'email'`/`'password'`; если пользователь не
      найден или пароль не совпал — `401` с кодом
      `INVALID_EMAIL_OR_PASSWORD` ("Invalid email or password") — в
      обоих случаях одна и та же ошибка, чтобы не подтверждать факт
      существования аккаунта перебором
   2. Если пароль верный, но `'emailVerified' = false` — `403` с кодом
      `EMAIL_NOT_VERIFIED` ("Email not verified"), сессия не создаётся.
      Конфигурация включает `emailVerification.sendOnSignIn: true`
      (`auth.ts:41`) — на этом же шаге Better Auth сама вызывает
      `sendVerificationEmail` и отправляет пользователю свежую ссылку
      подтверждения (тот же текст письма и обработчик, что при
      регистрации, см. п. 1.4-1.5), так что потерянное или попавшее в
      спам первое письмо не блокирует вход навсегда — достаточно
      попробовать войти ещё раз, чтобы получить новую ссылку
   3. Если пароль верный и почта подтверждена — создать `Session`,
      выставить cookie с токеном сессии в ответе

4. При получении `GET /api/auth/get-session` сервер должен:
   1. Прочитать cookie сессии из запроса, вернуть текущего
      `'user'`/`'session'`, либо `null`, если куки нет или сессия
      истекла/невалидна
   2. Этот метод дергает `useSession()` на фронтенде (см.
      `09.01. Account Access-FRONTEND.md`) и `requireAuth` — оба
      обращаются к нему через `auth.api.getSession(...)`, не через
      прямой HTTP-запрос, кроме клиентского `useSession`, который
      действительно ходит по сети на этот путь

5. При получении `POST /api/auth/sign-out` сервер должен: удалить
   строку `Session`, соответствующую текущей cookie, и очистить cookie
   в ответе

6. При получении `POST /api/auth/request-password-reset` сервер должен:
   1. Найти пользователя по `'email'`; независимо от того, найден он или
      нет, вернуть одинаковый успешный ответ — email-адрес не
      подтверждается публично (в отличие от регистрации, см. п. 1.1)
   2. Если пользователь найден — вызвать `sendResetPassword` (`auth.ts:22-28`)
      **без ожидания** (`void sendEmail(...)`, не `await`) — по
      собственной рекомендации Better Auth, чтобы время ответа не
      выдавало, существует ли аккаунт (медленный `await` на "не нашли
      email" vs быстрый ответ на "нашли и шлём письмо" сам по себе был
      бы утечкой информации через тайминг)

7. При получении `POST /api/auth/reset-password` сервер должен:
   1. Провалидировать токен из ссылки восстановления (`Verification`) и
      новый пароль (длина и состав — см. "Правила пароля" ниже)
   2. Если токен невалиден/истёк — вернуть ошибку, пароль не менять
   3. Если валиден — обновить `'password'` на связанной строке `Account`
      (`providerId: "credential"`), удалить использованный токен;
      существующие сессии эта операция сама по себе не отзывает

8. При получении `POST /api/auth/change-password` сервер должен:
   1. Требовать активную сессию — читает ту же cookie сессии, что и
      `get-session` (встроенный в Better Auth `sensitiveSessionMiddleware`,
      не наш `requireAuth`, см. п. 9 ниже: `requireAuth` защищает только
      `tasks`/`goals`/`habits`/`categories`, а не `/api/auth/*`)
   2. Принять тело `{ currentPassword, newPassword, revokeOtherSessions?
      }` — `'revokeOtherSessions'` необязателен, по умолчанию не
      передаётся (эквивалент `false`)
   3. Провалидировать `'newPassword'` — оба правила из "Правила пароля"
      ниже (длина 8–128, буква и цифра); при нарушении — `400` с кодом
      `PASSWORD_TOO_SHORT`/`PASSWORD_TOO_LONG`/`PASSWORD_NO_LETTER_OR_DIGIT`,
      пароль не меняется
   4. Найти строку `Account` с `'providerId' = "credential"` для
      текущего пользователя и сверить `'currentPassword'` с хранимым
      хэшем — если не совпал, `400` с кодом `INVALID_PASSWORD` (на
      фронтенде переводится как "Неверный текущий пароль", см.
      [12.01. Settings Panel-FRONTEND](../12.%20Settings/12.01.%20Settings%20Panel-FRONTEND.md))
   5. Если пароль верный — обновить `'password'` на этой строке
      `Account` новым хэшем
   6. Если `'revokeOtherSessions' === true` — удалить **все** сессии
      пользователя (включая текущую), сразу создать новую и выставить её
      cookie в ответе, чтобы вызвавший запрос браузер не потерял сессию;
      если `false`/не передан — сессии на других устройствах не
      трогаются
   7. Ответить `200 { token, user }` — `'token'` заполнен только если
      `'revokeOtherSessions'` был `true` (значение новой сессии), иначе
      `null`

9. Middleware `requireAuth` (`server/src/middleware/requireAuth.ts`),
   подключённый как `router.use(requireAuth)` в каждом из
   `tasksRouter`/`goalsRouter`/`habitsRouter`/`categoriesRouter` (не в
   `/api/auth/*`, чтобы не блокировать сам вход), должен:
   1. Прочитать сессию через `auth.api.getSession({ headers:
      fromNodeHeaders(req.headers) })`
   2. Если сессии нет — ответить `401 { error: "Unauthorized" }` и не
      вызывать `next()`
   3. Если сессия есть — положить `session.user.id` в `req.userId`
      (типизировано в `server/src/types/express.d.ts`) и вызвать
      `next()`

# Правила пароля

Общие для трёх методов, где пароль реально устанавливается:
`POST /sign-up/email` (п. 1), `POST /change-password` (п. 8),
`POST /reset-password` (п. 7).

10. Длина — 8–128 символов (`emailAndPassword.minPasswordLength`/
    `maxPasswordLength`, `auth.ts:30-31`, явно выставлены, а не оставлены
    дефолтом библиотеки). Проверка встроена в сам Better Auth и
    выполняется отдельно внутри кода каждого из трёх эндпоинтов (не
    общий middleware для всех трёх сразу) — при нарушении `400` с кодом
    `PASSWORD_TOO_SHORT` или `PASSWORD_TOO_LONG`
11. Хотя бы одна буква и хотя бы одна цифра — правило не из коробки
    Better Auth, добавлено через `hooks.before` (`auth.ts:63-73`,
    `createAuthMiddleware`/`APIError` из `"better-auth/api"`).
    Middleware вызывается на каждый запрос к `/api/auth/*`, но реально
    что-то проверяет, только если `ctx.path` входит в
    `PASSWORD_SETTING_PATHS` — `Set(["/sign-up/email", "/change-password",
    "/reset-password"])` (`auth.ts:12`):
    1. Достаёт пароль как `ctx.body?.newPassword ?? ctx.body?.password`
       (у `/change-password` и `/reset-password` поле называется
       `'newPassword'`, у `/sign-up/email` — `'password'`)
    2. Если `/\p{L}/u.test(password) && /\d/.test(password)` не
       выполняется — `400` с кодом `PASSWORD_NO_LETTER_OR_DIGIT`
       ("Password must contain at least one letter and one digit"),
       запрос не доходит до остального кода эндпоинта (пользователь не
       создаётся / пароль не меняется / не сбрасывается)
    3. `hooks.before` выполняется **до** встроенной проверки длины
       (п. 10) — если пароль одновременно без буквы/цифры и неверной
       длины, клиент увидит именно `PASSWORD_NO_LETTER_OR_DIGIT`, а не
       код о длине
    4. Тот же список путей и то же правило продублированы на фронтенде
       (`src/shared/lib/auth/passwordRequirements.ts`, см.
       `09.01. Account Access-FRONTEND.md`) для мгновенной обратной
       связи до отправки формы — но именно эта серверная проверка не
       даёт обойти правило прямым вызовом API, минуя форму

# Письма (`server/src/lib/email.ts`)

12. Функция `sendEmail` должна:
   1. Если задан `RESEND_API_KEY` — отправить письмо через Resend
      (`from` берётся из `RESEND_FROM_EMAIL`, иначе дефолтный адрес
      `onboarding@resend.dev`)
   2. Если `RESEND_API_KEY` не задан (локальная разработка, тесты) — не
      отправлять ничего, вывести тему и HTML письма в консоль сервера
      (`console.log`) — весь флоу (подтверждение почты, восстановление
      пароля) остаётся тестируемым без реальной почтовой инфраструктуры

# CORS и origin в деве (`trustedOrigins`)

13. `trustedOrigins` в `auth.ts` должен включать `"http://localhost:5173"`
    только когда `NODE_ENV !== "production"`. Причина: в деве браузер
    обращается к Vite dev-серверу на `:5173`, который проксирует `/api`
    на `:3001` (`vite.config.ts` → `server.proxy`), но заголовок
    `Origin` запроса при этом остаётся `:5173` — это расходится с
    `BETTER_AUTH_URL` (`:3001`), и без явного `trustedOrigins` Better
    Auth отклоняет такие запросы как чужой origin. В проде nginx отдаёт
    фронтенд и API с одного домена, так что `Origin` и `BETTER_AUTH_URL`
    и так совпадают — настройка там не нужна

# Известные ограничения

1. Тексты писем (тема, HTML) захардкожены на русском прямо в `auth.ts`
   — не проходят через словари `src/shared/lib/i18n/dictionaries/`, в
   отличие от остального интерфейса. Язык письма не зависит от того,
   на каком языке пользователь регистрировался
2. Регистрация раскрывает существование почты в системе (`422 "User
   already exists"`), а восстановление пароля — нет (см. п. 1.1 и п. 6.1
   выше). Это асимметрия из коробки Better Auth, не отдельное решение
   этого проекта — не исправлялось
3. `sendResetPassword`/`sendVerificationEmail` не ждут своих промисов
   (`void sendEmail(...)`) — если реальная отправка через Resend
   провалится (например, невалидный `RESEND_API_KEY` в проде), клиент
   всё равно получит успешный ответ от `/sign-up`/`/request-password-reset`,
   ошибка попадёт только в серверный лог (`console.error` внутри
   `sendEmail`), не будет видна пользователю
4. Регистрация открыта всем (`POST /sign-up/email` ничего не проверяет,
   кроме занятости email) — приглашений или модерации нет, любой может
   завести аккаунт
5. ~~`userId` у `Task`/`Goal`/`Habit`/`Category` остаётся nullable~~ —
   закрыто 2026-09-19: `userId` стал обязательным полем (`String`, не
   `String?`) у всех четырёх моделей. Миграцию продовых данных на
   владельца-аккаунт решили не делать вообще — на момент включения
   авторизации на проде реальных данных почти не было (0 задач/целей, 1
   привычка без важной истории), поэтому старые "ничейные" записи
   просто удалили и начали с чистого аккаунта (см. `docs/BACKLOG.md`,
   "Продовые данные разобраны")
6. `POST /change-password` (п. 8) теоретически может вернуть `400` с
   кодом `CREDENTIAL_ACCOUNT_NOT_FOUND`, если у пользователя нет строки
   `Account` с `'providerId' = "credential"` (встроенная проверка
   Better Auth) — в этом проекте единственный способ входа сейчас
   email/password, OAuth-провайдеров нет, так что каждый пользователь
   всегда имеет такую строку и этот код на практике не встречается; не
   отдельно обработан на фронтенде (`translateAuthError` для него нет
   ключа, упадёт на дефолтную `auth.error.generic`)
