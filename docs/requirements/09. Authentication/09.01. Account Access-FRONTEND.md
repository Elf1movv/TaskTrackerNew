# 09.01. Account Access [Frontend]

# Описание

Экраны входа, регистрации, восстановления и сброса пароля, плюс гейт
всего приложения по наличию сессии и кнопка выхода. Все действия идут
через клиент Better Auth (`better-auth/react`), а не через ручные
`fetch`-запросы, как остальные сущности приложения (задачи/цели/
привычки/категории через `Repository<T>`, см.
`docs/ARCHITECTURE.md`).

# Где находится (файлы)

- `src/shared/lib/auth/authClient.ts` — `createAuthClient()`, экспорт
  `useSession`/`signIn`/`signUp`/`signOut`/`requestPasswordReset`/
  `resetPassword`/`changePassword` (`changePassword` — форма смены
  пароля в панели настроек, не эта фича, см.
  [12.01. Settings Panel-FRONTEND](../12.%20Settings/12.01.%20Settings%20Panel-FRONTEND.md))
- `src/shared/lib/auth/index.ts` — публичный API слоя (обязателен по
  правилу FSD `fsd/no-public-api-sidestep`; до его появления 6 файлов
  импортировали `authClient` напрямую из `shared/lib/auth/authClient`,
  минуя `index.ts`)
- `src/shared/lib/auth/passwordRequirements.ts` — общие правила пароля:
  `MIN_PASSWORD_LENGTH` (8), `MAX_PASSWORD_LENGTH` (128),
  `hasLetterAndDigit()`, `meetsPasswordRequirements()` — используются и
  здесь (регистрация), и в панели настроек (смена пароля, см.
  `12.01. Settings Panel-FRONTEND.md`); должны быть синхронны с теми же
  правилами на сервере (см. `09.01. Account Access-BACKEND.md`, раздел
  "Правила пароля")
- `src/shared/ui/password-requirements-hint.tsx` — `PasswordRequirementsHint`,
  живая подсказка из двух строк под полем пароля, тоже общая между этой
  формой и панелью настроек
- `src/pages/auth/ui/AuthLayout.tsx` — общий каркас неавторизованных
  экранов (карточка по центру, без сайдбара)
- `src/pages/auth/ui/LoginPage.tsx`
- `src/pages/auth/ui/RegisterPage.tsx`
- `src/pages/auth/ui/ForgotPasswordPage.tsx`
- `src/pages/auth/ui/ResetPasswordPage.tsx`
- `src/app/layouts/RootLayout.tsx` — гейт по сессии, монтирует
  `TaskProvider`/`GoalProvider`/`HabitProvider`/`CategoryProvider`
- `src/app/routes/router.tsx` — регистрация auth-роутов вне
  `RootLayout`
- `src/widgets/navigation/ui/SidebarNav.tsx` — кнопка выхода

# Функциональные требования

## Маршруты

1. `/login`, `/register`, `/forgot-password`, `/reset-password` —
   зарегистрированы в `router.tsx` как соседи узла `RootLayout`, а не
   его дочерние роуты — рендерятся без сайдбара/нижней навигации,
   потому что предназначены для разлогиненного пользователя
2. Все прочие пути (`/today`, `/tasks`, `/goals`, `/calendar`, любой
   незнакомый путь) — дочерние `RootLayout`, который сам решает,
   показывать их или отправить на `/login`

## Гейт по сессии (`RootLayout`)

3. `RootLayout` вызывает `useSession()` и решает, что рендерить, по
   трём состояниям:
   1. `isPending === true` (сессия ещё загружается) — не рендерить
      ничего (`return null`), чтобы не мелькнул экран логина перед
      реальным ответом
   2. Сессии нет (`session` = `null`/`undefined`) — `<Navigate to="/login"
      replace />`
   3. Сессия есть — рендерить `TaskProvider` → `GoalProvider` →
      `HabitProvider` → `CategoryProvider`, а внутри них обычный каркас
      приложения (сайдбар + контент + мобильная навигация). Эти 4
      провайдера смонтированы именно здесь, ниже проверки сессии, а не в
      `AppProviders` (`src/app/providers/AppProviders.tsx`, выше
      `RouterProvider`), где были раньше — см. "Известные ограничения",
      п. 3

## Регистрация (`RegisterPage`)

4. Поля `'name'`, `'email'`, `'password'` — все обязательны (кнопка
   отправки не блокируется явно по пустоте этих полей, но `handleSubmit`
   рано выходит, если после `.trim()` любое из `'name'`/`'email'` пустое
   или пароль не проходит проверку требований, см. следующий пункт).
   Поле пароля — обычный `Input` с `type="password"` (без переключателя
   "показать/скрыть" — тот есть только в форме смены пароля в панели
   настроек, см. `PasswordInput`,
   [12.01. Settings Panel-FRONTEND](../12.%20Settings/12.01.%20Settings%20Panel-FRONTEND.md))
5. Под полем пароля — `PasswordRequirementsHint`, живая подсказка из
   двух строк, обновляется на каждое нажатие клавиши, цвет меняется с
   серого на цвет `primary` по мере выполнения:
   1. `'password'.length` от `MIN_PASSWORD_LENGTH` (8) до
      `MAX_PASSWORD_LENGTH` (128) — верхняя граница вдобавок жёстко
      ограничена атрибутом `maxLength` самого поля (ввести больше 128
      символов физически нельзя)
   2. `hasLetterAndDigit('password')` — хотя бы одна буква (`\p{L}`) и
      хотя бы одна цифра
   Кнопка отправки задизейблена, пока `meetsPasswordRequirements(password)`
   не вернёт `true` (обе группы условий выше). Те же два правила
   проверяет сервер (см.
   [09.01. Account Access-BACKEND](./09.01.%20Account%20Access-BACKEND.md),
   "Правила пароля") — фронтенд не полагается только на свою проверку
6. Успешная отправка **не** переводит пользователя дальше — вместо
   этого `RegisterPage` переключается на экран "Проверьте почту"
   (`submittedEmail` в состоянии компонента), потому что вход всё равно
   заблокирован до подтверждения почты (см.
   `09.01. Account Access-BACKEND.md`, `emailVerification`)
7. Ошибка регистрации (например, email уже занят или сервер отклонил
   пароль по правилам, описанным в п. 5) показывается текстом под
   формой — переведённым через `translateAuthError()`
   (`src/shared/lib/auth/errorMessages.ts`), которая мапит стабильный
   `error.code` от Better Auth на ключи `auth.error.*` в словарях
   `i18n`, а не сырой `error.message` библиотеки

## Вход (`LoginPage`)

8. Поля `'email'`, `'password'` — Enter в любом из полей отправляет
   форму так же, как клик по кнопке
9. Ссылка "Забыли пароль?" рядом с полем пароля ведёт на
   `/forgot-password`
10. При успешном входе — переход на `/today` через **полную навигацию
    браузера** (`window.location.href`), не через react-router
    `navigate()`. Это намеренный фикс реального бага (см. "Известные
    ограничения" ниже) — только для этого перехода, не общий паттерн для
    всего приложения. Фактический адрес перехода — `/today?firstLogin=1`
    или `/today?welcomeBack=1` в зависимости от того, пришёл ли вход сразу
    после подтверждения почты (query-параметр `'verified'`, который
    `RegisterPage` попросил Better Auth подставить в ссылку письма) — эти
    два варианта управляют экраном приветствия на `TodayPage`, см.
    [11.01. Welcome Screens-FRONTEND](../11.%20Onboarding/11.01.%20Welcome%20Screens-FRONTEND.md)
11. При ошибке входа — текст ошибки под формой, тот же паттерн
    `error.message`, что и в регистрации: неверный email/пароль и
    неподтверждённая почта показываются одним и тем же местом в UI, но
    разным текстом (see backend doc, `INVALID_EMAIL_OR_PASSWORD` vs
    `EMAIL_NOT_VERIFIED`)

## Восстановление пароля

12. `ForgotPasswordPage` принимает `'email'`, зовёт
    `authClient.requestPasswordReset({ email, redirectTo:
    "{origin}/reset-password" })`, и **всегда** показывает один и тот
    же экран "проверьте почту" после отправки — независимо от того,
    существует ли такой аккаунт (соответствует поведению бэкенда, см.
    `09.01. Account Access-BACKEND.md`, п. 6.1)
13. `ResetPasswordPage` читает `'token'` из query-параметра URL
    (`useSearchParams`):
    1. Если токена нет — показать сообщение "ссылка недействительна" с
       кнопкой назад на `/forgot-password`, форма пароля не рендерится
       вовсе
    2. Если токен есть — форма с одним полем нового пароля,
       `authClient.resetPassword({ newPassword, token })`; при успехе —
       переход на `/login` **через обычный react-router `navigate()`**
       (не через `window.location.href` — здесь этой гонки, что в
       `LoginPage`, нет, см. ниже). Поле пароля здесь — обычный
       `Input`, без `PasswordRequirementsHint` (этот экран сознательно
       не тронули при добавлении подсказки, см. "Известные
       ограничения", п. 4) — если сервер отклонит пароль по правилам
       п. 5, ошибка всё равно покажется переведённым текстом через
       `translateAuthError()`, потому что `errorMessages.ts` мапит те же
       коды ошибок независимо от того, на каком экране они пришли

## Выход (`SidebarNav`)

14. Кнопка "Log out" — в нижней части сайдбара, под переключателями
    темы/языка, вызывает `signOut()` без подтверждающего диалога.
    Логаут не требует `window.location.href` — компонент уже
    смонтирован внутри работающего `RootLayout`, и `useSession()` там
    сам реагирует на сброс сессии обычной client-side реактивностью

# Известные ограничения

1. **Гонка `navigate()` vs `window.location.href` после входа
   (реальный найденный и исправленный баг).** Изначально `LoginPage`
   вызывал `navigate("/today")` (react-router) после успешного
   `signIn.email(...)`. Это оставляло пользователя на экране логина,
   несмотря на валидную сессию (подтверждено напрямую: `fetch('/api/auth/get-session')`
   в консоли браузера показывал реальную сессию, пока UI всё ещё
   показывал форму входа). Причина — `useSession()` в `RootLayout`
   подписывается на стор сессии Better Auth; при чисто клиентской
   навигации `RootLayout` не перемонтируется заново, и его подписка
   иногда успевала прочитать состояние до того, как сторами Better Auth
   завершилась собственная инвалидация после `signIn`, — то есть гонка
   между двумя механизмами обновления состояния, не баг в одном из них
   по отдельности. Фикс — `window.location.href = "/today"` вместо
   `navigate()`: это полная перезагрузка страницы, `RootLayout`
   монтируется заново и сразу читает уже точно актуальную сессию.
   **Это однонаправленный фикс** именно для перехода
   "разлогинен → только что вошёл, первый раз в этой сессии попадает в
   защищённое дерево": логаут (уже внутри смонтированного `RootLayout`)
   и переход после сброса пароля (`ResetPasswordPage` → `/login`, тоже
   вне защищённого дерева в обе стороны) этой гонки не имеют и намеренно
   оставлены на обычном `navigate()`
2. ~~Тексты на экранах авторизации захардкожены на русском~~ —
   исправлено: `LoginPage`/`RegisterPage`/`ForgotPasswordPage`/
   `ResetPasswordPage` полностью переведены через `useLanguage()`/`t()`
   (ключи `auth.*` в обоих словарях), включая сообщения об ошибках
   через `translateAuthError()` (см. пункт 7 выше) — этот пункт был
   верен только на момент первой документации фичи (2026-09-18),
   i18n добавили в тот же день чуть позже
3. ~~Провайдеры данных (`TaskProvider`/`GoalProvider`/`HabitProvider`/
   `CategoryProvider`) смонтированы выше `RouterProvider`, запускают
   `repository.list()` безусловно и на `/login`/`/register` дают 4
   необработанных `401`~~ — исправлено: эти 4 провайдера переехали из
   `src/app/providers/AppProviders.tsx` (который монтируется выше
   `RouterProvider`) в `src/app/layouts/RootLayout.tsx`, внутрь ветки "сессия
   есть" (см. "Гейт по сессии", п. 3.3). `AppProviders` продолжает
   монтироваться выше роутера и оборачивать `/login`/`/register` — но
   теперь в нём остаётся только то, что не завязано на сессию (тема,
   язык, drag-and-drop, тултипы, тосты). `LanguageProvider` (в
   `AppProviders`) остаётся выше этих 4 провайдеров в дереве, потому что
   `usePersistedCollection` зовёт `useLanguage()` для перевода текста
   ошибок в `toast.error`. Практический эффект: на `/login` и `/register`
   `TaskProvider`/`GoalProvider`/`HabitProvider`/`CategoryProvider`
   больше не монтируются вообще (сессии там ещё нет), поэтому запросы
   `/api/tasks`/`/api/goals`/`/api/habits`/`/api/categories` не уходят и
   `401` в консоли браузера на этих страницах больше нет
4. `ResetPasswordPage` не получил `PasswordRequirementsHint` при
   добавлении живой подсказки требований к паролю в регистрацию и в
   смену пароля (см. п. 5 выше и
   [12.01. Settings Panel-FRONTEND](../12.%20Settings/12.01.%20Settings%20Panel-FRONTEND.md))
   — сознательное решение, не забытое место: пользователь на этом
   экране обычно уже знает свой прежний пароль и придумывает похожий
   новый, а не с нуля. Сервер всё равно проверяет оба правила на
   `/reset-password` (см. `09.01. Account Access-BACKEND.md`, "Правила
   пароля") — при нарушении пользователь просто увидит переведённую
   ошибку под формой уже после отправки, а не подсказку заранее
