# 13.04. Critical Reminder Alerts [Frontend]

# Описание

Модальное, требующее реакции окно (`AlertDialog`, не обычный `Dialog` —
не закрывается кликом мимо или по крестику) для напоминаний с
`'priority' === "critical"`, всплывающее по мере приближения их
времени/дня. Отдельный, более настойчивый механизм по сравнению с
`13.01. Due Date Reminders` (обычный toast про сроки задач/целей, никогда
не прерывает) — здесь окно перекрывает экран и требует явного клика по
одной из двух кнопок. Не визуальный компонент до первого сработавшего
порога — пока очередь пуста, рендерит `null`. Монтируется один раз в
`RootLayout`, срабатывает при открытом приложении, проверка — раз в
минуту.

# Где находится (файлы)

- `src/widgets/critical-reminder-alert/ui/CriticalReminderAlert.tsx` —
  вся логика компонента (таймер, очередь, `localStorage`-дедупликация)
- `src/widgets/critical-reminder-alert/lib/checkCriticalThresholds.ts` —
  чистая функция принятия решения "показать ли алерт", покрыта 8
  unit-тестами в `checkCriticalThresholds.test.ts`
- `src/widgets/critical-reminder-alert/index.ts` — публичный barrel
  (`CriticalReminderAlert`)

- `src/shared/ui/alert-dialog.tsx` — `AlertDialog`/`AlertDialogAction`/…
- `src/shared/lib/date.ts` — `formatDateKey`

# Функциональные требования

## Проверка порогов

1. Эффект в `CriticalReminderAlert` запускает проверку сразу при
   монтировании и затем каждые 60 секунд (`CHECK_INTERVAL_MS`,
   `setInterval`) — не событийно, а поллингом, поэтому точный момент
   пересечения порога может быть замечен с опозданием до минуты
2. На каждой проверке в расчёт берутся только напоминания с
   `'priority' === "critical"` и `'completed' === false`
   (`reminders.filter(...)`, `CriticalReminderAlert.tsx:58`) — обычные
   (`'normal'`) напоминания этот механизм не затрагивает вовсе
3. Решение — в чистой функции `checkCriticalThresholds(criticalReminders,
   shown, now)` (`src/widgets/critical-reminder-alert/lib/checkCriticalThresholds.ts`),
   принимающей уже отфильтрованный список, карту уже показанных порогов
   и текущее время — вынесена из компонента специально, чтобы быть
   тестируемой без моков таймера/DOM
4. Для напоминания **с** `'time'`:
   1. Целевой момент — `'date'` + `'time'`, разобранные вместе
      (`parse("yyyy-MM-dd HH:mm", ...)`, `date-fns`)
   2. Порог "24h" — срабатывает один раз, когда `now` впервые попадает в
      окно `[target − 24 часа, target)`
   3. Порог "1h" — срабатывает один раз, когда `now` впервые попадает в
      окно `[target − 1 час, target)`, независимо от того, сработал ли
      уже порог "24h" для этого же напоминания
   4. Оба порога могут сработать **одновременно** на одной проверке,
      если предыдущая проверка была давно (например, вкладка была
      закрыта и снова открылась за 30 минут до срока — оба ещё не
      показанных порога уже попадают в свои окна разом)
   5. После того как `now >= target` (время уже прошло) — ни один порог
      для этого напоминания больше не срабатывает, даже если не был
      показан раньше
   6. Каждый порог срабатывает не более одного раза на напоминание —
      повторное попадание `now` в то же окно на следующей проверке
      игнорируется благодаря `shown`
5. Для напоминания **без** `'time'` — единственный порог "day",
   срабатывает один раз, если `'date'` совпадает с сегодняшним днём
   (`formatDateKey(now)`) — то же правило по дню, что у `13.01. Due Date
   Reminders`, без учёта времени суток

## Дедупликация

6. Показанные пороги хранятся в `localStorage` под ключом
   `mytracker-critical-alerts-shown-<userId>` (`storageKey`,
   `CriticalReminderAlert.tsx:22-24`), значение — `Record<reminderId,
   Threshold[]>` (`{ [reminderId]: ("24h" | "1h" | "day")[] }`)
7. Ключ включает `'userId'`, не только само напоминание — та же причина,
   что у `13.01. Due Date Reminders`: общий браузер с двумя аккаунтами не
   должен позволять одному аккаунту молча гасить алерты другого
8. Если `localStorage` недоступен (приватный режим, заблокированное
   хранилище) — чтение и запись флага просто проглатывают исключение;
   алерт в этом случае может показываться повторно при каждой
   перезагрузке в рамках одной сессии, но приложение не падает — тот же
   приём, что у `13.01. Due Date Reminders`

## Окно и очередь

9. Если за одну проверку набралось несколько новых алертов (несколько
   напоминаний одновременно подошли к порогу, либо один сразу к двум
   порогам, см. п. 4.4) — они складываются в локальную очередь
   (`useState<CriticalAlert[]>`), показывается только первый (`queue[0]`)
10. Следующий алерт из очереди показывается сразу после закрытия
    текущего — очередь продвигается только через `onOpenChange` самого
    `AlertDialog` (`open => !open && dismiss()`), не из отдельных
    `onClick`-обработчиков кнопок, чтобы клик не продвигал очередь дважды
    за один тик (обе кнопки и так закрывают диалог по клику — встроенное
    поведение Radix для `AlertDialogAction`)
11. `AlertDialog` (не `Dialog`) — не закрывается кликом по оверлею или
    Escape без явного действия пользователя, только через одну из двух
    кнопок в футере
12. Контент диалога получает подсвечивающий класс (`border-destructive
    border-2 shadow-[0_0_40px_-5px_rgba(201,80,58,0.5)]`) — красная рамка
    и свечение вместо обычного нейтрального вида `AlertDialog`. Анимация
    пульсации под эту рамку сознательно отложена — пока статичная,
    прямое решение пользователя, не недосмотр
13. Заголовок диалога — заголовок напоминания (`'title'`); описание —
    метка сработавшего порога (`reminders.criticalAlertIn24h` = "через
    24 часа", `reminders.criticalAlertIn1h` = "через 1 час",
    `reminders.criticalAlertToday` = "сегодня" — для порога `"day"`), и
    через `·` время напоминания, если задано
14. Две кнопки в футере, обе — `AlertDialogAction` (закрывают диалог
    автоматически по клику, не только "Понятно"):
    1. "Перейти" (`reminders.viewAction`) — дополнительно, до закрытия,
       вызывает `navigate('/calendar?date=' + reminder.date)`
    2. "Понятно" (`reminders.criticalAlertAck`) — просто закрывает
       диалог, без навигации

# Известные ограничения

1. В приложении нет push-уведомлений/service worker — сработает только
   пока вкладка браузера реально открыта; закрытое приложение или ушедшая
   в фон надолго вкладка (дольше окна конкретного порога) может пропустить
   момент показа, хотя при следующем открытии до срока порог всё ещё
   сработает (окно проверяется по факту "уже вошли", не "только что
   вошли")
2. Проверка раз в минуту, не мгновенно на пересечении порога — точный
   момент показа может отличаться от расчётного часа/дня до 60 секунд
3. Как и у обычных напоминаний (`13.02.`), после того как целевое время
   критичного напоминания уже прошло, алерт по нему больше не появится —
   механизм только предупреждает заранее, не отмечает просроченное
   отдельно
