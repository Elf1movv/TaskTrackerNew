# 13.02. Reminder Entity [Backend]

# Где находится (файлы)

- `server/src/routes/reminders.ts` — все методы
- `server/src/validation/reminder.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Reminder`
- `server/prisma/migrations/20260922120000_add_reminders/` — миграция,
  добавившая таблицу
- `server/prisma/migrations/20260922160000_add_reminder_priority/` —
  миграция, добавившая колонку `'priority'`
- `server/src/middleware/requireAuth.ts` — проверка сессии (см.
  `09.01. Account Access-BACKEND.md`)

# Авторизация и разграничение по пользователю

1. `remindersRouter.use(requireAuth)` — весь роутер требует активную
   сессию; без неё любой метод ниже отвечает `401 { error: "Unauthorized"
   }` раньше, чем разбирается тело запроса
2. `requireAuth` кладёт `id` текущего пользователя в `req.userId` — каждый
   метод ниже фильтрует/проставляет именно это значение, `'userId'` от
   клиента не принимается нигде
3. `GET /` читает только строки, где `'userId' = req.userId`; `POST /`
   всегда создаёт запись с `'userId' = req.userId`
4. `PATCH /:id` и `DELETE /:id` используют `updateMany`/`deleteMany` (и
   отдельный `findFirst`, тоже с `userId` в `WHERE`) вместо
   `update`/`delete` по одному `'id'` — тот же приём, что у Task/Goal/
   Habit/Category. Следствие: если `'id'` существует, но принадлежит
   другому пользователю, ответ **не отличим** от "такой записи вообще
   нет" (`404`) — никогда `403`, чтобы не подтверждать чужому
   пользователю сам факт существования записи (см.
   `01.01. Task CRUD-BACKEND.md`, п. 4 — тот же принцип)

# Методы

1. При получении `GET /api/reminders` сервер должен:
   1. Прочитать все строки таблицы `Reminder`, где `'userId' =
      req.userId`, отсортированные по `'date'` по возрастанию, затем по
      `'time'` по возрастанию (`orderBy: [{ date: "asc" }, { time: "asc"
      }]`)
   2. Для каждой строки вернуть клиенту: `'id'`, `'title'`, `'date'`,
      `'time'`, `'priority'`, `'completed'`, `'updatedAt'`
      (`toClientReminder`, `server/src/routes/reminders.ts:22-40`)
   3. Не отдавать клиенту `'userId'`/`'createdAt'` — у напоминания, в
      отличие от `Task`, `'createdAt'` клиенту не нужен: нет правила
      видимости, которое от него зависело бы (сравни с `01.01. Task
      CRUD-BACKEND.md`, `GET /api/tasks`, п. 1.3)
   4. `'date'` хранится в базе как настоящая дата (`@db.Date`), но на
      проводе клиенту всегда отдаётся строкой в формате `"YYYY-MM-DD"` —
      та же конвертация, что у `Task.dueDate`
   5. `'time'` хранится и отдаётся как обычная строка `"HH:mm"` либо
      `null` — не отдельный SQL-тип времени, конвертации не требует

2. При получении `POST /api/reminders` сервер должен:
   1. Провалидировать тело запроса схемой `createReminderSchema` — если
      не прошло, вернуть `400` с `{ error, details }`
   2. `'id'` — обязательное поле тела запроса (UUID). Сервер его не
      генерирует сам, хотя в Prisma-схеме у `Reminder.id` есть
      `@default(uuid())` — клиент генерирует `'id'` заранее
      (`crypto.randomUUID()`), тот же паттерн, что у `Task`/`Goal`, ради
      оптимистичного отображения
   3. `'date'` — обязательное поле, строго формат `"YYYY-MM-DD"`, иначе
      `400`. В отличие от `Task.dueDate`, `null` не допускается —
      напоминание всегда привязано к дню
   4. `'time'` — необязательное поле, но ключ должен присутствовать в
      теле всегда (может быть `null`); если не `null`, строго формат
      `"HH:mm"` (`z.string().regex(/^\d{2}:\d{2}$/)`), иначе `400`
   5. `'priority'` — обязательное поле тела запроса, строго один из
      `"normal" | "critical"` (`z.enum(["normal", "critical"])`), иначе
      `400`. В отличие от колонки в базе (`Reminder.priority
      @default("normal")`, нужен только для бэкофилла строк, созданных
      до этого поля, через миграцию `20260922160000_add_reminder_priority`),
      на уровне API поле обязательно — клиент всегда отправляет его явно,
      как и `Task.priority`
   6. `'completed'` — обязательное булево поле тела запроса
   7. Создать новую строку `Reminder` с `'userId' = req.userId`. В
      отличие от `Task`/`Goal`/`Habit`/`Category`, у `Reminder` нет
      колонки `'order'` — порядок создания никак не сохраняется и не
      влияет на порядок выдачи (см. `GET /`, п. 1.1)
   8. Вернуть созданную запись с кодом `201`

3. При получении `PATCH /api/reminders/:id` сервер должен:
   1. Провалидировать тело схемой `updateReminderSchema` — ожидается
      `{ patch: {...изменённые поля...}, expectedUpdatedAt: "..." }`,
      иначе `400`. `'patch'` — те же поля, что в `createReminderSchema`,
      кроме `'id'`, все необязательные (`.partial()`) — тот же паттерн
      конфликт-детекции, что у `Task`/`Goal`/`Habit`
   2. Атомарно обновить строку **только если** её текущий `'updatedAt'` в
      базе совпадает с присланным `'expectedUpdatedAt'`
      (`updateMany({ where: { id, userId, updatedAt: expectedUpdatedAt }
      })`)
   3. Если ни одна строка не подошла под условие — проверить отдельно,
      существует ли запись с таким `'id'` **и** `'userId' = req.userId`:
      1. Не существует (или принадлежит другому пользователю) → `404` с
         `{ error: "Reminder not found" }`
      2. Существует, но `'updatedAt'` не совпал (кто-то другой уже
         изменил это напоминание) → `409` с `{ error, current: <актуальная
         запись> }` — клиент должен показать актуальную версию, а не
         тихо перезаписать её
   4. Если обновление прошло — вернуть актуальную запись с кодом `200`

4. При получении `DELETE /api/reminders/:id` сервер должен:
   1. Удалить запись с этим `'id'`, где `'userId' = req.userId`
      (`deleteMany`)
   2. Если записи не было (или она принадлежит другому пользователю) —
      вернуть `404` с `{ error: "Reminder not found" }`
   3. Если удаление прошло — вернуть `204` без тела

# Известные ограничения

1. Нет `PATCH /api/reminders/reorder` — единственная сущность проекта без
   ручного порядка. `GET /` сортирует по `'date'`, затем по `'time'`
   средствами Postgres (`orderBy`), но для `'time' = null` Postgres по
   умолчанию сортирует `NULL` **последним** при `ASC` — в то время как
   клиентские селекторы (`selectUpcomingReminders`/`selectRemindersOnDay`,
   см. `13.02. Reminder Entity-FRONTEND.md`) через `(a.time ?? "")
   .localeCompare(...)` ставят безвременные напоминания **первыми**. На
   практике это расхождение не проявляется — нигде в интерфейсе сырой
   порядок из `GET /` не показывается напрямую, оба места отображения
   (карточка на Today, сетка/панель календаря) всегда пропускают список
   через один из клиентских селекторов, которые и определяют финальный
   порядок
2. Валидация полей — через `zod` (`title` не пустой, `date`/`time`
   строго формат), но нет проверки на уровне бизнес-логики сверх этого
   (например, что `'date'` не в прошлом — как и у `Task.dueDate`, это
   осознанно не ограничивается)
3. Конфликт-детекция через `'updatedAt'` защищает только от
   одновременного изменения **одной и той же записи** двумя
   устройствами — если одно устройство удаляет напоминание, пока другое
   его редактирует, `PATCH` вернёт `404` (запись физически исчезла), а не
   `409` — тот же случай, что описан у `Task` (см. `01.01. Task
   CRUD-BACKEND.md`, "Известные ограничения", п. 2)
