# 02.01. Goal CRUD [Backend]

# Где находится (файлы)

- `server/src/routes/goals.ts` — все методы
- `server/src/validation/goal.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Goal`
- `server/src/middleware/requireAuth.ts` — проверка сессии

# Авторизация и разграничение по пользователю

Тот же паттерн, что у `Task` (см.
[01.01. Task CRUD-BACKEND](../01.%20Tasks/01.01.%20Task%20CRUD-BACKEND.md),
раздел "Авторизация и разграничение по пользователю"): `goalsRouter.use(requireAuth)`,
`401` без сессии, `'userId' = req.userId` на `GET`/`POST`, `userId` в
`WHERE` у `updateMany`/`deleteMany` для `PATCH reorder`/`PATCH :id`/
`DELETE :id` — цель другого пользователя ведёт себя как несуществующая
(`404`, не `403`).

# Методы

1. При получении `GET /api/goals` сервер должен:
   1. Прочитать все строки таблицы `Goal`, отсортированные по `'order'`
      по возрастанию
   2. Для каждой строки вернуть клиенту: `'id'`, `'title'`,
      `'description'`, `'progress'`, `'targetDate'`, `'color'`,
      `'milestones'`, `'updatedAt'`
   3. Не отдавать клиенту поля `'order'`, `'createdAt'`, `'userId'`

2. При получении `POST /api/goals` сервер должен:
   1. Провалидировать тело схемой `createGoalSchema` (включая массив
      `'milestones'` — каждый со своими `'id'`/`'title'`/`'completed'`),
      иначе `400`
   2. Создать запись с `'order'` = текущий минимум минус 1 (новая цель
      — первая в списке)
   3. `'milestones'` сохраняется как есть — это JSON-колонка, требует
      каста `as unknown as Prisma.InputJsonValue` при записи (Prisma
      не выводит совместимость типов автоматически для JSON-полей)
   4. Вернуть созданную запись с кодом `201`

3. При получении `PATCH /api/goals/reorder` сервер должен: то же самое,
   что и `PATCH /api/tasks/reorder` (см. `01.01. Task CRUD-BACKEND.md`)
   — обновляет только `'order'` для перечисленных `id`, одной
   транзакцией, зарегистрирован до `PATCH /:id`

4. При получении `PATCH /api/goals/:id` сервер должен:
   1. Провалидировать тело схемой `updateGoalSchema` —
      `{ patch: {...}, expectedUpdatedAt: "..." }`
   2. Атомарно обновить строку, только если `'updatedAt'` совпадает с
      `'expectedUpdatedAt'` (тот же паттерн, что у Task)
   3. Если `'patch'` содержит `'milestones'` — привести к
      `Prisma.InputJsonValue`; если не содержит — не трогать колонку
      `'milestones'` вообще (`undefined`, не перезаписывать пустым)
   4. При несовпадении — `404`, если записи нет, иначе `409` с
      актуальной записью (см. `01.01. Task CRUD-BACKEND.md`, тот же
      механизм)
   5. При успехе — вернуть актуальную запись, код `200`

5. При получении `DELETE /api/goals/:id` сервер должен: удалить запись,
   `404` если её не было, `204` при успехе — вместе с самой целью
   удаляются и все её `'milestones'` (они внутри той же JSON-колонки,
   отдельно не хранятся)

# Известные ограничения

1. **Нет отдельных серверных методов на milestones** — они всегда
   передаются и сохраняются как часть всего объекта `Goal` через
   `'milestones'` в `PATCH`. Если понадобится атомарно менять один
   milestone без риска перезаписать чужие параллельные правки других
   полей цели — текущая схема этого не даёт (весь `'milestones'`
   заменяется целиком при каждом изменении)
2. Валидация содержимого `'milestones'` — только форма (`id`/`title`/
   `completed` в каждом элементе), не проверяется, например, что `'id'`
   каждого milestone уникален в пределах массива
3. `'userId'` — `String?` (nullable): цели, созданные до авторизации,
   имеют `'userId' = NULL` и не видны ни одному пользователю, пока не
   выполнена разовая миграция продовых данных (см.
   [09.01. Account Access-BACKEND](../09.%20Authentication/09.01.%20Account%20Access-BACKEND.md))
