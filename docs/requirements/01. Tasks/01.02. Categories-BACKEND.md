# 01.02. Categories [Backend]

# Где находится (файлы)

- `server/src/routes/categories.ts` — все методы
- `server/src/validation/category.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Category`
- `server/prisma/migrations/20260917144335_add_completed_at_and_category/`
  — миграция, создающая таблицу и сидирующая 4 категории, ранее
  захардкоженные на фронтенде (`Work`, `Personal`, `Health`, `Learning`)

# Методы

1. При получении `GET /api/categories` сервер должен:
   1. Прочитать все строки таблицы `Category`, отсортированные по
      `'order'` по возрастанию
   2. Для каждой строки вернуть клиенту: `'id'`, `'name'`, `'updatedAt'`
   3. Не отдавать клиенту поля `'order'`, `'createdAt'`, `'userId'` —
      это поля только для сервера

2. При получении `POST /api/categories` сервер должен:
   1. Провалидировать тело запроса схемой `createCategorySchema` —
      `'id'` (UUID, обязателен, генерируется клиентом — как и у задач),
      `'name'` (непустая строка) — если не прошло, `400`
   2. Создать новую строку `Category` с `'order'` = текущий максимум
      среди всех категорий плюс 1 (в отличие от `Task`, который
      добавляется **первым** — новая категория добавляется
      **последней**: пикер категорий читается как "старые/устоявшиеся
      сверху", а не "новые сверху")
   3. `'name'` помечено `@unique` на уровне БД (`schema.prisma`) — если
      имя уже существует, `Prisma` выбросит ошибку нарушения уникального
      ограничения (см. "Известные ограничения")
   4. Вернуть созданную запись с кодом `201`

3. При получении `PATCH /api/categories/reorder` сервер должен:
   1. Провалидировать тело как массив `{ id, order }`-пар — если не
      прошло, `400`
   2. Обновить **только** колонку `'order'` для перечисленных строк,
      одной транзакцией
   3. Зарегистрирован **до** `PATCH /:id` — та же причина, что у задач
      (иначе `"reorder"` был бы принят за `:id`)
   4. Вернуть `204` без тела
   5. На данный момент ни один экран фронтенда этот метод не вызывает —
      реализован для полноты API по образцу `tasks`/`goals`, UI для
      переупорядочивания категорий не существует (см.
      `01.02. Categories-FRONTEND.md`)

4. При получении `PATCH /api/categories/:id` сервер должен:
   1. Провалидировать тело схемой `updateCategorySchema` — ожидается
      `{ patch: {...изменённые поля...}, expectedUpdatedAt: "..." }`,
      иначе `400`
   2. Атомарно обновить строку **только если** её текущий `'updatedAt'`
      в базе совпадает с присланным `'expectedUpdatedAt'`
      (`updateMany({ where: { id, updatedAt: expectedUpdatedAt } })`) —
      тот же паттерн конфликт-детекции, что у задач
   3. Если ни одна строка не подошла — `404`, если записи нет вовсе, или
      `409` с `{ error, current }`, если `'updatedAt'` не совпал
   4. Если обновление прошло — вернуть актуальную запись с кодом `200`
   5. На данный момент фронтенд этот метод не вызывает — нет UI для
      переименования категории

5. При получении `DELETE /api/categories/:id` сервер должен:
   1. Удалить запись с этим `'id'`
   2. Если записи не было — вернуть `404` с
      `{ error: "Category not found" }`
   3. Если удаление прошло — вернуть `204` без тела
   4. На данный момент фронтенд этот метод не вызывает — нет UI для
      удаления категории. Удаление категории никак не затрагивает
      задачи, у которых `'category'` равно её имени — `'category'` у
      `Task` остаётся простой строкой, а не внешним ключом (см. ниже)

# Известные ограничения

1. `Task.category` — обычная строка, **не** внешний ключ на
   `Category.id`/`Category.name`. Это осознанный выбор, чтобы не делать
   миграцию данных по существующим задачам при введении сущности
   `Category`. Следствие: удаление или переименование категории (через
   `DELETE`/`PATCH`, которые реализованы, но пока не вызываются из UI) не
   обновит и не удалит `'category'` у уже созданных задач — они останутся
   со старым именем как со свободной строкой, никак не привязанной к
   реальной категории
2. Дубликат `'name'` при `POST` не обрабатывается отдельно — нарушение
   `@unique` из Prisma долетает до общего `errorHandler` и превращается в
   `500 { error: "Internal server error" }`, а не в осмысленный `400`/
   `409` с понятным сообщением о том, что имя занято (подтверждено
   тестом — см. `server/src/routes/categories.test.ts`, "rejects a
   duplicate category name" ожидает именно `500`)
3. Как и у задач, нет проверки согласованности бизнес-логики сверх
   `zod` (например, ограничения на длину `'name'` нет)
