# 01.02. Categories [Backend]

# Где находится (файлы)

- `server/src/routes/categories.ts` — все методы
- `server/src/validation/category.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Category`, поле
  `User.categoriesSeeded`
- `server/src/middleware/requireAuth.ts` — проверка сессии

# Авторизация и разграничение по пользователю

Тот же общий паттерн, что у `Task` (см.
[01.01. Task CRUD-BACKEND](./01.01.%20Task%20CRUD-BACKEND.md), раздел
"Авторизация и разграничение по пользователю"): `categoriesRouter.use(requireAuth)`,
`401` без сессии, `userId` в `WHERE` у `updateMany`/`deleteMany` для
`PATCH reorder`/`PATCH :id`/`DELETE :id` — категория другого
пользователя ведёт себя как несуществующая (`404`, не `403`). Плюс
специфика этой сущности:

1. `'name'` больше не `@unique` глобально — ограничение изменено на
   `@@unique([userId, name])`: два разных пользователя теперь могут
   каждый завести категорию с одинаковым именем "Work", конфликт
   возможен только внутри одного и того же аккаунта

# Методы

1. При получении `GET /api/categories` сервер должен:
   1. Прочитать `'categoriesSeeded'` текущего пользователя (поле
      `User.categoriesSeeded`, `server/prisma/schema.prisma`) —
      булево, по умолчанию `false` для новых аккаунтов
      (`server/src/routes/categories.ts:28-31`)
   2. Если `'categoriesSeeded' === false` — одной транзакцией: создать 4
      стандартные категории (`DEFAULT_CATEGORY_NAMES = ["Work", "Personal",
      "Health", "Learning"]`) для этого пользователя ("ленивый" сид, как
      раньше) и выставить `'categoriesSeeded' = true`
      (`server/src/routes/categories.ts:32-45`). Создание категорий идёт с
      `skipDuplicates: true` — пользователь мог успеть создать свою первую
      категорию с именем, совпадающим с одним из стандартных (например,
      "Work"), пока этот же самый `GET` ещё выполнялся (см. `POST` ниже);
      без `skipDuplicates` сид упал бы с ошибкой нарушения
      `@@unique([userId, name])` вместо того, чтобы просто пропустить
      совпавшее имя
   3. `'categoriesSeeded'` — а не "равно ли текущее количество категорий
      пользователя нулю" — то, что отличает новый аккаунт от аккаунта,
      который осознанно удалил все свои категории: простой подсчёт строк
      не мог различить эти два случая, из-за чего удаление последней
      категории раньше молча возвращало 4 стандартные заново при
      следующей загрузке (см. `LEARNING.md`; раньше документировано как
      "принятый компромисс" в "Известные ограничения" этого файла — теперь
      исправлено, см. ниже)
   4. Прочитать все строки `Category` с `'userId' = req.userId`,
      отсортированные по `'order'` по возрастанию
   5. Для каждой строки вернуть клиенту: `'id'`, `'name'`, `'updatedAt'`
   6. Не отдавать клиенту поля `'order'`, `'createdAt'`, `'userId'` —
      это поля только для сервера

2. При получении `POST /api/categories` сервер должен:
   1. Провалидировать тело запроса схемой `createCategorySchema` —
      `'id'` (UUID, обязателен, генерируется клиентом — как и у задач),
      `'name'` (непустая строка) — если не прошло, `400`
   2. Создать новую строку `Category` с `'userId' = req.userId` и
      `'order'` = текущий максимум среди категорий **этого же
      пользователя** плюс 1 (в отличие от `Task`, который добавляется
      **первым** — новая категория добавляется **последней**: пикер
      категорий читается как "старые/устоявшиеся сверху", а не "новые
      сверху")
   3. В той же транзакции выставить `'categoriesSeeded' = true` для этого
      пользователя (`server/src/routes/categories.ts:63-72`) — пользователь,
      создавший свою первую категорию раньше, чем успел выполниться его
      начальный `GET` (гонка "добавить категорию" против ещё не
      завершённого исходного списка), уже имеет свою собственную
      категорию, поэтому следующий `GET` не должен досеивать сверху 4
      стандартные
   4. `('userId', 'name')` помечены `@@unique` на уровне БД
      (`schema.prisma`) — если у этого же пользователя уже есть
      категория с таким именем, `Prisma` выбрасывает ошибку нарушения
      уникального ограничения (код `P2002`)
   5. Поймать `P2002` и вернуть чистый `409 { error: "Category name
      already exists" }` (`server/src/routes/categories.ts:74-78`), а не
      дать ошибке долететь до общего `errorHandler` — раньше это
      превращалось в необработанный `500 { error: "Internal server
      error" }` (см. "Известные ограничения" — исправлено, подтверждено
      тестом `server/src/routes/categories.test.ts`, "rejects a duplicate
      category name for the same user with a clean 409, not a raw 500")
   6. Вернуть созданную запись с кодом `201`

3. При получении `PATCH /api/categories/reorder` сервер должен:
   1. Провалидировать тело как массив `{ id, order }`-пар — если не
      прошло, `400`
   2. Обновить **только** колонку `'order'` для перечисленных строк,
      одной транзакцией, отфильтрованных по `'userId' = req.userId`.
      Строки транзакции отсортированы по `'id'` перед сборкой — тот же
      приём, что у `Task` (детерминированный порядок блокировок, чтобы
      две перекрывающиеся транзакции `PATCH /reorder` не задедлочились
      друг с другом, реальный баг, исправлен 2026-09-21, см. `01.01.
      Task CRUD-BACKEND.md`, `PATCH /reorder` и `LEARNING.md`)
   3. Зарегистрирован **до** `PATCH /:id` — та же причина, что у задач
      (иначе `"reorder"` был бы принят за `:id`)
   4. Вернуть `200` с JSON-массивом `{ id, updatedAt }[]` — по одной паре
      на каждую переставленную строку. Не `204` без тела: Prisma's
      `@updatedAt` обновляет `'updatedAt'` у любой изменённой строки, даже
      когда меняется только `'order'` — если не вернуть клиенту свежие
      значения, следующий точечный `PATCH /:id` по одной из этих же
      категорий уйдёт со старым `'expectedUpdatedAt'` и получит ложный
      `409 "changed elsewhere"` (тот же баг и то же исправление, что у
      `Task`, см. `01.01. Task CRUD-BACKEND.md` и `LEARNING.md`,
      2026-09-19)
   5. На данный момент ни один экран фронтенда этот метод не вызывает —
      реализован для полноты API по образцу `tasks`/`goals`, UI для
      переупорядочивания категорий не существует (см.
      `01.02. Categories-FRONTEND.md`)

4. При получении `PATCH /api/categories/:id` сервер должен:
   1. Провалидировать тело схемой `updateCategorySchema` — ожидается
      `{ patch: {...изменённые поля...}, expectedUpdatedAt: "..." }`,
      иначе `400`
   2. Атомарно обновить строку **только если** её текущий `'updatedAt'`
      в базе совпадает с присланным `'expectedUpdatedAt'` и `'userId'`
      совпадает с `req.userId`
      (`updateMany({ where: { id, userId, updatedAt: expectedUpdatedAt } })`) —
      тот же паттерн конфликт-детекции, что у задач
   3. Если ни одна строка не подошла — `404`, если записи (своей для
      этого пользователя) нет вовсе, или `409` с `{ error, current }`,
      если `'updatedAt'` не совпал
   4. Если обновление прошло — вернуть актуальную запись с кодом `200`
   5. На данный момент фронтенд этот метод не вызывает — нет UI для
      переименования категории. Переименование категории **не**
      затрагивает `'category'` у уже созданных задач (см. "Известные
      ограничения" — в отличие от удаления, см. п. 5 ниже)

5. При получении `DELETE /api/categories/:id` сервер должен:
   1. Найти запись с этим `'id'`, принадлежащую `req.userId`
      (`findFirst({ where: { id, userId } })`)
   2. Если своей записи с таким `'id'` не было — вернуть `404` с
      `{ error: "Category not found" }`
   3. Если найдена — одной транзакцией: удалить **все** задачи этого же
      пользователя, у которых `'category'` равно имени удаляемой
      категории (`task.deleteMany({ where: { userId, category:
      category.name } })`), затем удалить саму категорию
      (`server/src/routes/categories.ts:133-150`). Одной транзакцией — чтобы
      сбой на полпути не мог оставить категорию удалённой, а её задачи
      висящими, или наоборот
   4. Вернуть `204` без тела
   5. Вызывается из UI — кнопка "×" на вкладке-фильтре категории на
      странице Tasks, после подтверждения в диалоге (см.
      `01.02. Categories-FRONTEND.md`)

# Известные ограничения

1. `Task.category` — обычная строка, **не** внешний ключ на
   `Category.id`/`Category.name`. Это осознанный выбор, чтобы не делать
   миграцию данных по существующим задачам при введении сущности
   `Category`. Следствие:
   1. Переименование категории (`PATCH /:id`, хоть и без UI на сегодня)
      не обновит `'category'` у уже созданных задач — они останутся со
      старым именем как со свободной строкой, никак не привязанной к
      реальной категории
   2. Удаление категории (`DELETE /:id`), наоборот, **каскадно удаляет**
      все задачи с совпадающим именем категории (см. "Методы", п. 5.3) —
      сравнение идёт по строке `'category'`, а не по внешнему ключу,
      поэтому это явный `deleteMany` по имени в коде роута, а не
      поведение уровня БД (`onDelete: Cascade` тут не задействован)
2. Как и у задач, нет проверки согласованности бизнес-логики сверх
   `zod` (например, ограничения на длину `'name'` нет)
