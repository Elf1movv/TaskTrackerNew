# 01.01. Task CRUD [Frontend]

# Описание

Создание, редактирование, удаление и переключение статуса выполнения
задачи. Форма используется в двух режимах — добавление новой задачи и
редактирование существующей — одним и тем же компонентом.

# Где находится (файлы)

- `src/features/task-form/ui/TaskForm.tsx` — сама форма (add + edit режим)
- `src/entities/task/model/task.ts` — тип `Task`, `Priority`,
  `TASK_CATEGORIES`
- `src/entities/task/model/TaskProvider.tsx` — `addTask`, `updateTask`,
  `deleteTask`
- `src/widgets/task-board/ui/TaskBoard.tsx` — список задач + точки входа в
  форму (Tasks-страница)
- `src/widgets/today-tasks-card/ui/TodayTasksCard.tsx` — тот же CRUD,
  используется на странице Today
- `src/shared/lib/storage/usePersistedCollection.ts` — оптимистичные
  обновления, откат при ошибке, реакция на `409` (общий механизм для
  задач/целей/привычек)

# Функциональные требования

1. Форма `TaskForm` должна принимать необязательный проп `'task'`:
   1. Если `'task'` передан → форма работает в режиме редактирования,
      поля предзаполняются его значениями, кнопка сохранения вызывает
      `updateTask`
   2. Если `'task'` не передан → форма работает в режиме добавления,
      кнопка вызывает `addTask` с `'completed' = false`
2. Поле `'title'`:
   1. Обязательное — сохранение не должно происходить, если `'title'`
      после `.trim()` пустой
   2. Enter в поле title должен сохранять форму так же, как клик по кнопке
3. Поле `'priority'`:
   1. Один из `"low" | "medium" | "high"`
   2. По умолчанию для новой задачи — `"medium"`
   3. Отображается тремя кнопками-переключателями, у каждой свой цвет
      (см. `PRIORITY_COLORS` в `entities/task/model/task.ts`)
4. Поле `'category'`:
   1. Список допустимых значений — `TASK_CATEGORIES` (`Work`, `Personal`,
      `Health`, `Learning`)
   2. Если форма открыта через проп `'lockedCategory'` (например, при
      добавлении задачи из вкладки конкретной категории на Tasks-странице)
      и это **режим добавления** — пикер категории скрывается, вместо
      него показывается зафиксированная категория бейджем, задача
      сохраняется сразу с `'category' = lockedCategory`
   3. В режиме редактирования пикер категории показывается всегда,
      независимо от `'lockedCategory'`
   4. На вкладке "All" `'lockedCategory'` не передаётся → пикер доступен
      всегда
5. Поле `'dueDate'`:
   1. По умолчанию для новой задачи — сегодняшняя дата
      (`getTodayKey()`), если не передан проп `'defaultDueDate'`
      (используется при добавлении задачи из конкретного дня в Calendar)
   2. Может быть очищено → сохраняется как `null`
6. Удаление задачи (`deleteTask`) — без подтверждающего диалога.
   Изменение применяется на экране сразу (оптимистично), а не после
   ответа сервера
7. Переключение `'completed'` — отдельным контролом (чекбокс/клик по
   строке), не через форму
8. Порядок задач в списке (`'order'`) меняется через drag-and-drop —
   см. `docs/ARCHITECTURE.md`, раздел про нестабильные callback ref
   (частый источник регрессий именно в этом месте)
9. Каждая задача несёт `'updatedAt'` — используется для обнаружения
   конфликтов при одновременном редактировании (см.
   `01.01. Task CRUD-BACKEND.md`). Все действия (`addTask`/`updateTask`/
   `deleteTask`/переупорядочивание) — **оптимистичные**: изменение сразу
   видно на экране, реальный запрос уходит в фоне
   1. Если запрос завершился успехом — локальная запись подменяется
      версией с сервера (актуальный `'updatedAt'`)
   2. Если запрос завершился сетевой/серверной ошибкой — изменение
      откатывается на экране, показывается `toast.error` с понятным
      текстом
   3. Если сервер ответил `409` (кто-то другой уже изменил эту же
      задачу) — локальная версия **не откатывается назад**, а
      заменяется той версией, что реально сейчас в базе, плюс
      отдельный `toast` с текстом о том, что задача была изменена в
      другом месте
