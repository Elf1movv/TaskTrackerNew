# 01.01. Task CRUD [Frontend]

# Описание

Создание, редактирование, удаление и переключение статуса выполнения
задачи. Форма используется в двух режимах — добавление новой задачи и
редактирование существующей — одним и тем же компонентом. Также здесь
описаны правила видимости и пагинации задач на странице Tasks, потому
что они напрямую завязаны на `'completed'`/`'completedAt'`/`'dueDate'`.

# Функциональные требования

1. Форма `TaskForm` должна принимать необязательный проп `'task'`:
   1. Если `'task'` передан → форма работает в режиме редактирования,
      поля предзаполняются его значениями, кнопка сохранения вызывает
      `updateTask`
   2. Если `'task'` не передан → форма работает в режиме добавления,
      кнопка вызывает `addTask` с `'completed' = false`
2. Поле `'title'`:
   1. Обязательное — сохранение не должно происходить, если `'title'`
      после `.trim()` пустой
   2. Enter в поле title должен сохранять форму так же, как клик по кнопке
3. Поле `'priority'`:
   1. Один из `"low" | "medium" | "high"`
   2. По умолчанию для новой задачи — `"medium"`
   3. Отображается одной кнопкой-переключателем (не тремя раздельными) —
      тот же паттерн "кнопка со своим текущим значением внутри", что у
      `src/shared/ui/language-toggle.tsx`/`theme-toggle.tsx`. Клик по
      кнопке циклически меняет значение: низкий → средний → высокий →
      снова низкий (`nextPriority`, `src/features/task-form/ui/TaskForm.tsx:20-22`).
      Текст и цвет кнопки — цвет и подпись текущего значения приоритета
      (см. `PRIORITY_COLORS` в `entities/task/model/task.ts`)
   4. Вне формы приоритет виден в списках задач как иконка (`PriorityDot`,
      `src/entities/task/ui/PriorityDot.tsx`), не сплошной цветной кружок
      — сама форма фигуры дополнительно намекает на уровень, а не только
      цвет: `"low"` → шеврон вниз (`ChevronDown`), `"medium"` → знак
      "равно" (`Equal`), `"high"` → двойной шеврон вверх (`ChevronsUp`,
      lucide-react), цвет каждой — тот же `PRIORITY_COLORS`. Дефолтный
      размер — `14`px (проп `'size'`, необязательный; до 2026-09-22 у
      компонента был плоский кружок размером `6`px — при таком маленьком
      размере кружок читался слабо, тонкая иконка при том же размере
      читалась ещё хуже, поэтому дефолт увеличен вместе со сменой формы).
      Показывается в: `TaskRow.tsx` (страница Tasks), `DayTaskRow.tsx`
      (панель дня Calendar), `CalendarDayCell.tsx` (точки в сетке месяца,
      размер увеличен отдельно с `4` до `10`px — см. `04.02. Month
      View-FRONTEND.md`, п. 3) и `TodayTaskRow.tsx` (карточка
      сегодняшних задач на Today, между заголовком задачи и бейджем
      категории, с тем же `Tooltip`-паттерном, что и в `TaskRow.tsx` —
      наведение показывает `task.priority` текстом). До 2026-09-22
      `TodayTaskRow` вообще не показывала приоритет задачи ни в каком
      виде — не сознательное решение, а пробел, найденный и закрытый
      попутно с заменой кружков на иконки во всех остальных местах
4. Поле `'category'`:
   1. Список допустимых значений — реальные категории из
      `useCategories()` (сущность `Category`, backend-persisted, см.
      [01.02. Categories-FRONTEND](./01.02.%20Categories-FRONTEND.md)), а
      не хардкод. По умолчанию для новой задачи (без `'lockedCategory'`)
      — первая категория из списка
   2. Пикер категории — обычный выпадающий `Select` только для выбора из
      уже существующих категорий. Создать новую категорию прямо из формы
      задачи нельзя — эта возможность убрана из `TaskForm`; добавление
      категории теперь отдельной кнопкой "+ Добавить категорию" на
      странице Tasks (см.
      [01.02. Categories-FRONTEND](./01.02.%20Categories-FRONTEND.md))
   3. Если форма открыта через проп `'lockedCategory'` (например, при
      добавлении задачи из вкладки конкретной категории на Tasks-странице)
      и это **режим добавления** — пикер категории скрывается, вместо
      него показывается зафиксированная категория бейджем, задача
      сохраняется сразу с `'category' = lockedCategory`
   4. В режиме редактирования пикер категории показывается всегда,
      независимо от `'lockedCategory'`
   5. На вкладке "All" `'lockedCategory'` не передаётся → пикер доступен
      всегда
5. Поле `'dueDate'` — необязательное, управляется единым полем
   `DateTimeField` (`src/shared/ui/date-time-field.tsx`). До 2026-09-24
   (ещё одной, более поздней правкой того же дня, уже после того как у
   задачи появились `'time'`/`'endTime'`) было отдельной
   кнопкой-тумблером "Без срока"/"Со сроком" + отдельный `DatePicker` +
   отдельный тумблер "Есть время" + два `Select` + подпись "Конец" + ещё
   один тумблер + ещё два `Select`, все время видимые прямо в форме —
   прямая обратная связь, что это "выглядит плохо, слишком много кнопок".
   Теперь — одна компактная кнопка: пока
   `'hasDueDate'` выключен, показывает плейсхолдер (`taskForm.noDueDate`,
   "Без срока"); когда включён — вычисленную сводку (например, "24 сент,
   19:15–19:45", дата плюс время начала-конца, если они заданы). Клик
   открывает один `Popover` с календарём и, у `TaskForm` — двумя
   `TimePicker` внутри
   1. `'hasDueDate'` по умолчанию **выключен** для новой задачи — новая
      задача больше не получает сегодняшнюю дату автоматически
   2. `'hasDueDate'` включён по умолчанию только если форма открыта в
      режиме редактирования задачи, у которой уже есть `'dueDate'`. Проп
      `'defaultDueDate'` (используется при добавлении задачи из
      конкретного дня в Calendar — см. `04.02. Month
      View-FRONTEND.md`, п. 9.1) сам по себе `'hasDueDate'` **не**
      включает — он только подставляет значение поля даты на случай,
      если пользователь сам выберет дату в попапе; если оставить дату
      непроставленной и сохранить, задача уйдёт без `'dueDate'`, несмотря
      на переданный `'defaultDueDate'`
   3. Отдельного видимого тумблера "Со сроком"/"Без срока" в разметке
      больше нет — `'hasDueDate'` управляется неявно, через сам
      `DateTimeField`: выбор дня в календаре попапа включает его
      (`onDateChange(d)` с ненулевым `d` → `setHasDueDate(true)`), клик по
      "×" на кнопке (видна только когда дата уже выбрана и передан
      `clearable` — по умолчанию `true`, `date-time-field.tsx:84-104`)
      выключает его и сбрасывает дату в `null`. Пока `'hasDueDate'`
      выключен, ни календарь, ни `TimePicker`-ы не видны вовсе — они
      появляются только после того, как поле показывает выбранную дату
   4. Выбор дня в календаре при пустом значении сразу подставляет
      выбранный день — отдельного шага "включить тумблер → подставится
      сегодняшняя дата" больше нет, день выбирается сразу тем кликом,
      которым открывается и используется попап
   5. При сохранении: `'hasDueDate' = false` → `'dueDate'` отправляется
      как `null`; `'hasDueDate' = true` → отправляется выбранная дата.
      Бэкенд не менялся для этой фичи — `'dueDate'` в БД и в zod-схеме
      уже был `nullable()` (см. `01.01. Task CRUD-BACKEND.md`)
   6. Сам виджет выбора даты внутри попапа — переиспользуемый `Calendar`
      (shadcn/react-day-picker, `mode="single"`), тот же компонент,
      которым раньше изнутри пользовался удалённый `DatePicker` — дата
      выбирается кликом по дню, ввод даты текстом по-прежнему не
      поддерживается. `src/shared/ui/date-picker.tsx` (старая обёртка
      Popover + Calendar) удалён полностью 2026-09-24 — после миграции
      всех трёх форм (задача/напоминание/цель) на `DateTimeField` у него
      не осталось ни одного импортёра
   7. В списке задач (`TaskRow`/`DayTaskRow`) строка даты под заголовком
      не отображается вовсе, если у задачи `'dueDate' === null` — не
      показывается никакого плейсхолдера вроде "No due date"
   8. С 2026-09-24 задача может дополнительно нести `'time'` — строка
      `"HH:mm"` (24-часовой формат), тот же паттерн, что у `Reminder.time`
      (см. `13.02. Reminder Entity-BACKEND.md`). Управляется через
      `TimePicker` (`src/shared/ui/time-picker.tsx`, без изменений этим
      раундом — переехал сюда из `features/reminder-form/ui/components`
      ещё в первом раунде того же дня), который `DateTimeField` рендерит
      внутри своего попапа и **только** пока у поля уже выбрана дата
      (`hasTimeField && selected`, `date-time-field.tsx:115`) — задача без
      срока не может нести время дня отдельно от даты
      1. `TimePicker` сам по себе выключен (`value = null`) по умолчанию —
         собственная кнопка-переключатель "Без времени"/"Со временем"
         (`common.noTime`/`common.hasTime`), тот же паттерн "кнопка =
         текущее значение", что у `language-toggle`/`theme-toggle`, без
         изменений этим раундом. Включение подставляет `"09:00"` как
         стартовое значение, дальше час/минуты выбираются двумя `Select`
         (минуты — шагом 5)
      2. При сохранении: очистка даты (клик по "×", `'hasDueDate' =
         false`) всегда очищает и `'time'` (`time: hasDueDate ? time :
         null`, `TaskForm.tsx:93`) — у задачи не может остаться
         "осиротевшее" время без даты
      3. `'time'` используется вне формы календарём — часовая шкала
         Дня/Недели показывает по нему задачу на конкретной высоте, а
         задачи без времени попадают в её строку "весь день" (см.
         `04.04. Day & Week Timeline-FRONTEND.md`)
      4. С 2026-09-24 задача может дополнительно нести `'endTime'` — конец
         временного блока, тот же формат `"HH:mm"` и тот же `TimePicker`,
         что у `'time'`. Поле-подпись "End" (`taskForm.endTime`)
         рендерится внутри того же попапа `DateTimeField`, сразу под
         полем `'time'`, но **только** пока у поля уже выбрано начало
         (`hasEndTimeField && time`, `date-time-field.tsx:118-123`) — блок
         без начала не может иметь конец. У напоминания аналогичного поля
         нет и не планируется — напоминание в этом приложении всегда
         одномоментное "пинг", а не блок времени (см. `13.02. Reminder
         Entity-FRONTEND.md`); `ReminderForm` поэтому вызывает
         `DateTimeField` вообще без пропов `'endTime'`/`'onEndTimeChange'`
         — именно их **отсутствие**, а не значение `null`, и есть сигнал
         "этому полю конец не нужен" (`hasEndTimeField = onEndTimeChange
         !== undefined`, `date-time-field.tsx:54`)
         1. При сохранении: снятие даты **или** очистка `'time'` очищает
            и `'endTime'` (`endTime: hasDueDate && time ? endTime : null`,
            `TaskForm.tsx:94`) — то же правило "очистка якоря очищает то,
            что от него зависит", что уже применяется к самому `'time'`
            (п. 5.8.2)
         2. `'endTime'` используется вне формы часовой шкалой Дня/Недели —
            определяет переменную высоту блока задачи и служит целью
            ручки изменения размера (см. `04.04. Day & Week
            Timeline-FRONTEND.md`, пп. 4, 6)
6. Удаление задачи (`deleteTask`) — без подтверждающего диалога.
   Изменение применяется на экране сразу (оптимистично), а не после
   ответа сервера
7. Переключение `'completed'` — отдельным контролом (чекбокс/клик по
   строке), не через форму (`toggleTask`, `entities/task/model/
   TaskProvider.tsx:18-26`):
   1. При переключении в `true` — `'completedAt'` выставляется в
      `new Date().toISOString()` (текущий момент на клиенте)
   2. При переключении обратно в `false` — `'completedAt'` сбрасывается в
      `null`
   3. `'completedAt'` осознанно не выводится из `'updatedAt'` —
      `'updatedAt'` меняется при любом редактировании (например, при
      переименовании задачи спустя недели после выполнения), что исказило
      бы "день, когда задача была выполнена"; `'completedAt'` хранит
      именно этот момент отдельно
   4. `'completedAt'` используется двумя другими фичами — видимостью на
      странице Tasks (`isCompletedToday`, п. 11 ниже) и размещением
      бездатных задач в Calendar (`isTaskOnDay`, см.
      `04.02. Month View-FRONTEND.md`, п. 5)
8. Новая задача (`addTask`) добавляется **в конец** списка, не в начало
   — `'order'` на сервере выставляется как текущий максимум плюс 1 (см.
   `01.01. Task CRUD-BACKEND.md`, `POST`). До 2026-09-21 было наоборот
   (новая задача становилась первой); правило то же и у целей, и у
   привычек — см. `02.01. Goal CRUD-BACKEND.md`, `03.01. Habit
   CRUD-BACKEND.md`
9. Порядок задач в списке (`'order'`) дальше меняется через
   drag-and-drop:
   1. Нестабильные callback ref — см. `docs/ARCHITECTURE.md`, раздел про
      нестабильные callback ref (частый источник регрессий именно в этом
      месте)
   2. `useDragReorder`'s `hover` (react-dnd) срабатывает на каждый тик
      движения курсора над целью, а не один раз при реальном попадании —
      `lastMovedIdRef` в `useDragReorder.ts:47-56` запоминает, что этот
      перетаскиваемый элемент уже был передвинут к этой цели, и
      игнорирует повторы того же перемещения; без этого секунда наведения
      на одну цель порождала десятки одинаковых вызовов `onHoverMove`
      (и, ниже по цепочке, десятки одинаковых сетевых запросов)
   3. `usePersistedCollection.reorder()` выстраивает вызовы в очередь
      по одной за раз (`pendingReorder`, `usePersistedCollection.ts:135-160`)
      — один жест перетаскивания может вызвать `reorder()` больше одного
      раза (проход через несколько целей подряд), и без очереди каждый
      вызов уходил отдельным параллельным запросом с полным списком,
      из-за чего перекрывающиеся транзакции `PATCH /reorder` на бэкенде
      могли задедлочиться и вернуть сырой `500` (реальный баг, найден и
      исправлен 2026-09-21, см. `LEARNING.md` и `01.01. Task
      CRUD-BACKEND.md`, `PATCH /reorder`). Оптимистичное обновление на
      экране всё равно применяется сразу на каждый вызов — сериализуются
      только сетевые запросы, не сам визуальный отклик перетаскивания
   4. Тот же механизм (`useDragReorder` + `usePersistedCollection.reorder()`)
      используется для целей, привычек и категорий — не переописывается
      отдельно в их доках
10. Каждая задача несёт `'updatedAt'` — используется для обнаружения
   конфликтов при одновременном редактировании (см.
   `01.01. Task CRUD-BACKEND.md`). Все действия (`addTask`/`updateTask`/
   `deleteTask`/переупорядочивание) — **оптимистичные**: изменение сразу
   видно на экране, реальный запрос уходит в фоне
   1. Если запрос завершился успехом — локальная запись подменяется
      версией с сервера (актуальный `'updatedAt'`)
   2. Если запрос завершился сетевой/серверной ошибкой — изменение
      откатывается на экране, показывается `toast.error` с понятным
      текстом
   3. Если сервер ответил `409` (кто-то другой уже изменил эту же
      задачу) — локальная версия **не откатывается назад**, а
      заменяется той версией, что реально сейчас в базе, плюс
      отдельный `toast` с текстом о том, что задача была изменена в
      другом месте

## Видимость и пагинация на странице Tasks

11. Правило видимости задачи на любой вкладке статуса (`filterTasks`,
    `src/pages/tasks/lib/filterTasks.ts`), в таком порядке:
    1. Если задача выполнена (`'completed' = true`) и **не** выполнена
       сегодня (`isCompletedToday` возвращает `false`, т.е.
       `'completedAt'` не сегодняшнего дня либо `null`) — задача **не
       показывается вообще**, ни на одной вкладке статуса, включая "All"
    2. Иначе — дальше применяется обычный фильтр по вкладке статуса
       (`"active"` скрывает выполненные, `"done"` скрывает невыполненные,
       `"all"` не фильтрует по статусу) и по вкладке категории
    3. Это меняет прежнее поведение: раньше вкладка "All" копила **все**
       когда-либо выполненные задачи; теперь выполненная задача видна на
       странице Tasks только в день, когда она была выполнена
    4. Задача без `'dueDate'`, пока она не выполнена, остаётся видимой
       бессрочно — это правило не изменилось
    5. Задача, скрытая с Tasks по этому правилу, не удаляется — её можно
       найти позже через Calendar (см. `04.02. Month View-FRONTEND.md`,
       `isTaskOnDay`, п. 5)
    6. Заголовок страницы ("N remaining · M done", `TaskBoard.tsx:92-99`)
       — независимый счётчик поверх `allTasks`, не поверх отфильтрованного
       вкладками списка (`filteredTasks`):
       1. `'remaining'` (`N`) = `allTasks.filter(t => !t.completed).length`
          — все невыполненные задачи без учёта даты, как и раньше:
          активная задача учитывается в заголовке независимо от того,
          когда она создана и когда у неё срок
       2. `'done'` (`M`) = `allTasks.filter(t => t.completed &&
          isCompletedToday(t)).length` (`TaskBoard.tsx:98`,
          `isCompletedToday` — `src/entities/task/lib/isCompletedToday.ts`)
          — только задачи, выполненные **сегодня**, то же правило, что
          уже прячет из списка ниже задачи, выполненные не сегодня (см.
          п. 11.1). До 2026-09-23 (второй заход) считалось как
          `allTasks.filter(t => t.completed).length` — абсолютно все
          когда-либо выполненные задачи; число только росло и не
          совпадало со списком под заголовком, который эти же задачи уже
          скрывал по правилу п. 11.1
12. Пагинация выполненных сегодня задач (`TasksProvider`,
    `src/pages/tasks/connectors/TasksProvider.tsx`):
    1. Из отфильтрованного списка невыполненные задачи показываются все
       сразу; выполненные сегодня — показываются по `10` штук
       (`COMPLETED_PAGE_SIZE`)
    2. Кнопка "Load N more" показывается, пока в списке остались ещё не
       показанные выполненные сегодня задачи; `N` — минимум из
       оставшегося количества и `10`
    3. Счётчик показанных выполненных задач сбрасывается на первую
       страницу при смене вкладки статуса **или** категории — иначе
       нажатое "Load more" на одном сочетании фильтров переносилось бы на
       другое и путало пользователя
    4. Невыполненные задачи всегда идут в списке первыми, показанные
       выполненные — за ними (`[...pending, ...visibleCompleted]`)
13. Фильтры статуса и категории на странице Tasks (`TaskBoard.tsx`) — в
    **двух** отдельных визуальных рядах, не в одном: ряд статуса
    (All/Active/Done, `STATUS_LABEL_KEYS`) над рядом категорий (All +
    список категорий + "+ Добавить категорию", см. `01.02.
    Categories-FRONTEND.md`). До 2026-09-21 оба ряда были одним общим
    рядом, где кнопки "All" статуса и "All" категории шли подряд и
    выглядели как случайный дубликат одной и той же кнопки — при том, что
    это два независимых фильтра с разными переводами (`tasks.status.all`
    и `tasks.categoryAll`)
14. Строка задачи в списке — корневой flex-контейнер выровнен по
    **верхнему краю** (`items-start`), не по центру всей строки, во всех
    трёх местах, где рендерится строка задачи:
    `src/widgets/task-board/ui/components/TaskRow.tsx:29` (страница
    Tasks), `src/widgets/today-tasks-card/ui/components/
    TodayTaskRow.tsx:20` (карточка Today) и `src/widgets/
    day-detail-panel/ui/components/DayTaskRow.tsx:16` (панель дня
    Calendar). Из-за этого чекбокс, иконка приоритета (`PriorityDot`) и
    бейдж категории выравниваются по первой строке заголовка задачи, а
    не по геометрическому центру всей строки — до 2026-09-23 контейнер
    был `items-center`, и у задач с названием, перенесённым на 2+ строки,
    все эти элементы визуально съезжали ниже, чем у однострочных задач
    рядом
15. Бейдж категории (`Badge variant="secondary"`, `src/shared/ui/badge.tsx`)
    в строке задачи получил фиксированную ширину `w-20 justify-center
    truncate`, переопределяющую дефолтный `w-fit` самого `Badge`
    (`badge.tsx:8`, переопределение работает через `twMerge` в `cn()`) —
    `TaskRow.tsx:56` (страница Tasks) и `TodayTaskRow.tsx:40` (карточка
    Today, здесь ещё и `shrink-0`). Причина, отдельная от п. 14: иконка
    приоритета (`PriorityDot`, п. 3.4) стоит слева от бейджа категории в
    одном `flex`-ряду; весь этот правый блок (иконка + бейдж + кнопки
    редактирования/удаления) прижат к правому краю строки соседним
    `flex-1` на заголовке задачи — без фиксированной ширины бейдж занимал
    ровно столько места, сколько требовало название категории, и при
    разной длине названия у разных задач весь правый блок целиком
    сдвигался по горизонтали, утаскивая иконку приоритета вместе с
    собой — она оказывалась в разных колонках у разных задач. Теперь
    бейдж всегда одной ширины (длинные кастомные названия категорий
    обрезаются `truncate`), поэтому весь правый блок стабильной ширины и
    иконка приоритета — в одной колонке у всех задач. `DayTaskRow.tsx`
    (панель дня Calendar) не затронут — там нет бейджа категории вообще,
    иконка приоритета там уже была в одной колонке
