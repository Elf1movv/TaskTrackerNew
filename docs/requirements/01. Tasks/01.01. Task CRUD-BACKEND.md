# 01.01. Task CRUD [Backend]

# Где находится (файлы)

- `server/src/routes/tasks.ts` — оба метода
- `server/prisma/schema.prisma` — модель `Task`

# Методы

1. При получении `GET /api/tasks` сервер должен:
   1. Прочитать все строки таблицы `Task`, отсортированные по `'order'`
      по возрастанию
   2. Для каждой строки вернуть клиенту только: `'id'`, `'title'`,
      `'completed'`, `'priority'`, `'category'`, `'dueDate'`
   3. Не отдавать клиенту поля `'order'`, `'createdAt'`, `'updatedAt'`,
      `'userId'` — это поля только для сервера

2. При получении `PUT /api/tasks` сервер должен:
   1. Ожидать в теле массив задач той же формы, что вернул `GET` (см.
      выше)
   2. Если тело — не массив → вернуть `400` с
      `{ "error": "Expected an array of tasks" }`
   3. В одной транзакции:
      1. Удалить все существующие строки `Task` (`deleteMany({})`)
      2. Создать заново все строки из присланного массива
      3. `'order'` каждой строки = индекс элемента в присланном массиве
         (порядок в массиве **является** порядком, отдельного поля
         сортировки в запросе нет)
   4. Вернуть клиенту обратно присланный массив как подтверждение

# Известные ограничения

1. `PUT` заменяет **всю** коллекцию задач целиком, а не только
   изменённые — гранулярных `POST /tasks`, `PATCH /tasks/:id`,
   `DELETE /tasks/:id` не существует. Смотри `docs/ARCHITECTURE.md`,
   раздел "REST API: замена всей коллекции целиком" — там же описано,
   при каких условиях это станет проблемой (параллельное редактирование
   с двух устройств) и что тогда нужно будет менять.
2. Валидация тела запроса в `PUT` — только проверка "это массив".
   Содержимое элементов (`'priority'` — валидное ли значение enum,
   `'title'` — не пустой ли) на сервере не проверяется, только на
   клиенте в форме (см. `01.01. Task CRUD-FRONTEND.md`). Если появится
   второй клиент (не наш фронтенд), это станет дырой.
