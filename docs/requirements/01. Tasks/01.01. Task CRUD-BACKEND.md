# 01.01. Task CRUD [Backend]

# Описание

Задача хранит дело, его выполнение и необязательный срок. Календарное
расписание хранится отдельно в CalendarPlan; создание/изменение срока
не создаёт план. Спецификация ветки product-logic-redesign, до выпуска
на main поведение рабочего сайта остаётся прежним.

# Где находится (файлы)

- `server/src/routes/tasks.ts`
- `server/src/validation/task.ts`
- `server/src/lib/productLogic.ts`
- `server/prisma/schema.prisma`

# Методы и правила

1. Все методы требуют сессию (`401` без неё), ограничены `'userId'`
   текущего пользователя. Чужая запись/связь возвращает `404`.
2. `GET /api/tasks` возвращает свои невыведенные из использования
   записи (`'retiredAt' = null`) по `'order'`. Поля: `'id'`, `'title'`,
   `'description'`, `'priority'`, `'category'`, `'completed'`,
   `'completedAt'`, `'dueDate'`, `'goalId'`, `'legacyPending'`,
   `'createdAt'`, `'updatedAt'` и исторические `'time'`/`'endTime'`.
   `'dueDate'` — `YYYY-MM-DD` либо null; даты-время — ISO-8601.
   `'userId'` и `'order'` клиенту не передаются.
3. `POST /api/tasks`: UUID задаёт клиент; новая запись добавляется в
   конец своего списка. `'goalId'` необязателен, цель должна принадлежать
   тому же владельцу. Новая запись не является legacy. Время работы
   новая форма хранит в плане, исторические поля задачи остаются null.
4. `PATCH /api/tasks/:id` принимает `{ patch, expectedUpdatedAt }`.
   Проверка версии и изменение выполняются в одной транзакции с
   блокировкой связанных операций владельца. Несовпадение версии —
   `409 { error, current }`, отсутствие записи — `404`.
5. При смене `'completed'` на true фиксируется `'completedAt'`
   (переданное клиентом значение или время сервера); при возвращении
   в активные поле очищается. Изменение задачи отражается в её цели
   и всех связанных планах, без копирования задачи.
6. `PATCH /api/tasks/reorder`: массив `{ id, order }`, меняется только
   порядок своих записей. Транзакция упорядочена по id для защиты от
   взаимных блокировок. Ответ `200 { id, updatedAt }[]` обновляет версии
   на клиенте, иначе следующее редактирование получило бы ложный `409`.
7. `GET /api/tasks/:id/deletion-preview` возвращает `'futurePlans'` —
   количество будущих/отложенных связанных планов для подтверждения.
8. `DELETE /api/tasks/:id`: в одной транзакции удаляются будущие и
   отложенные планы, их напоминания и будущие прямые напоминания задачи.
   Прошлые планы сохраняют снимок текста, выполнения и оформления и
   теряют ссылку на удалённую задачу. Успех — `204`, нет задачи — `404`.
9. `POST /api/tasks/:id/clear-future-plans` доступен только выполненной
   задаче. Удаляет будущие/отложенные интервалы и их напоминания,
   сохраняет задачу и прошлую историю. Ответ `204`.
10. Будущее определяется по местным дате/времени из заголовка
    `X-Time-Zone` (UTC, если отсутствует). Уже начавшийся интервал и
    сегодняшний план без времени не считаются будущими.
11. Переход старых записей описан в
    [Calendar Plans](../04.%20Calendar/04.06.%20Calendar%20Plans-BACKEND.md).
    Неразобранные записи не теряются и доступны через `/api/transition`.

# Ограничения

История загружается API целиком; страницы по 10 формируются клиентом.
Исторические поля времени сохранены ради перехода/отката, но больше не
определяют календарь. Категория пока является строкой, не внешним ключом.
