# 01.01. Task CRUD [Backend]

# Где находится (файлы)

- `server/src/routes/tasks.ts` — все методы
- `server/src/validation/task.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Task`

# Методы

1. При получении `GET /api/tasks` сервер должен:
   1. Прочитать все строки таблицы `Task`, отсортированные по `'order'`
      по возрастанию
   2. Для каждой строки вернуть клиенту: `'id'`, `'title'`,
      `'completed'`, `'priority'`, `'category'`, `'dueDate'`,
      `'updatedAt'`
   3. Не отдавать клиенту поля `'order'`, `'createdAt'`, `'userId'` —
      это поля только для сервера
   4. `'dueDate'` хранится в базе как настоящая дата (`@db.Date`), но на
      проводе клиенту всегда отдаётся строкой в формате `"YYYY-MM-DD"` —
      конвертация происходит в `toClientTask`

2. При получении `POST /api/tasks` сервер должен:
   1. Провалидировать тело запроса схемой `createTaskSchema` — если не
      прошло, вернуть `400` с `{ error, details }`
   2. `'dueDate'`, если передан — строго формат `"YYYY-MM-DD"` (regex),
      иначе `400`
   3. Создать новую строку `Task` с `'order'` = текущий минимум среди
      всех задач минус 1 (не максимум плюс 1) — так новая задача
      оказывается **первой** в списке
   4. Вернуть созданную запись с кодом `201`

3. При получении `PATCH /api/tasks/reorder` сервер должен:
   1. Провалидировать тело как массив `{ id, order }`-пар
      (`reorderSchema`) — если не прошло, `400`
   2. Обновить **только** колонку `'order'` для перечисленных строк,
      одной транзакцией — остальные поля этих строк не трогать
   3. Этот эндпоинт зарегистрирован **до** `PATCH /:id` — иначе Express
      принял бы `"reorder"` за значение `:id`
   4. Вернуть `204` без тела

4. При получении `PATCH /api/tasks/:id` сервер должен:
   1. Провалидировать тело схемой `updateTaskSchema` — ожидается
      `{ patch: {...изменённые поля...}, expectedUpdatedAt: "..." }`,
      иначе `400`
   2. Атомарно обновить строку **только если** её текущий `'updatedAt'`
      в базе совпадает с присланным `'expectedUpdatedAt'`
      (`updateMany({ where: { id, updatedAt: expectedUpdatedAt } })`)
   3. Если ни одна строка не подошла под условие — проверить отдельно,
      существует ли запись с таким `'id'`:
      1. Не существует → `404` с `{ error: "Task not found" }`
      2. Существует, но `'updatedAt'` не совпал (кто-то другой уже
         изменил эту задачу) → `409` с `{ error, current: <актуальная
         запись> }` — клиент должен показать актуальную версию, а не
         тихо перезаписать её
   4. Если обновление прошло — вернуть актуальную запись с кодом `200`

5. При получении `DELETE /api/tasks/:id` сервер должен:
   1. Удалить запись с этим `'id'`
   2. Если записи не было — вернуть `404` с
      `{ error: "Task not found" }`
   3. Если удаление прошло — вернуть `204` без тела

# Известные ограничения

1. Валидация полей в `POST`/`PATCH` — через `zod` (`priority` строго
   `"low" | "medium" | "high"`, `title` не пустой, `dueDate` строго
   формат даты), но нет проверки на уровне бизнес-логики сверх этого
   (например, что `'dueDate'` не в прошлом — это осознанно не
   ограничивается)
2. Конфликт-детекция через `'updatedAt'` защищает только от
   одновременного изменения **одной и той же записи** двумя
   устройствами — если одно устройство удаляет задачу, пока другое её
   редактирует, `PATCH` вернёт `404` (запись физически исчезла), а не
   `409` — с точки зрения пользователя это тоже "кто-то другой изменил
   эту задачу", просто через другой код ответа
