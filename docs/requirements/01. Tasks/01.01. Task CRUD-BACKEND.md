# 01.01. Task CRUD [Backend]

Редакция второй итерации, 2026-10-10. Задача имеет собственный срок и выполнение.

1. Все методы требуют сессию и ограничены userId. Без сессии 401, чужой id 404.
2. GET /api/tasks возвращает все свои записи по order; поля title,
   description, category, priority, dueDate, completed, completedAt,
   createdAt, updatedAt и исторические time/endTime (`toClientTask`,
   `server/src/routes/tasks.ts:12-27`). С 2026-11-08 (выпускная уборка)
   скрытых задач нет: колонки `legacyPending`/`retiredAt` удалены
   миграцией `20261108180000_release_cleanup`. Колонки `time`/`endTime`
   намеренно сохранены до следующего выпуска, чтобы при откате на
   production могла работать старая версия кода; интерфейс их не показывает.
3. POST создаёт только задачу и добавляет её в конец. Связи с целью нет:
   с 2026-11-08 колонка `Task.goalId` удалена, и схема валидации
   (`server/src/validation/task.ts:22-43`) поле `goalId` не объявляет.
   zod отбрасывает неизвестные ключи, поэтому устаревший клиент,
   приславший `goalId`, получает 201/200, а значение нигде не сохраняется
   (раньше — 400 и CHECK в БД); см. тест «ignores experimental
   relationship fields from stale clients» в
   `server/src/routes/productLogic.test.ts:109-135`.
4. PATCH принимает patch и expectedUpdatedAt. В транзакции проверяется
   версия: при несовпадении 409 с current. При смене completed сервер
   выставляет completedAt либо очищает при возврате в активные.
5. PATCH /reorder изменяет только порядок своих записей, сортирует
   блокировки по id и возвращает свежие updatedAt.
6. DELETE удаляет только задачу. Нет deletion-preview и clear-future-plans;
   будущие планы, цели, напоминания и заметки не затрагиваются.
7. История загружается полностью; страницы по 10 формируются клиентом.
   Дата на проводе YYYY-MM-DD, timestamps ISO-8601.
8. Старые записи: с 2026-11-08 (выпускная уборка) все существующие задачи
   остаются обычными задачами, ручного разбора нет (`/api/transition`
   удалён, 404). Миграция `20261108180000_release_cleanup` перед этим
   записывает полную копию каждой старой задачи (`legacyPending = true`)
   в таблицу `LegacyTransition` (sourceKey `release:task:<id>`, choice
   `kept-task`) — это невидимый журнал только для ручного восстановления,
   приложение его не читает; задачи с заполненным `retiredAt` (уже
   превращённые старой панелью в заметку/план, только на стенде)
   удаляются. Опубликованные миграции не переписываются. История —
   Calendar Plans-BACKEND.
9. Задача также создаётся переносом заметки: `POST /api/notes/:id/to-task`
   проверяет её тем же `createTaskSchema` и ставит в конец списка, удаляя
   заметку в той же транзакции — см.
   [14.01. Note Entity-BACKEND](../14.%20Notes/14.01.%20Note%20Entity-BACKEND.md), п. 6.
