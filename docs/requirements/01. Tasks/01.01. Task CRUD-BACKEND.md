# 01.01. Task CRUD [Backend]

# Где находится (файлы)

- `server/src/routes/tasks.ts` — все методы
- `server/src/validation/task.ts` — схемы валидации (`zod`)
- `server/prisma/schema.prisma` — модель `Task`
- `server/prisma/migrations/20260924140000_add_task_time/` — миграция,
  добавившая колонку `'time'`
- `server/prisma/migrations/20260924170000_add_task_end_time/` — миграция,
  добавившая колонку `'endTime'`
- `server/src/middleware/requireAuth.ts` — проверка сессии (см.
  [09.01. Account Access-BACKEND](../09.%20Authentication/09.01.%20Account%20Access-BACKEND.md))

# Авторизация и разграничение по пользователю

1. `tasksRouter.use(requireAuth)` — весь роутер требует активную сессию;
   без неё любой метод ниже отвечает `401 { error: "Unauthorized" }`
   раньше, чем разбирается тело запроса
2. `requireAuth` кладёт `id` текущего пользователя в `req.userId` —
   каждый метод ниже фильтрует/проставляет именно это значение, `'userId'`
   от клиента не принимается нигде
3. `GET /` читает только строки, где `'userId' = req.userId`; `POST /`
   всегда создаёт запись с `'userId' = req.userId`
4. `PATCH /reorder`, `PATCH /:id`, `DELETE /:id` используют
   `updateMany`/`deleteMany` с `userId` в том же `WHERE`, что и `'id'` —
   не `update`/`delete` по одному `'id'`, потому что Prisma не позволяет
   `update`/`delete` по условию, не являющемуся уникальным ограничением.
   Следствие: если `'id'` существует, но принадлежит другому
   пользователю, ответ **не отличим** от "такой записи вообще нет"
   (`404`) — никогда `403`, чтобы не подтверждать чужому пользователю
   сам факт существования записи

# Методы

1. При получении `GET /api/tasks` сервер должен:
   1. Прочитать все строки таблицы `Task`, отсортированные по `'order'`
      по возрастанию
   2. Для каждой строки вернуть клиенту: `'id'`, `'title'`,
      `'completed'`, `'priority'`, `'category'`, `'dueDate'`, `'time'`,
      `'endTime'`, `'completedAt'`, `'updatedAt'`, `'createdAt'`
   3. Не отдавать клиенту поле `'order'`/`'userId'` — эти поля только для
      сервера. `'createdAt'` клиенту, в отличие от них, **отдаётся**
      (`toClientTask`, `server/src/routes/tasks.ts:22-44`) — без него
      `selectTodayTasks` на клиенте не может отличить "эта бездатная
      задача создана сегодня" от "создана вчера и просто зависла на
      Today навсегда" (см. `05.01. Today Dashboard-FRONTEND.md`, реальный
      баг, найден и исправлен 2026-09-21)
   4. `'dueDate'` хранится в базе как настоящая дата (`@db.Date`), но на
      проводе клиенту всегда отдаётся строкой в формате `"YYYY-MM-DD"` —
      конвертация происходит в `toClientTask`
   5. `'completedAt'` хранится как `TIMESTAMP` (полная дата-время, в
      отличие от `'dueDate'`) и отдаётся клиенту строкой ISO-8601
      (`.toISOString()`) либо `null`

2. При получении `POST /api/tasks` сервер должен:
   1. Провалидировать тело запроса схемой `createTaskSchema` — если не
      прошло, вернуть `400` с `{ error, details }`
   2. `'id'` — **обязательное** поле тела запроса (UUID), сервер его не
      генерирует сам, хотя в Prisma-схеме у `Task.id` есть
      `@default(uuid())` — это может ввести в заблуждение при чтении
      только схемы. Клиент генерирует `'id'` заранее
      (`crypto.randomUUID()`, `src/shared/lib/id.ts`), чтобы можно было
      сразу оптимистично показать новую задачу на экране, ещё не
      дождавшись ответа сервера
   3. `'dueDate'` — тоже обязательное поле (может быть `null`, но ключ
      должен присутствовать в теле всегда), строго формат
      `"YYYY-MM-DD"`, если не `null` — иначе `400`
   4. `'completedAt'` — тоже обязательное поле тела запроса (может быть
      `null`, но ключ должен присутствовать всегда), тот же паттерн, что
      у `'dueDate'`: если не `null`, строго строка в формате ISO-8601
      datetime (`z.string().datetime()`), иначе `400`. Сервер не
      вычисляет `'completedAt'` сам — клиент присылает готовое значение
      (`new Date().toISOString()` в момент переключения `'completed'` в
      `true`, см. `01.01. Task CRUD-FRONTEND.md`)
   5. `'time'` — обязательное поле тела запроса (ключ должен
      присутствовать всегда, значение может быть `null`); если не `null`,
      строго формат `"HH:mm"` (`z.string().regex(/^\d{2}:\d{2}$/)`),
      иначе `400` — тот же паттерн валидации, что у `Reminder.time` (см.
      `13.02. Reminder Entity-BACKEND.md`). Колонка добавлена миграцией
      `20260924140000_add_task_time` — простое аддитивное nullable-поле,
      без бэкофилла: у уже существующих задач `'time'` остаётся `NULL`,
      пока их не отредактируют
   6. `'endTime'` — тот же паттерн, что у `'time'` (п. 5): обязательное
      поле тела запроса (ключ должен присутствовать всегда, значение
      может быть `null`), если не `null` — строго формат `"HH:mm"`, иначе
      `400`. Колонка добавлена миграцией
      `20260924170000_add_task_end_time` — тоже аддитивное nullable-поле
      без бэкофилла. Сервер не проверяет, что `'endTime'` позже `'time'`
      или что `'time'` вообще не `null`, когда `'endTime'` задан — эта
      согласованность целиком на фронтенде (`TaskForm` всегда шлёт
      `'endTime' = null` вместе с `'time' = null`, см. `01.01. Task
      CRUD-FRONTEND.md`, п. 5.8.4.1; ручка изменения размера на часовой
      шкале Дня технически не может отправить `'endTime'` раньше `'time'`
      — она сама зажимает минимум в 15 минут, см. `04.04. Day & Week
      Timeline-FRONTEND.md`, п. 6)
   7. Создать новую строку `Task` с `'order'` = текущий максимум среди
      **своих же** задач плюс 1 — так новая задача оказывается
      **последней** в списке (`server/src/routes/tasks.ts:58-64`). До
      2026-09-21 было наоборот (минимум минус 1, новая задача первая) —
      изменено вместе с `Goal`/`Habit`, чтобы новая запись не заслоняла
      уже существующие наверху списка; `Category` уже была устроена так
      и не менялась (см. `01.02. Categories-BACKEND.md`)
   8. Вернуть созданную запись с кодом `201`

3. При получении `PATCH /api/tasks/reorder` сервер должен:
   1. Провалидировать тело как массив `{ id, order }`-пар
      (`reorderSchema`) — если не прошло, `400`
   2. Обновить **только** колонку `'order'` для перечисленных строк,
      одной транзакцией — остальные поля этих строк не трогать
   3. Строки транзакции строятся отсортированными по `'id'`
      (`[...parsed.data].sort((a, b) => a.id.localeCompare(b.id))`,
      `server/src/routes/tasks.ts:88-92`) **перед** тем, как передаются в
      `$transaction` — без детерминированного порядка блокировок две
      перекрывающиеся по времени транзакции `PATCH /reorder` (например,
      два быстрых шага одного и того же перетаскивания, каждый из которых
      успел уйти в сеть до завершения предыдущего) могут заблокировать
      друг друга в Postgres крест-накрест, что раньше всплывало как сырой
      `500` без понятного сообщения (реальный баг, найден и исправлен
      2026-09-21, см. `LEARNING.md`). Тот же приём — во всех четырёх
      `PATCH /reorder` (`Task`/`Goal`/`Habit`/`Category`)
   4. Этот эндпоинт зарегистрирован **до** `PATCH /:id` — иначе Express
      принял бы `"reorder"` за значение `:id`
   5. Вернуть `200` с JSON-массивом `{ id, updatedAt }[]` — по одной паре
      на каждую переставленную строку (`db.task.findMany` с `select: {
      id, updatedAt }` сразу после обновления). Не `204` без тела: Prisma's
      `@updatedAt` обновляет `'updatedAt'` у любой изменённой строки, даже
      когда меняется только `'order'` — если не вернуть клиенту свежие
      значения, следующий точечный `PATCH /:id` по одной из этих же задач
      уйдёт со старым `'expectedUpdatedAt'` и получит ложный `409 "changed
      elsewhere"` (реальный баг, найден и исправлен 2026-09-19, подробности
      в `LEARNING.md`)

4. При получении `PATCH /api/tasks/:id` сервер должен:
   1. Провалидировать тело схемой `updateTaskSchema` — ожидается
      `{ patch: {...изменённые поля...}, expectedUpdatedAt: "..." }`,
      иначе `400`
   2. Атомарно обновить строку **только если** её текущий `'updatedAt'`
      в базе совпадает с присланным `'expectedUpdatedAt'`
      (`updateMany({ where: { id, updatedAt: expectedUpdatedAt } })`)
   3. Если ни одна строка не подошла под условие — проверить отдельно,
      существует ли запись с таким `'id'`:
      1. Не существует → `404` с `{ error: "Task not found" }`
      2. Существует, но `'updatedAt'` не совпал (кто-то другой уже
         изменил эту задачу) → `409` с `{ error, current: <актуальная
         запись> }` — клиент должен показать актуальную версию, а не
         тихо перезаписать её
   4. Если обновление прошло — вернуть актуальную запись с кодом `200`

5. При получении `DELETE /api/tasks/:id` сервер должен:
   1. Удалить запись с этим `'id'`
   2. Если записи не было — вернуть `404` с
      `{ error: "Task not found" }`
   3. Если удаление прошло — вернуть `204` без тела

# Известные ограничения

1. Валидация полей в `POST`/`PATCH` — через `zod` (`priority` строго
   `"low" | "medium" | "high"`, `title` не пустой, `dueDate` строго
   формат даты), но нет проверки на уровне бизнес-логики сверх этого
   (например, что `'dueDate'` не в прошлом — это осознанно не
   ограничивается)
2. Конфликт-детекция через `'updatedAt'` защищает только от
   одновременного изменения **одной и той же записи** двумя
   устройствами — если одно устройство удаляет задачу, пока другое её
   редактирует, `PATCH` вернёт `404` (запись физически исчезла), а не
   `409` — с точки зрения пользователя это тоже "кто-то другой изменил
   эту задачу", просто через другой код ответа
3. Сервер не проверяет согласованность `'completed'` и `'completedAt'`
   между собой — можно, например, прислать `PATCH` с `'completed' =
   false` и непустым `'completedAt'`, и он пройдёт валидацию. На эту
   согласованность полагается только фронтенд (`toggleTask` всегда
   выставляет оба поля вместе, см. `01.01. Task CRUD-FRONTEND.md`)
