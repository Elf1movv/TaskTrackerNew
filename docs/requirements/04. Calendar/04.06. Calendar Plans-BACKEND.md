# 04.06. Calendar Plans [Backend]

1. CalendarPlan хранится отдельно от Task. `'taskId'` необязателен;
   при его наличии чтение названия, описания и выполнения использует Task.
2. `GET /api/plans` возвращает записи текущего пользователя.
3. `POST /api/plans` проверяет реальные дату/время, конец позже начала,
   длительность и принадлежность связанной задачи владельцу.
4. У обычного плана обязательна дата; время необязательно. У отложенного
   `'onHold' = true`, дата/время/конец равны null, длительность сохраняется.
5. `PATCH /api/plans/:id` проверяет `'expectedUpdatedAt'` и объединённое
   состояние записи. Несовпадение версии — 409; чужой id — 404.
6. Перенос плана меняет только его расписание, не срок задачи и не другие
   интервалы. Выполнение связанной задачи изменяется через `/api/tasks`.
7. Связанное относительное напоминание пересчитывается после переноса.
   Без времени или при On hold оно получает `'suspended' = true`.
8. `DELETE /api/plans/:id` удаляет только этот план и его напоминания.
9. При удалении задачи будущие и отложенные интервалы удаляются; прошлые
   сохраняют снимок её названия, описания и выполнения, связь снимается.
10. Будущее определяется по локальной дате/времени из `'X-Time-Zone'`.
    Уже начавшийся интервал и план без времени на сегодня относятся к
    истории; отложенный план относится к ещё не состоявшейся работе.
11. Связанные операции сериализованы по владельцу внутри транзакции.
    Даты передаются как YYYY-MM-DD, часы — HH:mm, без UTC-сдвига дня.

# Известные ограничения

Планы не пересекают полночь одним блоком; нужно два отдельных интервала.
Напоминания используют текущую модель локальных календарных часов,
фоновой доставки при закрытом сайте нет.

# Одноразовый переход прежних данных

1. Миграция выставляет `'legacyPending'` только существующим Task.
   `GET /api/transition` возвращает собственные неразобранные задачи
   и цели с прежним JSON подцелей. Баннер доступен на всех страницах.
2. `POST /api/transition/task` принимает `'sourceId'`, `'choice'`
   (`task`, `note`, `plan`), `'expectedUpdatedAt'`.
   task сохраняет задачу и при наличии старой даты создаёт связанный
   план; note переносит текст/описание, старую дату в showFrom,
   выполненную запись в архив; plan создаёт самостоятельный план
   (без старой даты — отложенный).
3. Для note/plan исходная Task получает `'retiredAt'` и перестаёт
   участвовать в общем API. Снимок исходных полей, выбор и resultId
   сохраняются в LegacyTransition с уникальным ключом владельца/источника.
4. Версия/владелец проверяются в общей транзакции. Повтор того же решения
   возвращает прежний результат; другое решение для разобранной записи
   возвращает конфликт. Две одновременные попытки не создают копии.
5. Подцели переводятся через `/api/transition/milestone`, см. Goal CRUD.
   Неразобранные записи доступны до явного выбора, включая исходные даты.
6. Длительность расписанного плана вычисляется из начала/конца на сервере;
   допустимы 1–1439 минут в рамках дня. При снятии расписания сохраняется.
