# 04.06. Calendar Plans [Backend]

Редакция второй итерации, 2026-10-10.

1. CalendarPlan — самостоятельные заголовок, описание, выполнение,
   дата, время и длительность. Создание/изменение плана не меняет Task/Goal.
2. Все /api/plans требуют сессию, GET возвращает только свои записи.
3. POST проверяет реальные дату/время, конец позже начала. Связи с
   задачей нет: с 2026-11-08 (выпускная уборка) колонка
   `CalendarPlan.taskId` удалена, `planFields`
   (`server/src/validation/productLogic.ts:22-34`) поле `taskId` не
   объявляет, и zod его отбрасывает — устаревший клиент получает 201/200,
   значение нигде не сохраняется (до 2026-11-08 — 400 и CHECK в БД); см.
   `server/src/routes/productLogic.test.ts:109-135`. Из формы выбор задачи
   удалён. Поля `priority`/`category` плана намеренно сохранены до
   следующего выпуска, чтобы при откате на production могла работать
   старая версия кода.
4. У обычного плана дата обязательна, время необязательно. У отложенного
   onHold=true, дата/время/конец=null; длительность сохраняется.
5. PATCH принимает expectedUpdatedAt, проверяет объединённое состояние:
   чужой id 404, конфликт 409 с current. Записи сериализованы по владельцу.
6. Перенос/растягивание меняет только выбранный план. Длительность
   вычисляется по началу/концу, 1–1439 минут, не округляется повторно.
7. DELETE удаляет только план. Обычные напоминания живут независимо.
8. Даты YYYY-MM-DD, время HH:mm. План не пересекает полночь одним блоком.

## Старые записи и переход второй итерации

С 2026-11-08 (выпускная уборка, решение владельца) одноразовый ручной
разбор старых записей отменён: `/api/transition` удалён (GET теперь 404),
панель `src/widgets/legacy-transition` удалена, все существующие задачи
остаются обычными задачами. Миграция
`server/prisma/migrations/20261108180000_release_cleanup/migration.sql`:
записывает полную копию каждой старой задачи (`legacyPending = true`) в
`LegacyTransition` (sourceKey `release:task:<id>`, choice `kept-task`,
`ON CONFLICT DO NOTHING`); удаляет задачи с заполненным `retiredAt` (уже
превращённые старой панелью в заметку/план, только на стенде — их
оригиналы уже в журнале); удаляет колонки `Task.goalId`/`legacyPending`/
`retiredAt`, `CalendarPlan.taskId`, `Reminder.taskId`/`planId`/
`offsetMinutes`/`suspended`, `Goal.achievedAt` вместе с их CHECK.
`LegacyTransition` — невидимый журнал только для ручного восстановления,
приложение его не читает. Колонки `Task.time`/`endTime` и
`CalendarPlan.priority`/`category` удаляются в следующем выпуске (чтобы
при откате работал старый код). Ниже — история второй итерации.

1. GET /api/transition возвращает только неразобранные собственные Task.
   Milestones больше не предлагаются для конвертации, endpoint удалён.
2. POST /api/transition/task: sourceId, choice=task|note|plan, expectedUpdatedAt.
   task оставляет только задачу со сроком, время сохраняется в журнале;
   note сохраняет текст/описание/выполнение, не архивирует; у заметок
   нет дат (с 2026-11-08), поэтому прежний срок пишется первой строкой
   описания `Срок: YYYY-MM-DD` (`server/src/routes/transition.ts`, файл
   удалён 2026-11-08);
   plan создаёт только план, без даты — отложенный.
3. Для note/plan исходная Task получает retiredAt, скрывается из активных.
   Полный snapshot, решение и resultId остаются в LegacyTransition.
4. Повтор того же решения возвращает прежний результат, другое решение
   даёт 409. Транзакция и уникальный ключ защищают от дубликатов.
5. Миграция 20261010120000 добавляет Note.completed=false. Перед отвязкой
   экспериментальных Task→Goal/Plan→Task/Reminder сохраняет полные снимки.
   У плана фиксирует видимые значения связанной задачи, сохраняя расписание.
   Задачи остаются общими задачами, цели сохраняют свои milestones.
   Процент целей пересчитывается по milestones, achievedAt очищается.
6. Прежние связанные сигналы сохраняют последнюю дату/время и становятся
   самостоятельными. suspended-сигналы сохраняются выполненными в истории,
   чтобы не сработать с устаревшей датой; оригиналы доступны в журнале.
   На текущем стенде таких сигналов и конвертаций milestones не было.
7. Старые колонки/журнал не удаляются; CHECK запрещает новые связи.
   Перед установкой на стенд обязательна резервная копия. С 2026-11-08
   (выпускная уборка) старые колонки связей и CHECK удалены миграцией
   `20261108180000_release_cleanup`; журнал `LegacyTransition` остаётся.

## Изменения 2026-11-09 (аудит, пачка 4)

У плана нет полей `priority` / `category` (удалены миграцией
`20261109190000_audit_batch4`; с пачки 3 они не показывались). API их не
принимает и не возвращает.
