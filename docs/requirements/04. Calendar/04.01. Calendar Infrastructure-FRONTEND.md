# 04.01. Calendar Infrastructure [Frontend]

# Описание

Общее состояние и навигация календаря, разделяемые всеми пятью видами
(Повестка дня/День/Неделя/Месяц/Год) — переключатель видов, единая точка
"где мы сейчас" (`'anchorDate'`), синхронизация с URL, общая дата-математика
для построения сеток/диапазонов и общие для всех видов действия
(перенос задачи/цели на день, перепланирование задачи по времени). Каждый
конкретный вид (Месяц — `04.02`, Повестка дня — `04.03`, День/Неделя —
`04.04`, Год — `04.05`) строит собственную сетку/диапазон из `'anchorDate'`
самостоятельно — провайдер не решает за виды, какой формы у них сетка.
Своей серверной логики нет — под капотом обычный CRUD задач/целей/
напоминаний/привычек (`01. Tasks`, `02. Goals`, `13. Reminders`,
`03. Habits`).

# Функциональные требования

## Виды и состояние

1. Пять видов календаря (`CalendarView`, `calendarContext.ts:7`):
   `"agenda" | "day" | "week" | "month" | "year"`. До 2026-09-24
   единственным видом был `"month"` — остальные четыре реализованы в
   рамках этой фичи
   1. Вид по умолчанию (`useState<CalendarView>(...)`,
      `CalendarProvider.tsx:17`) — с 2026-09-25 **"День"**, не "Месяц".
      Применяется только при заходе без `?view=` в URL (см. п. 14.1) —
      явный `?view=month` в ссылке по-прежнему открывает Месяц
2. `'anchorDate'` — единственный источник истины "где мы сейчас в
   календаре" (`CalendarProvider.tsx:17`), не отдельная переменная-дата на
   каждый вид (это бы позволяло видам рассинхронизироваться друг с
   другом при переключении). Каждый вид сам строит из него свою
   сетку/диапазон через `shared/lib/calendarGrid.ts` (см. пп. 8-10)
3. `'selectedDay'` осмыслен только для вида "Месяц" (боковая панель дня,
   см. `04.02. Month View-FRONTEND.md`) — у Дня/Недели вместо неё
   собственная часовая шкала как детальный вид, у Повестки дня всё уже
   показано построчно, ни одной из них отдельная панель не нужна
4. `goToPrev`/`goToNext` сдвигают `'anchorDate'` на единицу, зависящую от
   активного вида (`switch (view)`, `CalendarProvider.tsx:28-60`):
   1. `"day"` → на 1 день (`subDays`/`addDays`)
   2. `"week"` → на 1 неделю (`subWeeks`/`addWeeks`)
   3. `"month"` → на 1 месяц (`subMonths`/`addMonths`)
   4. `"year"` → на 1 год (`subYears`/`addYears`)
   5. `"agenda"` → на 30 дней (`subDays`/`addDays` на 30, не изменилось
      2026-09-25) — у Повестки дня нет "календарной единицы", есть
      только сдвиг всего окна целиком. С 2026-09-25 (см. п. 13, `04.03.
      Agenda View-FRONTEND.md`) её видимое окно больше не фиксировано на
      30 дней — этот сдвиг остался жёстко зашитым числом 30 независимо
      от того, сколько дней сейчас реально раскрыто кнопкой "показать
      ещё"; переход "вперёд"/"назад" всегда сбрасывает окно обратно к
      начальным 6 дням от нового `'anchorDate'` (см. `04.03`)
5. `goToToday` одновременно возвращает `'anchorDate'` на сегодня **и**
   выставляет `'selectedDay'` в сегодня (`CalendarProvider.tsx:62-66`) —
   если панель дня (вид "Месяц") была закрыта, она открывается с
   сегодняшним днём; для остальных видов второе присваивание просто не
   используется
6. `goToDate(date)` — прыжок на конкретную дату, используется при клике
   по дню соседнего месяца (Месяц), клике по дню в Годе (переключает ещё
   и вид на "День", см. `04.05. Year View-FRONTEND.md`) и при разборе
   `?date=` из URL (п. 14)
7. Провайдер отдаёт видам:
   1. `allTasks`/`allReminders`/`allGoals`/`allHabits` — полные коллекции,
      без фильтрации по дню (Повестка дня/День/Неделя/Год сами фильтруют
      нужные дни из них)
   2. `selectedTasks`/`selectedReminders`/`selectedGoals`/`selectedHabits`
      — уже отфильтрованные по `'selectedDay'` подмножества, только для
      панели дня вида "Месяц" (`useMemo` над `'selectedDay'`,
      `CalendarProvider.tsx:68-88`) — пустые массивы, пока `'selectedDay'
      = null`
   3. `moveTaskToDay(taskId, day)` — `updateTask(id, { dueDate:
      formatDateKey(day) })`, меняет только `'dueDate'`, используется
      перетаскиванием задачи на день в сетке "Месяца" (`04.02`) —
      Повестка дня недрагабельна (`04.03`). До 2026-09-25 этим же
      действием пользовалась и строка "весь день" Дня/Недели
      (`AllDayRow`) — с удалением этой строки целиком (`04.04`, п. 9.3)
      `moveTaskToDay` там больше не используется вообще, `CalendarPage.tsx`
      перестал передавать его в `CalendarDayView`/`CalendarWeekView`
   4. `moveGoalDeadline(goalId, day)` — тот же паттерн для
      `Goal.targetDate` (`updateGoal(id, { targetDate:
      formatDateKey(day) })`) — новое действие этой фичи, до неё цель
      на календаре не появлялась вообще
   5. `rescheduleTaskTime(taskId, day, time)` — `updateTask(id, { dueDate,
      time, endTime })`, действие для перетаскивания по времени на часовой
      шкале Дня/Недели (`04.04`) — в отличие от `moveTaskToDay`, меняет
      сразу три поля, а не только день. С 2026-09-24 (после появления
      `Task.endTime`, `04.04`, п. 4) дополнительно сдвигает `'endTime'` на
      ту же дельту минут, что и `'time'`, через `addMinutesToTime`
      (`shared/lib/timeOffset.ts`), чтобы длительность блока сохранялась
      при перетаскивании целиком, а не "сплющивалась" к старому
      `'endTime'`, пересчитанному от нового начала; если у задачи `'time'`
      был `null` (перенос из строки "весь день") — `'endTime'` тоже
      обнуляется, то же правило "очистка якоря очищает то, что от него
      зависит", что уже применяет `TaskForm` (`01.01. Task
      CRUD-FRONTEND.md`, п. 5.8.2)
   6. `resizeTask(taskId, endTime)` — `updateTask(id, { endTime })`, новое
      действие этой фичи (2026-09-24) для ручки изменения размера блока
      задачи на часовой шкале — двигает только `'endTime'`, начало не
      трогает (`04.04`, п. 6)

## Переключатель видов и заголовок периода

8. Переключатель — горизонтальный ряд кнопок-пилюль в едином фоне
   (`BUILT_VIEWS.map`, `CalendarPage.tsx:128-140`), визуально тот же
   паттерн, что у переключателя периода истории привычек (`03.02. Habit
   History-FRONTEND.md`). Порядок кнопок — `["agenda", "day", "week",
   "month", "year"]` (`BUILT_VIEWS`, `CalendarPage.tsx:20`), тот же
   порядок вкладок, что в TickTick
9. Заголовок периода (`formatPeriodTitle`, `CalendarPage.tsx:35-56`) —
   свой формат на каждый вид: `"Месяц YYYY"` (Месяц), `"YYYY"` (Год),
   `"День недели, D Месяц YYYY"` (День), диапазон `"D MMM – D MMM YYYY"`
   для начала-конца окна (Повестка дня — от `'anchorDate'` до конца её
   30-дневного окна, Неделя — от понедельника до воскресенья её недели)
10. Кнопка "Сегодня"/"К сегодня" (`isViewingCurrentPeriod`,
    `CalendarPage.tsx:27-33`) — подпись зависит от вида: `"month"`
    сравнивается через `isSameMonth`, `"day"` — `isSameDay`, `"week"` —
    `isSameWeek` (понедельник первый день), `"year"` — сравнение
    `getFullYear()`; для `"agenda"` всегда `true` (у неё нет
    "просматриваемого периода" в этом смысле — сегодня всегда где-то в
    начале её окна, кнопка сдвигает окно назад к текущей дате, а не
    "возвращает" в какой-то конкретный период)

## Общая дата-математика (`shared/lib/calendarGrid.ts`)

11. `buildMonthGrid(month)` — сетка дней месяца, всегда кратна 7,
    понедельник первый день недели (см. подробности в `04.02. Month
    View-FRONTEND.md`, п. 1). До 2026-09-24 жила в
    `widgets/calendar-grid/lib`, перенесена в `shared/lib`, потому что
    вид "Год" (`04.05`, легитимный виджет) не может импортировать её из
    другого виджета `calendar-grid` — межвиджетный импорт запрещён FSD
    (`fsd/forbidden-imports`, error-level правило Steiger в этом
    проекте) — а сама функция чистая дата-математика без зависимости
    от UI/сущностей, то есть по назначению всегда была `shared/lib`
12. `buildWeekRange(anchor)` — ровно 7 дней недели `'anchor'`,
    понедельник первый (`startOfWeek(anchor, { weekStartsOn: 1 })`), без
    ведущих/хвостовых дней — в отличие от `buildMonthGrid`, неделе не
    нужно дополнение до кратности 7, она и так всегда 7 дней
13. `buildAgendaRange(anchor, days = 30)` — окно из `'days'` дней вперёд
    от `'anchor'`, **не** бесконечная прокрутка — осознанное решение:
    бесконечная прокрутка потребовала бы intersection observer'ов,
    инкрементального расширения диапазона и сохранения позиции скролла
    при рефетче — непропорционально сложно для персонального
    однопользовательского трекера такого масштаба
    (`shared/lib/calendarGrid.ts:46-48`). Параметр по умолчанию (`= 30`)
    с 2026-09-25 больше не отражает реальное поведение Повестки дня —
    `CalendarAgendaView` всегда передаёт `'days'` явно, начиная с `6` и
    растя на `6` за клик "показать ещё" (см. `04.03. Agenda
    View-FRONTEND.md`); значение по умолчанию в сигнатуре осталось
    просто неиспользуемым фолбэком, не единственным вызывающим кодом

## Синхронизация с URL

14. `CalendarPage.tsx` держит вид и `'anchorDate'` синхронизированными с
    query-параметрами `?view=X&date=Y` через два независимых `useEffect`:
    1. Одноразовая реконциляция при монтировании (`hasConsumedInitialParams`,
       `CalendarPage.tsx:92-106`, пустой массив зависимостей намеренно) —
       разбирает `?view=`/`?date=`, с которыми страница была открыта:
       либо внешний deep link (клик по напоминанию на Today/`ReminderBell`/
       критичном поп-апе присылает только `?date=`, без `?view=`, что при
       дефолтном состоянии провайдера равносильно "открыть этот день на
       виде по умолчанию" — до 2026-09-25 это было "Месяц", теперь "День",
       см. п. 1.1 — оба раза именно вид по умолчанию, не что-то специально
       посчитанное для этого deep link'а), либо ранее сохранённая/
       расшаренная ссылка на календарь (`?view=week&date=...`).
       Срабатывает **только один раз** — повторный запуск при каждом
       изменении параметров боролся бы со вторым эффектом (п. 14.2),
       который эти же параметры и пишет
    2. Непрерывное отражение `['view', 'anchorDate']` обратно в URL
       (`CalendarPage.tsx:112-119`) — `replace: true`, не `push`, чтобы
       клики по "вперёд"/"назад" не забивали историю браузера десятками
       записей. `'selectedDay'` в URL не попадает — это внутреннее
       состояние панели дня вида "Месяц", а не "где я нахожусь в
       календаре"

## Layering (FSD) — где физически живут виды

15. Месяц/Повестка дня/День/Неделя — компоненты **уровня страницы**
    (`src/pages/calendar/ui/Calendar{Month,Agenda,Day,Week}View.tsx`), не
    виджеты — каждый из них компонует несколько виджетов-соседей
    (`calendar-grid` + `day-detail-panel` у Месяца, `calendar-timeline` +
    `calendar-item-popover` у Дня, `calendar-timeline` + формы напрямую у
    Недели, см. `04.04`), а межвиджетные импорты запрещены FSD в этом
    проекте (`fsd/forbidden-imports`, error-level). Это повторяет уже
    существующий прецедент — `GoalReminderSwapCard` на странице Today.
    Виджетами остались только `calendar-grid`, `day-detail-panel`,
    `calendar-timeline`, `calendar-year` и (с 2026-09-24)
    `calendar-item-popover` — ни один из них не зависит от
    виджета-соседа, только от `shared/lib` и селекторов сущностей

## Оболочка страницы

16. С 2026-09-24 внешний контейнер `CalendarPage.tsx` — `p-4 md:p-6`, без
    ограничения максимальной ширины (раньше `p-6 md:p-10 max-w-5xl
    mx-auto`, `CalendarPage.tsx:131`) — общий для всех пяти видов, потому
    что переключатель/заголовок периода/тело вида рендерятся внутри одного
    и того же `<div>`. Это расширение затронуло область, доступную всем
    видам, но собственную вёрстку под неё в эту же дату перестроил только
    "День" (`04.04`) — он теперь единственный, кто реально растягивается
    на всю ширину; "Повестка дня" сохраняет собственную внутреннюю обёртку
    `max-w-2xl mx-auto` (`CalendarAgendaView.tsx:70`), "Месяц"/"Неделя"/
    "Год" визуально ограничены собственной сеткой колонок, а не отдельным
    `max-w-*`-контейнером, поэтому их вёрстка не менялась
