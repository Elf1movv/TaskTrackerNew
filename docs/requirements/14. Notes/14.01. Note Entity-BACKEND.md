# 14.01. Note Entity [Backend]

Редакция третьей итерации, 2026-11-08 (тестовый стенд): заметки без дат.

# Где находится (файлы)

- `server/src/routes/notes.ts` — все методы
- `server/src/validation/productLogic.ts` — `noteFields`/`patchNote`
- `server/prisma/schema.prisma` — модель `Note`
- `server/prisma/migrations/20261108120000_simplify_notes_goal_category/` —
  удаление колонки `'showFrom'`

# Методы

1. Все `/api/notes` требуют сессию (`requireAuth`, без неё `401`);
   `'userId'` берётся из неё.
2. `GET /api/notes` возвращает только записи владельца по `'order'`.
   `'userId'` клиенту не отдаётся.
3. `POST /api/notes` проверяет UUID, непустое название до 500 символов,
   `'completed'` (boolean, по умолчанию false), описание до 50000 символов
   или null и `'archivedAt'` или null. Запись добавляется в конец списка.
   Поля даты у заметки нет: колонка `'showFrom'` удалена миграцией
   `20261108120000`.
4. `PATCH /api/notes/:id` принимает `'patch'` и `'expectedUpdatedAt'`.
   Чужая запись — 404, несовпавшая версия — 409 с `'current'`.
5. `PATCH /api/notes/reorder` меняет только порядок; блокировки берутся
   по отсортированным id, клиент получает новые версии.
6. При получении `POST /api/notes/:id/to-task` сервер должен
   (`server/src/routes/notes.ts:78-98`):
   1. Проверить тело `{ expectedUpdatedAt, task }`:
      1. `'expectedUpdatedAt'` — строка ISO datetime
      2. `'task'` — полная задача по `createTaskSchema`
         (`server/src/validation/task.ts`, те же правила, что у
         `POST /api/tasks`)
      3. Иначе — `400 { error: "Invalid move to task" }`
   2. В одной транзакции владельца (`ownerTransaction`, advisory lock по
      `'userId'`):
      1. Найти заметку по `'id'` и `'userId'`; нет своей — `404`
         `"Note not found"`
      2. Если `'updatedAt'` заметки не совпадает с `'expectedUpdatedAt'` —
         `409` `"Note changed elsewhere"` (без `'current'`, в отличие от
         `PATCH`)
      3. Создать задачу с `'userId' = req.userId` и `'order'` = максимум
         задач владельца + 1 (в конец списка)
      4. Удалить заметку
   3. Вернуть созданную задачу (`toClientTask`) с кодом `201`
   4. При любой ошибке транзакция откатывается: не остаётся ни дубликата
      (задача + заметка), ни потери (ни того, ни другого)
7. `DELETE /api/notes/:id` ограничен владельцем; доступен из актуальных
   и архива с подтверждением. Архив — отдельное обратимое действие.
8. `'completed'` не меняет `'archivedAt'`. Выполнение/отмена сохраняются
   после перезагрузки, редактирование текста не сбрасывает галочку.
9. Ручной порядок един для коллекции; фильтрация вкладки не сортирует
   записи заново. Перестановка передаёт всю коллекцию, не теряет
   скрытые вкладками записи.
10. Перевод старой записи в заметку (`POST /api/transition/task`,
    `'choice' = "note"`) сохраняет прежний срок текстом: если у исходной
    задачи был `'dueDate'`, описание заметки начинается строкой
    `Срок: YYYY-MM-DD`, затем через перевод строки — прежнее описание
    (`server/src/routes/transition.ts:53-55`). См.
    [04.06. Calendar Plans-BACKEND](../04.%20Calendar/04.06.%20Calendar%20Plans-BACKEND.md).

# Известные ограничения

1. Отдельного раздела Notes в боковом меню нет — заметки живут на Today
   (см. [05.01. Today Dashboard-FRONTEND](../05.%20Today/05.01.%20Today%20Dashboard-FRONTEND.md)).
2. Обратного перевода задачи в заметку нет; `to-task` — одностороннее
   действие.
3. Колонка `'showFrom'` удалена без переноса значений в текст: таблица
   `Note` существовала только на тестовом стенде (комментарий миграции
   `20261108120000`).
