# Roadmap — известные слабые места и план улучшений

Это рабочий список: что не так в текущей архитектуре, почему это важно,
и что с этим сделать. В отличие от `docs/ARCHITECTURE.md` (описывает
текущее состояние и объясняет уже принятые решения) — этот файл смотрит
вперёд: что ещё предстоит сделать, чтобы приложение по-настоящему
надёжно масштабировалось на несколько активных устройств.

Отмечай пункт `[x]`, когда он сделан, и добавляй ссылку на коммит/дату —
чтобы файл оставался источником правды о реальном прогрессе, а не
списком благих намерений.

## 🔴 Критично — напрямую блокирует надёжную синхронизацию между устройствами

Сделано целиком 2026-09-16 (одним заходом, см. `docs/ARCHITECTURE.md`,
раздел "REST API: гранулярный CRUD + защита от конфликтов").

- [x] **Гранулярный REST API** вместо "весь список целиком" —
      `POST`/`PATCH /:id`/`DELETE /:id`/`PATCH /reorder` на каждую
      сущность (`tasks`, `goals`, `habits`). Старые `PUT /` удалены.
- [x] **`updatedAt` возвращать клиенту** — теперь в каждом `toClient*`
      мапере, используется для конфликт-детекции на `PATCH`
- [x] **Обработка ошибок сохранения на фронте** — `usePersistedCollection`
      теперь ловит ошибку, откатывает оптимистичное изменение и
      показывает `toast.error` (проверено вживую — отключение сети даёт
      понятную ошибку, а не тихую потерю данных)
- [x] **Индикация загрузки/ошибки в UI** — `isLoaded` теперь реально
      возвращается из хука; полноценный спиннер/skeleton на месте
      загрузки — опциональная косметика на будущее, не блокер
- [x] **Debounce на сохранение** — решилось архитектурно, не отдельной
      мерой: каждое действие пользователя теперь = один явный
      `create`/`update`/`remove`/`reorder` вызов вместо `useEffect`,
      реагирующего на любое изменение состояния — лишних параллельных
      запросов физически неоткуда взяться

## 🟡 Важно — пока не горит, станет проблемой при росте или публичности

- [x] **Валидация полей на сервере** — `zod`-схемы в
      `server/src/validation/`, проверяют `priority`/`progress`/форму
      каждой сущности при `POST`/`PATCH`, `400` с деталями при ошибке
- [x] **Централизованная обработка ошибок** на Express —
      `server/src/middleware/errorHandler.ts`, единый JSON-формат
- [ ] **`dueDate` → настоящий `DateTime`** в Prisma-схеме (сейчас
      `String?`) — нужно для нормальных SQL-запросов "задачи за
      диапазон дат" (сейчас Calendar фильтрует весь список на клиенте)
- [ ] **Индексы в БД** (как минимум на `dueDate`, `order`) — не имеет
      значения при текущем объёме данных, важно при росте истории
- [ ] **Ограничить CORS**, когда появится авторизация — сейчас открыт
      полностью (`cors()` без настроек), пока не с чем эксплуатировать,
      но нужно вернуться к этому вместе с логином

## 🟢 Косметика / стандарты — не блокирует ничего функционально

- [ ] Правильные HTTP-коды: `201` при создании, `404` при отсутствии
      ресурса, различать `400` (плохой запрос) и `500` (ошибка сервера)
- [ ] Security-заголовки (`helmet`)

## 📋 Логирование — фронтенд и бэкенд

- [x] **Бэкенд**: `morgan` подключен в `server/src/app.ts` (запросы) +
      `errorHandler.ts` логирует необработанные ошибки в консоль —
      видно через `sudo journalctl -u tasktracker -f` на проде
- [x] **Фронтенд**: `console.error` централизован в
      `usePersistedCollection` — там же, где показывается `toast.error`,
      так что любая ошибка сохранения одновременно и видна пользователю,
      и попадает в консоль браузера для отладки. Отправка ошибок во
      внешний сервис мониторинга — не сделано, не нужно на этом масштабе
- [ ] Продумать хранение и ротацию логов на сервере (systemd уже отчасти
      решает это для `journalctl`, но стоит явно ограничить размер)

## 🐳 Docker — контейнеризация и деплой

Цель: собирать приложение в Docker-образ и деплоить его на VPS вместо
текущего "голый `git pull` + `npm install` прямо на сервере" —
_отдельный, самостоятельный этап_, не смешивать с рефакторингом API
выше (слишком много одновременных изменений усложняет отладку, если
что-то сломается).

Сделано 2026-09-16 — приложение в Docker, PostgreSQL сознательно оставлен
нативным (следующий отдельный шаг, см. ниже).

- [x] `Dockerfile` — многоступенчатый, один образ на весь стек (фронтенд
      + бэкенд, Express раздаёт всё сам, как и раньше)
- [x] Решено: **один образ**, не отдельные фронт/бэк-образы — проще,
      меньше движущихся частей для соло-проекта
- [x] `docker-compose.yml` — только приложение; **PostgreSQL оставлен
      нативным на VPS** (осознанно, обсуждено с владельцем) — бэкапы уже
      настроены и проверены против нативной базы, менять деплой-механизм
      и слой данных одновременно — лишний риск
- [x] `.github/workflows/deploy.yml` — образ собирается **в CI**
      (GitHub Actions), пушится в GHCR; VPS только `docker compose pull`
      + `up -d`
- [x] На VPS: Docker установлен, старый `tasktracker.service` удалён,
      `docker compose` + `restart: unless-stopped` — переживание
      перезагрузки VPS проверено вживую (`sudo reboot`)
- [x] `docs/DEPLOYMENT.md` обновлён под новый процесс

**Следующий шаг** (не сделано, отдельный заход): контейнеризовать
PostgreSQL тоже — потребует продумать volume для данных, перенести
бэкап-скрипт на контейнер, протестировать миграцию данных из нативной
инсталляции.

**Почему это вообще нужно** (если понадобится вспомнить, зачем): Docker
даёт воспроизводимое окружение — "работает у меня" перестаёт зависеть от
того, что именно установлено на конкретном VPS, и переезд на новый
сервер (см. `PROJECT_BRAIN.md`, раздел 7.2) сводится к "поставь Docker,
подними контейнер" вместо повторения всей ручной установки.
