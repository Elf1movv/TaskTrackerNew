# Roadmap — известные слабые места и план улучшений

Это рабочий список: что не так в текущей архитектуре, почему это важно,
и что с этим сделать. В отличие от `docs/ARCHITECTURE.md` (описывает
текущее состояние и объясняет уже принятые решения) — этот файл смотрит
вперёд: что ещё предстоит сделать, чтобы приложение по-настоящему
надёжно масштабировалось на несколько активных устройств.

Отмечай пункт `[x]`, когда он сделан, и добавляй ссылку на коммит/дату —
чтобы файл оставался источником правды о реальном прогрессе, а не
списком благих намерений.

---

## 🔴 Критично — напрямую блокирует надёжную синхронизацию между устройствами

- [ ] **Гранулярный REST API** вместо "весь список целиком" — заменить
      `PUT /api/tasks` (удалить всё, создать заново) на `POST /api/tasks`
      (создать одну), `PATCH /api/tasks/:id` (изменить одну),
      `DELETE /api/tasks/:id` (удалить одну). То же самое для `goals` и
      `habits`. Без этого два устройства могут тихо затирать изменения
      друг друга (race condition при одновременном редактировании)
- [ ] **`updatedAt` возвращать клиенту** — сейчас сервер намеренно
      вырезает это поле из ответа. Без него невозможно определить "моё
      изменение новее или чужое" — обязательное условие для
      гранулярного API выше, чтобы конфликт не проходил тихо
- [ ] **Обработка ошибок сохранения на фронте** — сейчас `save()`
      ничего не делает при неудаче (нет `.catch()`), изменение просто
      теряется молча. Нужно: показывать пользователю, что сохранение не
      удалось, и/или повторять попытку
- [ ] **Индикация загрузки/ошибки в UI** — `isLoaded` уже вычисляется в
      `usePersistedCollection`, но никем не используется. Нужно
      прокинуть в интерфейс (спиннер при загрузке, сообщение при ошибке)
- [ ] **Debounce на сохранение** — сейчас каждое изменение сразу летит
      отдельным запросом; быстрые последовательные правки создают
      параллельные `PUT`-запросы без гарантии порядка выполнения — тот
      же класс проблемы, что и синхронизация между устройствами, только
      воспроизводится даже в одной вкладке

## 🟡 Важно — пока не горит, станет проблемой при росте или публичности

- [ ] **Валидация полей на сервере** — сейчас проверяется только "это
      массив?"; нет проверки `priority`/`dueDate`/`progress` и т.п. на
      корректность. Станет дырой, если появится второй клиент
- [ ] **Централизованная обработка ошибок** на Express — сейчас при
      ошибке Prisma сервер отдаёт невнятный ответ без единого JSON-формата
- [ ] **`dueDate` → настоящий `DateTime`** в Prisma-схеме (сейчас
      `String?`) — нужно для нормальных SQL-запросов "задачи за
      диапазон дат" (сейчас Calendar фильтрует весь список на клиенте)
- [ ] **Индексы в БД** (как минимум на `dueDate`, `order`) — не имеет
      значения при текущем объёме данных, важно при росте истории
- [ ] **Ограничить CORS**, когда появится авторизация — сейчас открыт
      полностью (`cors()` без настроек), пока не с чем эксплуатировать,
      но нужно вернуться к этому вместе с логином

## 🟢 Косметика / стандарты — не блокирует ничего функционально

- [ ] Правильные HTTP-коды: `201` при создании, `404` при отсутствии
      ресурса, различать `400` (плохой запрос) и `500` (ошибка сервера)
- [ ] Security-заголовки (`helmet`)

## 🧪 Тесты

- [ ] Автотесты на новый гранулярный API (бэкенд) — сейчас во всём
      проекте вообще нет ни одного теста, только ручная проверка через
      браузер
- [ ] Тесты на критичные фронтенд-хуки (особенно `shared/lib/dnd/*` —
      это место уже один раз ломалось системно, см.
      `docs/ARCHITECTURE.md`)

## 📋 Логирование — фронтенд и бэкенд

- [ ] **Бэкенд**: структурированное логирование запросов (например,
      `morgan` или `pino`) + логирование необработанных ошибок — сейчас
      единственный источник "что произошло" — `journalctl -u tasktracker`,
      и там только то, что сам код явно вывел в консоль
- [ ] **Фронтенд**: логирование ошибок в браузере — как минимум
      единообразный `console.error` в одном месте (там же, где будет
      обработка ошибок сохранения из раздела 🔴 выше), в перспективе —
      отправка критичных ошибок на сервер или во внешний сервис
      мониторинга, если понадобится видеть, что ломается у
      пользователя, а не только у себя при разработке
- [ ] Продумать хранение и ротацию логов на сервере (systemd уже отчасти
      решает это для `journalctl`, но стоит явно ограничить размер)

## 🐳 Docker — контейнеризация и деплой

Цель: собирать приложение в Docker-образ и деплоить его на VPS вместо
текущего "голый `git pull` + `npm install` прямо на сервере" —
_отдельный, самостоятельный этап_, не смешивать с рефакторингом API
выше (слишком много одновременных изменений усложняет отладку, если
что-то сломается).

- [ ] `Dockerfile` для бэкенда (Node + собранный `dist/`)
- [ ] Решить: фронтенд как отдельный образ (nginx отдаёт статику) или
      по текущей схеме — Express раздаёт `dist/` сам, один образ на всё
      приложение (проще, меньше движущихся частей для соло-проекта)
- [ ] `docker-compose.yml` — приложение + PostgreSQL как отдельные
      контейнеры **или** оставить PostgreSQL нативно на VPS, а
      контейнеризовать только само приложение (нативная БД с уже
      настроенными бэкапами — менее рискованный вариант, обсудить перед
      стартом)
- [ ] Обновить `.github/workflows/deploy.yml` — вместо `git pull` +
      `npm ci` на сервере, собирать образ (в CI или на сервере) и
      перезапускать контейнер
- [ ] На VPS: установить Docker, заменить текущий systemd-юнит
      `tasktracker.service` на управление контейнером (через
      `docker compose` + отдельный systemd-юнит, который его поднимает)
- [ ] Обновить `docs/DEPLOYMENT.md` под новый процесс — текущее описание
      (голый Node-процесс через systemd) станет неактуальным

**Почему это вообще нужно** (если понадобится вспомнить, зачем): Docker
даёт воспроизводимое окружение — "работает у меня" перестаёт зависеть от
того, что именно установлено на конкретном VPS, и переезд на новый
сервер (см. `PROJECT_BRAIN.md`, раздел 7.2) сводится к "поставь Docker,
подними контейнер" вместо повторения всей ручной установки.

## Рекомендуемый порядок

1. 🔴-пункты — они логически один кусок работы (гранулярный API +
   `updatedAt` + обработка ошибок на фронте идут рука об руку)
2. Валидация из 🟡 — естественно делать вместе с переписыванием роутов
   в пункте 1
3. Логирование — полезно иметь уже во время переписывания API, чтобы
   сразу видеть, что происходит
4. Остальное из 🟡 и 🟢 — по мере необходимости
5. Docker — отдельным заходом, когда API-часть уже стабильна
6. Тесты — писать вместе с новым API по мере его появления, а не отдельным
   этапом "потом"
