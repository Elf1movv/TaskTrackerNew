## Кандидат №1 — Авторизация (аккаунты пользователей)

Сейчас в приложении **нет логина вообще** — кто угодно, кто открывает
`mytracker.space`, видит один и тот же общий список задач/целей/привычек/
категорий. Поле `userId` зарезервировано в схеме почти у всех моделей
(`Task`, `Goal`, `Habit`, `Category`), но нигде не используется — это
осознанное решение на будущее (см. `LEARNING.md`), чтобы не пришлось
болезненно мигрировать данные, когда до логина дойдёт.

**Это главный кандидат на "что дальше"**, если цель — дать доступ
реальным пользователям (не только владельцу). Без этого "несколько
пользователей" технически невозможно: они будут просто редактировать
одни и те же данные.

**Решения, принятые заранее (обсуждено с владельцем 2026-09-18),
до захода в Plan Mode:**
- Всё своё, без стороннего auth-сервиса (Clerk/Auth0 и т.п.) — данные
  пользователей остаются в нашей же PostgreSQL, чтобы всегда можно было
  напрямую починить/восстановить/выдать доступ через Prisma
  Studio/SQL, не завися от чужой инфраструктуры (тот же принцип, что и
  выбор своего VPS вместо управляемых платформ)
- Библиотека — **Better Auth** (не писать сессии/хэширование паролей
  руками с нуля — слишком легко незаметно ошибиться в security-код;
  не хотим и полноценный сторонний сервис — see above)
- **Вход по паролю**, не по ссылке на почту (magic link) — обсуждали
  оба варианта: magic link меньше кода/багов, но требует открывать
  почту на каждый вход, а цель пользователя — быстро попасть в
  привычный флоу. Восстановление пароля ("забыл пароль") всё равно
  идёт через письмо
- Почта для писем восстановления — **Resend** (или аналог, замена
  провайдера — это один callback-метод + DNS-записи, не миграция
  данных, т.к. сам сервис ничего не хранит)
- **Категории — свои у каждого пользователя**, не общие на всех.
  При создании аккаунта новому пользователю автоматически заводятся
  те же 4 стандартные категории (Work/Personal/Health/Learning), что
  сейчас сидятся один раз на всё приложение — но **с возможностью их
  удалить** через интерфейс, чтобы пользователь мог полностью
  кастомизировать список под себя. Бэкенд для удаления категории уже
  готов (`DELETE /api/categories/:id`), не хватает только фронтенда и
  привязки категорий к `userId`

Что реально входит в эту фичу (чтобы не недооценить размер):
- [x] Модель `User` в Prisma + миграция (2026-09-18, руками, не через
      CLI-генератор Better Auth — см. `LEARNING.md`)
- [x] Better Auth: настройка, пароль + восстановление через письмо
      (Resend) (2026-09-18, код и логика; сам Resend с подтверждённым
      доменом `mytracker.space` и реальной отправкой писем настроен и
      проверен на проде 2026-09-19 — до этого письма технически не
      уходили, падали в лог сервера, т.к. `RESEND_API_KEY` был пуст)
- [x] Сессии на бэкенде (куки), middleware проверки авторизации на
      каждый роут (2026-09-18, `requireAuth`)
- [x] Продовые данные разобраны (2026-09-19) — **не переносом, а чистым
      стартом**: на проде реально было почти пусто (0 задач, 0 целей,
      1 привычка без важной истории, 4 дефолтные категории), поэтому
      решили не переносить старые "ничейные" записи на аккаунт
      владельца, а просто удалить их и начать с нуля на настоящем
      аккаунте. `userId` стал обязательным полем сразу после — без
      реальных данных вся сложная процедура репетиции/сверки строк
      была не нужна
- [x] Каждый запрос на бэкенде фильтрует по `userId` (2026-09-18)
- [x] `Category` по-настоящему привязана к `userId`
      (`@@unique([userId, name])`); сид 4 стандартных категорий теперь
      "лениво" — при первом запросе списка у нового пользователя
      (2026-09-18)
- [x] UI: экран входа/регистрации, разлогинивание, "забыл пароль"
      (2026-09-18)
- [x] UI: удаление категории — кнопка "×" на категории в фильтре
      вкладки Tasks, не в самом пикере формы (Radix `Select` плохо
      уживается с вложенной интерактивной кнопкой внутри пункта списка)
      (2026-09-18)

**Полностью готово и выкачено на прод (2026-09-19)** — регистрация →
подтверждение → вход → выход, изоляция данных между двумя разными
аккаунтами, автотесты бэкенда (31 тест, все зелёные), `userId`
обязателен везде. Владелец зарегистрировал настоящий аккаунт на
`mytracker.space`, старые данные без владельца удалены.

**Реальный инцидент по пути (2026-09-19)**: после пуша с новым кодом
прод упал на ~2 часа (502) — забыли реально прописать
`BETTER_AUTH_SECRET`/`BETTER_AUTH_URL` в `server/.env` на самом VPS
перед деплоем (документацию обновили, а сам файл на сервере — нет).
База данных не пострадала. Урок: при следующем изменении, требующем
новых переменных окружения — сначала руками прописать их на сервере,
потом уже пушить код, не наоборот.

      фиксированной ширины, и при разной длине названия категории весь
      правый блок (иконка+бейдж+кнопки), прижатый к краю карточки через
      соседний `flex-1`, целиком сдвигался по горизонтали, "утаскивая"
      иконку за собой. Фикс — фиксированная ширина у `Badge`
      (`w-20 justify-center truncate`) в `TaskRow.tsx` и
      `TodayTaskRow.tsx` — теперь правый блок всегда одной ширины,
      иконка приоритета в одной колонке независимо от длины категории.
      (3) Заголовок напоминания обрезался посередине слова — после
      добавления даты в прошлый раз строка "чекбокс+иконка+заголовок+
      дата+время" стала слишком тесной. `ReminderRow.tsx` и
      `ReminderBell.tsx` переведены на двухстрочную раскладку через
      `grid-cols-[auto_1fr]`: левая колонка — чекбокс+иконка
      фиксированной ширины, правая — заголовок сверху (на всю ширину,
      переносится свободно) и дата+время снизу помельче. (4) "Выполнено:
      N" в заголовке страницы Tasks считало вообще все выполненные
      задачи за всё время (`allTasks.filter(t => t.completed).length`),
      число росло бесконечно и не совпадало со списком под ним (тот уже
      показывает только сегодня выполненные, через готовую
      `isCompletedToday`). Заголовок теперь считает так же:
      `allTasks.filter(t => t.completed && isCompletedToday(t))`.
      `qa-tester` подтвердил все 4 пункта, включая живую проверку
      счётчика (+1/-1 при отметке/снятии задачи) и зумированные
      скриншоты выравнивания колонки приоритета.

## Как этим пользоваться

Когда в разговоре всплывает "давай это отложим на потом" — записывай
сюда пункт с коротким объяснением (что это и почему не сейчас), а не
только держи в голове. Если пункт из этого списка берём в работу —
переносим его в план (Plan Mode) как обычно, а здесь отмечаем `[x]`
после того, как сделано и запушено.
