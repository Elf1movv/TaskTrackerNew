## ✅ 1. HTML-инъекция в письме обратной связи — исправлено

**Файл:** `server/src/routes/feedback.ts:46-57`

Текст отзыва пользователя, а также его имя и email из аккаунта
вставляются в HTML письма без экранирования:

```ts
html: `
  <p><strong>Type:</strong> ${typeLabel}</p>
  <p><strong>From:</strong> ${from}</p>          // from = "${user.name} (${user.email})"
  <p><strong>Page:</strong> ${parsed.data.page ?? "unknown"}</p>
  <p><strong>Message:</strong></p>
  <p>${parsed.data.message}</p>                  // ← до 5000 символов свободного текста
`,
```

**В чём риск.** Любой залогиненный пользователь может написать в форме
обратной связи что-то вроде `<img src=x onerror="...">` или спрятать
поддельную ссылку под видом обычного текста — и это письмо в таком виде
придёт на почту разработчика (`FEEDBACK_EMAIL_TO`). Большинство
почтовых клиентов режут `<script>`, но не режут остальной HTML/CSS —
поддельные ссылки, скрытый текст, трекинг-пиксели всё ещё пройдут. То же
самое верно для имени пользователя (`user.name`) — оно тоже никак не
ограничено при регистрации и точно так же попадает в письмо сырым.

**Не затронуто:** письма подтверждения почты/сброса пароля
(`server/src/lib/emailTemplates.ts`) вставляют только серверную ссылку
(`url`), не текст пользователя — там инъекции нет.

**Сделано:** новая функция `escapeHtml` (`server/src/lib/escapeHtml.ts`,
с юнит-тестом) применена к `message`, `from`, `page` и `typeLabel` перед
вставкой в шаблон письма (`server/src/routes/feedback.ts`). Проверено
живьём — отправлен отзыв с `<img src=x onerror=...>` и кавычками,
принято корректно (201), покрыто тестами.

## ✅ 2. "Скриншот" в форме обратной связи не проверяется, что это изображение — исправлено

**Файл:** `server/src/validation/feedback.ts:5,10`, `server/src/routes/feedback.ts:31-32,56`

Сейчас единственная проверка — это длина строки:

```ts
const MAX_IMAGE_DATA_LENGTH = 7_000_000
imageData: z.string().max(MAX_IMAGE_DATA_LENGTH).optional(),
```

Нет проверки, что это действительно PNG/JPEG (ни по префиксу
`data:image/...`, ни по "магическим байтам" самого файла). Файл всегда
прикрепляется к письму под именем `screenshot.png` независимо от
реального содержимого.

**В чём риск.** Залогиненный пользователь может отправить под видом
"скриншота" произвольные данные (до ~5.25МБ) — это уйдёт вложением на
почту разработчика с обманчивым именем `screenshot.png`. Не критично
(нужен уже залогиненный аккаунт, получатель — сам разработчик), но
дыра в валидации, которую легко закрыть.

**Как починить.** Проверять, что `imageData` начинается с
`data:image/(png|jpeg|jpg|webp|gif);base64,` регуляркой перед принятием,
и/или сверять первые байты декодированного содержимого с сигнатурой
формата (PNG всегда начинается с `\x89PNG`, JPEG — с `\xFF\xD8\xFF`).
Регулярка на префикс — самый дешёвый вариант, закрывает 90% риска.

## ✅ 3. Лимит тела запроса 8MB общий на все роуты, парсится раньше проверки логина — исправлено

**Файл:** `server/src/app.ts:44`

```ts
app.use(express.json({ limit: "8mb" }))   // общий для /api/tasks, /api/goals, /api/habits и т.д.
```

Восьмимегабайтный лимит был поднят специально ради вложения-скриншота
в форме обратной связи, но применяется вообще ко всем JSON-роутам — а
задачи/цели/привычки/категории/напоминания в таком объёме тела никогда
не нуждаются. Хуже: `express.json()` — это глобальный middleware,
который выполняется **до** `requireAuth` каждого роутера. Значит,
неавторизованный запрос всё равно заставит сервер распарсить до 8МБ
JSON в память, и только потом получит 401.

**В чём риск.** Некритичный, но реальный вектор DoS: если слать много
параллельных запросов с телом в 7-8МБ на любой из этих роутов без
логина, сервер тратит CPU/память на парсинг, даже не дойдя до проверки
сессии. Для персонального проекта риск невысокий (нужен направленный
поток запросов), но легко устраняется.

**Сделано:** каждый роутер теперь монтируется со своим собственным
`express.json(...)` прямо на своём пути — `/api/tasks`, `/api/goals` и
т.д. получают лимит `256kb`, только `/api/feedback` — свои `8mb`
(`server/src/app.ts`). Заодно нашли и починили попутный баг: превышение
лимита раньше отдавало `500 Internal server error` вместо честного
`413` — `server/src/middleware/errorHandler.ts` теперь передаёт код
ошибки body-parser'а наружу как есть. Новый тест
(`server/src/app.test.ts`) проверяет оба сценария: маленький роут режет
слишком большое тело, фидбек — нет.

## 🟡 4. Нет блокировки аккаунта после подряд неудачных попыток входа — осознанно отложено

**Решение пользователя (2026-09-26):** для текущего масштаба проекта
(личный трекер) это признано ненужным усложнением, реализовывать не
будем. Раздел ниже оставлен как справочная информация — если проект
вырастет и появится больше пользователей, стоит вернуться к этому.

Проверено: Better Auth в этом проекте не подключает плагин
двухфакторной аутентификации (там же живёт единственная в библиотеке
логика блокировки аккаунта), и в `auth.ts` никакой отдельной логики
"N неверных паролей подряд → заблокировать" нет. Единственная защита —
общий rate-limit самой библиотеки (см. следующий пункт) — это лимит на
число запросов вообще, не на количество попыток именно для одного
email/пароля.

**В чём риск.** Подбор пароля (brute-force) конкретного аккаунта
технически возможен быстрее, чем хотелось бы — единственное
препятствие — общий лимит запросов, а не что-то, привязанное к
конкретному аккаунту.

**Как починить (по нарастающей сложности):**
- Минимум: в `auth.ts` явно настроить `rateLimit` построже именно для
  `/sign-in/email` (Better Auth поддерживает `rateLimit.customRules` по
  пути).
- Более надёжно: собственный счётчик неудачных попыток по email в базе
  (или временном хранилище) с блокировкой на N минут после, скажем,
  5 подряд неудачных попыток.

Для личного проекта с небольшим числом пользователей — не аварийная
находка, но стоит держать в бэклоге.

## 🟢 5. Rate-limit живёт в памяти процесса

Better Auth по умолчанию хранит счётчики запросов в оперативной памяти
процесса (`storage: "memory"`, никакого `secondaryStorage` в проекте не
настроено). Это значит: счётчики обнуляются при каждом рестарте
процесса — а у нас автодеплой на каждый пуш в `main`, то есть счётчик
обнуляется буквально при каждом деплое. Пока сервер один (не
масштабируется на несколько инстансов) — это не критично, просто
теоретическое окно "подождать деплоя и попробовать снова". Стоит знать,
не обязательно чинить прямо сейчас.

## ✅ Уже сделано правильно (проверено, не трогать)

- **IDOR (доступ к чужим данным по id)** — проверены ВСЕ 7 роутеров
  (tasks, goals, habits, habitGroups, categories, reminders, feedback)
  построчно. Каждый GET/PATCH/DELETE по id фильтрует одновременно по
  `id` И `userId` в одном Prisma-запросе. Проверки владения
  распространяются и на вложенные ссылки (например, при переносе
  привычки в другую группу — принадлежность группы тоже перепроверяется
  тем же пользователем). Ни одной дыры не найдено.
- **SQL-инъекции** — не используется ни одного `$queryRaw`/`$executeRaw`
  нигде в проекте, только типизированный Prisma query builder.
- **Утечка лишних полей через API** — все `toClientX`-мапперы (tasks,
  goals, habits, habitGroups, categories, reminders) явно перечисляют
  поля вручную, `userId` и служебный `order` нигде наружу не уходят.
- **CORS** — ограничен ровно двумя настоящими доменами
  (`mytracker.space`, `www.mytracker.space`), никакого `*`.
- **Заголовки безопасности** — `helmet()` подключен, живой сайт отдаёт
  полный набор: CSP, `Strict-Transport-Security`, `X-Content-Type-Options`,
  `X-Frame-Options`, `Referrer-Policy` и т.д. (проверено напрямую
  `curl -I https://mytracker.space/`).
- **HTTPS** — принудительный редирект с HTTP, сертификат обновляется
  автоматически (certbot).
- **Куки сессии** — `httpOnly: true`, `sameSite: "lax"`, `secure: true`
  в проде (Better Auth сам выставляет `secure` по протоколу
  `BETTER_AUTH_URL`) — фронтенд никогда не читает и не хранит токен
  сессии сам, только полагается на куку.
- **Смена пароля** — реально проверяет текущий пароль на сервере (не
  только на фронте), плюс требует "свежую" сессию (переавторизацию за
  последние 24 часа) для чувствительных действий.
- **"Выйти на всех устройствах"** — реально удаляет все сессии
  пользователя в базе, не просто чистит куку в браузере.
- **Асимметрия при сбросе пароля** — регистрация честно говорит "такой
  email уже есть", а сброс пароля намеренно НЕ показывает, существует
  ли email (ответ не ждёт результата отправки письма) — это осознанное,
  правильное решение против угадывания зарегистрированных email.
- **Секреты (.env)** — никогда не попадали в git ни разу за всю историю
  репозитория (проверено по `git log --all`), в бандл фронтенда не
  протекают (единственная `VITE_`-переменная — это просто `/api`,
  не секрет).
- **Фронтенд** — ни одного `dangerouslySetInnerHTML` с пользовательскими
  данными, ни одного прямого запроса на сторонний домен, пароли нигде
  не логируются и не отображаются, localStorage хранит только
  настройки интерфейса (тема, язык), никогда — токены или пароли.
