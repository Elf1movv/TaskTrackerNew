# File Guide — что за файл, зачем он и как им пользоваться

`docs/REPO_STRUCTURE.md` объясняет репозиторий как 3 больших слоя
(приложение / инструменты Claude Code / документация). Этот файл —
на уровень глубже: конкретный файл в корне репозитория или в
`src`/`server` — что он делает, почему он тут, и что с ним можно делать
руками.

**Что НЕ входит в этот файл**: каждый отдельный React-компонент внутри
`src/` (их сотни). Про то, "что делает конкретная кнопка/форма" — читай
`docs/requirements/` (там описано поведение по каждой фиче) или просто
спроси. Про то, "почему код в `src/` разложен по папкам `entities`/
`features`/`widgets` именно так" — читай `docs/ARCHITECTURE.md` (там
объяснена вся Feature-Sliced Design архитектура). Этот файл — только про
корневые/конфигурационные/инфраструктурные файлы и про то, что лежит на
первом уровне внутри `src`/`server`.

## 1. Что реально нужно приложению

### `package.json` (корень) и `server/package.json`

"Паспорт" проекта — два отдельных, потому что фронтенд и бэкенд — это
два разных Node-проекта со своими зависимостями (не монорепо в строгом
смысле, просто два соседних `package.json`). Внутри:
- `dependencies`/`devDependencies` — какие библиотеки нужны
- `scripts` — команды, которые можно запускать через `npm run <имя>`.
  В корне: `dev` (запустить фронтенд), `build` (собрать прод-версию),
  `typecheck`, `lint`, `test`, `fsd-lint`. В `server/`: `dev`, `build`,
  `test`, плюс `prisma:migrate`/`prisma:deploy`/`prisma:studio` —
  команды для работы с базой данных через Prisma
- `lint-staged` (корень) — какие проверки/автоформатирование запускать
  на изменённые файлы перед коммитом (см. `.husky/` ниже)

**Как пользоваться**: `npm run <script>` из соответствующей папки
(корень — для фронтенда, `server/` — для бэкенда).

### `package-lock.json` (в обеих папках)

Точные версии вообще всех зависимостей (включая зависимости
зависимостей), зафиксированные автоматически при `npm install`. Нужен,
чтобы у тебя, на CI и на проде ставились ровно одинаковые версии пакетов
— без него `npm install` мог бы поставить чуть более новую версию
где-то в глубине дерева зависимостей, и код бы вёл себя по-разному в
разных окружениях. **Руками не редактируется никогда** — меняется сам,
когда меняешь `package.json` и запускаешь `npm install`.

### `.env` и `.env.example` (в обеих папках, `.env.test`/`.env.test.example` в `server/`)

`.env` — реальные значения переменных окружения для этого конкретного
места (у тебя на компьютере — свои, на проде — свои, никогда не
коммитятся в git — см. `.gitignore` ниже). `.env.example` — тот же
список переменных, но с пустыми/примерными значениями, специально
закоммичен в git, чтобы было видно, какие переменные вообще нужны, не
раскрывая настоящих секретов. Когда клонируешь репозиторий с нуля —
копируешь `.env.example` → `.env` и заполняешь реальными значениями.
`.env.test`/`.env.test.example` — то же самое, но специально для тестов
(указывает на отдельную тестовую базу `tasktracker_test`, чтобы тесты не
могли случайно стереть реальные данные).

### `node_modules/` (в обеих папках)

Сюда `npm install` физически скачивает все зависимости. Полностью
генерируется из `package.json`/`package-lock.json` — можно удалить и
пересоздать командой `npm install`, ничего не потеряется. Никогда не
коммитится (в `.gitignore`), никогда не редактируется руками.

### `dist/` (в обеих папках)

Результат сборки — то, что реально запускается в проде. Во фронтенде —
готовый HTML/CSS/JS после `npm run build` (`vite build`). В `server/` —
скомпилированный из TypeScript в обычный JavaScript код после
`npm run build` (`tsc`). Тоже генерируется автоматически, тоже в
`.gitignore` — коммитить сюда нечего, это не исходный код, а его
"выхлоп".

### `.gitignore`

Список того, что git должен **игнорировать** — не показывать в
`git status`, никогда не добавлять в коммит, даже если попросить
`git add .`. У нас туда попадают: `node_modules`/`dist` (генерируются),
`.env`/`.env.test`/`db.env` (секреты), `.DS_Store` (мусор от macOS),
логи. Если создаёшь новый тип файла с секретами — обязательно добавь
сюда, иначе он может случайно попасть в публичный репозиторий.

## 2. Инструменты качества кода — работают вместе как конвейер

Эти файлы редко трогаешь руками, но важно понимать, что каждый из них
делает и **в каком порядке** они выполняются при коммите.

### `tsconfig.json` + `tsconfig.node.json` (корень), `server/tsconfig.json`

Настройки TypeScript-компилятора: как проверять типы, какую версию
JavaScript использовать как цель, где искать файлы. `tsconfig.node.json`
— отдельный маленький конфиг только для `vite.config.ts` (сам конфиг
Vite тоже написан на TypeScript и запускается в Node, а не в браузере —
ему нужны немного другие настройки). Команда `npm run typecheck`
(`tsc --noEmit`) читает эти файлы и проверяет весь код на ошибки типов,
ничего не собирая — просто "нашли бы мы ошибку, если бы собирали".

### `eslint.config.js` (корень)

Правила линтера — что считается плохим стилем кода или потенциальной
ошибкой (неиспользуемая переменная, нарушение правил React-хуков и
т.п.). Специально исключает `src/shared/ui/**` — это вендорные
(сгенерированные, не написанные нами) компоненты из shadcn/ui, их не
имеет смысла проверять по нашим правилам. `npm run lint` — проверить,
`npm run lint:fix` — исправить то, что можно исправить автоматически.

### `.prettierrc.json` + `.prettierignore` (корень)

Настройки автоформатирования (отступы, кавычки, длина строки — у нас:
без точек с запятой, двойные кавычки, 110 символов на строку). Отдельно
от ESLint: ESLint ищет ошибки и плохие практики, Prettier — только
форматирует внешний вид кода, они не конфликтуют благодаря
`eslint-config-prettier` в `eslint.config.js` (отключает те правила
ESLint, что касаются форматирования, чтобы два инструмента не спорили
друг с другом). `npm run format` — переформатировать всё вручную.

### `steiger.config.js` (корень)

Настройки **Steiger** — линтера конкретно для архитектуры
Feature-Sliced Design (проверяет, что слои `app/pages/widgets/features/
entities/shared` не нарушают правила зависимостей между собой, и что
папки не слишком мелкие/бесполезные). `npm run fsd-lint`. Два правила
специально понижены с ошибки до предупреждения — см. комментарии в
самом файле (проект специально готовит слайсы `features`/`widgets`
заранее, до второго места использования — расчёт на рост).

### `.husky/pre-commit` + `lint-staged` (в `package.json`)

**Husky** — механизм git-хуков: маленьких скриптов, которые git
запускает автоматически на определённых действиях. У нас один хук —
`pre-commit`, который просто запускает `npx lint-staged`. **lint-staged**
берёт только те файлы, которые ты сейчас коммитишь (не весь репозиторий
— это было бы медленно), и прогоняет их через ESLint (`--fix`) и
Prettier — правки применяются автоматически и попадают в тот же коммит.
Поэтому иногда после `git commit` видно, что файлы "поменялись на
диске" — это не баг, это именно так и должно работать.

**Порядок при `git commit`**: husky → lint-staged → ESLint исправляет,
что может → Prettier форматирует → коммит создаётся уже с
отформатированными файлами.

## 3. Frontend-специфичные конфиги

### `vite.config.ts`

Настройки **Vite** — инструмента, который во время разработки мгновенно
пересобирает страницу при изменении файла (`npm run dev`), а для прода
собирает всё в оптимизированные `dist/assets/*.js`/`*.css`
(`npm run build`). Важные детали именно нашего конфига:
- `alias: { "@": "./src" }` — почему в коде пишем `import ... from
  "@/entities/task"` вместо длинных `../../../entities/task`
- `server.proxy` — в разработке фронтенд (порт 5173) и бэкенд (порт
  3001) это два разных процесса; прокси перенаправляет запросы на
  `/api/*` с 5173 на 3001, чтобы код мог всегда обращаться к
  относительному пути `/api`, не важно — разработка это или прод
- `test: { ... }` — тот же файл используется и для настройки Vitest
  (тестов), не только сборки — `include` специально ограничивает тесты
  только папкой `src/`, чтобы фронтенд случайно не подхватил и не
  запустил тесты бэкенда (те бьют по базе данных и опасны без
  специальной тестовой базы)
- `figmaAssetResolver` — небольшой плагин, оставшийся от исходного
  экспорта из Figma Make (см. раздел 5 ниже)

### `postcss.config.mjs`

Формально нужен для Tailwind CSS, но сейчас пустой (`export default {}`)
— Tailwind v4 через `@tailwindcss/vite`-плагин настраивает себя сам,
этот файл существует только на случай, если понадобится добавить
дополнительный PostCSS-плагин в будущем.

### `index.html`

Единственный настоящий HTML-файл всего приложения — точка входа. React
"монтируется" в `<div id="root">` этого файла через `src/main.tsx`.
Всё остальное, что ты видишь в браузере — это JavaScript, который
динамически строит содержимое этого одного `div`'а (Single Page
Application).

### `.dockerignore`

То же самое, что `.gitignore`, но для Docker: список того, что **не**
копировать внутрь Docker-образа при сборке — экономит время сборки и
размер образа (не тащим `node_modules`/`dist` внутрь, они всё равно
пересоздаются заново прямо в образе, см. `Dockerfile` ниже) и не даёт
секретам (`.env`) случайно попасть в публично доступный образ на GHCR.

## 4. Docker и деплой

### `Dockerfile`

Рецепт сборки одного Docker-образа для всего приложения (фронтенд +
бэкенд вместе — Express сам раздаёт статику фронтенда). Три стадии
(multi-stage build):
1. **frontend-build** — ставит зависимости, собирает фронтенд (`npm run
   build` → `dist/`)
2. **backend-build** — ставит зависимости бэкенда, генерирует Prisma
   Client, компилирует TypeScript в JS
3. **runtime** — финальный, лёгкий образ: копирует только то, что
   реально нужно для запуска (собранные файлы, `node_modules` бэкенда,
   без исходников TypeScript и без инструментов сборки) — так итоговый
   образ меньше и не тащит с собой ничего лишнего

### `docker-compose.yml`

Описывает, какие контейнеры поднимать вместе и как они связаны:
`app` (само приложение) + `db` (PostgreSQL). Ключевые детали:
- `app` слушает только на `127.0.0.1:3001` — снаружи VPS недоступен
  напрямую, только через nginx (см. `docs/DEPLOYMENT.md`)
- `db` вообще не публикует порт наружу — достижим только изнутри
  Docker-сети `tasktracker-net`, по имени сервиса `db`
- `depends_on: condition: service_healthy` — `app` не запустится, пока
  `db` не прошла healthcheck (иначе бэкенд мог бы упасть при старте,
  пытаясь подключиться к ещё не готовой базе)
- `volumes: tasktracker-db-data` — здесь реально живут все данные
  Postgres на диске VPS; без явного `name:` Docker Compose подставил бы
  префикс проекта и можно было бы случайно получить пустой volume
  вместо настоящего (это реально едва не случилось при переносе базы в
  Docker, см. `LEARNING.md`)
- `x-logging` — общие настройки на оба сервиса: не более 30MB логов на
  контейнер, чтобы диск VPS не забился логами со временем

**Как пользоваться на VPS**: `docker compose up -d` (поднять),
`docker compose logs app -f` (смотреть логи), `docker compose down`
(остановить — **без** `-v`, иначе удалится и volume с данными). Локально
этот файл не используется — для разработки Postgres просто установлен
через Homebrew напрямую (см. `docs/ARCHITECTURE.md`).

### `.github/workflows/deploy.yml`

Настройки **GitHub Actions** — автоматизации, которая запускается на
серверах GitHub при пуше в `main`. У нас два шага:
1. Собрать Docker-образ (по `Dockerfile`) и запушить его в GHCR (GitHub
   Container Registry — бесплатное хранилище Docker-образов от GitHub)
2. Зайти на VPS по SSH и выполнить: `git pull` → `docker compose pull`
   (скачать новый образ) → `npx prisma migrate deploy` (применить новые
   миграции базы, если есть) → `docker compose up -d` (перезапустить
   с новым образом) → `docker image prune -f` (убрать старые
   неиспользуемые образы, чтобы не копились на диске)

Именно этот файл выполняется автоматически каждый раз, когда мы делаем
`git push origin main` — то, что мы только что и сделали для шести
фич.

## 5. Файлы-артефакты — не используются, но лежат в репозитории

Проект изначально был экспортирован из **Figma Make** (см. `README.md`,
`ATTRIBUTIONS.md`) — инструмента, который генерирует стартовый React-код
по дизайну в Figma. От этого в репозитории остались файлы, которые
реальному приложению не нужны:

- **`guidelines/Guidelines.md`** — шаблон от Figma Make для
  инструкций дизайн-системы, полностью закомментирован, никогда не
  заполнялся. Не используется никаким инструментом в проекте.
- **`pnpm-workspace.yaml`** — конфиг для пакетного менеджера `pnpm`, но
  проект на самом деле использует `npm` (смотри `package-lock.json`, а
  не `pnpm-lock.yaml`). Просто не удалили при переходе.
- **`default_shadcn_theme.css`** (корень) — общая дефолтная тема
  shadcn/ui, никуда не импортируется (реальная тема — `src/styles/
  theme.css`, см. `docs/requirements/08. Theme.md`).

Трогать их не обязательно — они не мешают работе приложения, но и не
нужно на них ориентироваться, если что-то ищешь (например, если ищешь
"где настроена тема" — это `src/styles/theme.css`, не
`default_shadcn_theme.css`).

## 6. `src/` — верхний уровень (фронтенд)

Подробное объяснение **почему** код разложен именно так — в
`docs/ARCHITECTURE.md` (раздел про Feature-Sliced Design). Здесь —
только что означает каждая папка/файл первого уровня:

- **`main.tsx`** — самая первая строчка кода, которая выполняется в
  браузере. Находит `<div id="root">` в `index.html` и "монтирует" туда
  React-приложение (`<App />` из `app/App.tsx`)
- **`vite-env.d.ts`** — служебный файл с типами для Vite (например,
  чтобы TypeScript понимал `import.meta.env.VITE_API_URL`)
- **`app/`** — сборка всего приложения воедино: роутинг
  (`app/routes/router.tsx` — какой URL показывает какую страницу),
  провайдеры (`app/providers/AppProviders.tsx` — все контексты
  React, вложенные друг в друга: тема, язык, задачи, цели, привычки,
  категории), общие стили
- **`pages/`** — по одной папке на каждый экран/страницу (Tasks, Goals,
  Today, Calendar) — собирают widgets в готовый экран
- **`widgets/`** — самостоятельные крупные блоки интерфейса, каждый
  используется на одной конкретной странице (список задач, сетка
  привычек, панель дня в календаре)
- **`features/`** — конкретные пользовательские действия (форма
  добавления задачи, кнопка удаления, переключатель выполнено/нет) —
  меньше, чем widgets, обычно переиспользуются в нескольких местах
- **`entities/`** — бизнес-сущности сами по себе: что такое `Task`,
  откуда берутся его данные (`api/`), как ими управлять (`model/`) —
  независимо от того, на какой странице их показывают
- **`shared/`** — то, что не привязано к конкретной фиче вообще:
  универсальные UI-компоненты (`shared/ui/` — кнопки, попапы,
  вендорные shadcn-компоненты), общие утилиты (`shared/lib/` —
  работа с датами, drag-and-drop, i18n, хранение/синхронизация данных)
- **`styles/`** — глобальные CSS-файлы, включая `theme.css` (тёмная и
  светлая палитра — см. `docs/requirements/08. Theme.md`)

**Правило зависимостей** (проверяется `steiger`/`fsd-lint`): слой может
использовать только слои ниже себя в этом списке (`app` может всё,
`shared` не может использовать вообще ничего из перечисленного выше себя)
— это и есть то самое архитектурное правило, подробно объяснённое в
`docs/ARCHITECTURE.md`.

## 7. `server/` — верхний уровень (бэкенд)

- **`src/index.ts`** — точка входа: запускает Express-сервер, слушает
  порт (3001)
- **`src/app.ts`** — собирает сам Express-объект: подключает middleware
  (`cors`, `helmet`, `morgan` — логирование запросов), регистрирует все
  роуты (`/api/tasks`, `/api/goals`, `/api/habits`, `/api/categories`),
  раздаёт собранный фронтенд как статику, обрабатывает 404 и ошибки.
  Отдельно от `index.ts` специально — чтобы тесты (`supertest`) могли
  создать приложение и слать ему запросы напрямую, не поднимая реальный
  сетевой порт
- **`src/db.ts`** — создаёт и экспортирует один общий экземпляр Prisma
  Client (объект, через который весь остальной код бэкенда обращается к
  базе данных)
- **`src/routes/`** — по одному файлу на каждую сущность
  (`tasks.ts`/`goals.ts`/`habits.ts`/`categories.ts`) — здесь живут все
  `GET`/`POST`/`PATCH`/`DELETE` обработчики
- **`src/validation/`** — `zod`-схемы: что именно можно прислать в теле
  запроса на `POST`/`PATCH`, что будет отклонено с `400`
- **`src/middleware/errorHandler.ts`** — ловит любую необработанную
  ошибку из любого роута и превращает её в единообразный JSON-ответ
  `500`, вместо падения всего процесса
- **`src/lib/`** — мелкие утилиты общего назначения для бэкенда
  (например, распознавание "эта ошибка Prisma значит 'запись не
  найдена'")
- **`prisma/schema.prisma`** — модели данных (структура таблиц
  `Task`/`Goal`/`Habit`/`Category`) — единственное место, откуда Prisma
  знает, как устроена база
- **`prisma/migrations/`** — история изменений структуры базы, по одной
  папке на каждое изменение, в хронологическом порядке. Каждая — это
  реальный `.sql`-файл, который можно прочитать и понять, что именно
  изменилось. **Никогда не редактируется задним числом** после того,
  как применена хоть где-то (кроме как в момент, пока миграция ещё не
  выкачена ни на одну реальную базу — так один раз сделали, чтобы
  добавить сид данных в ту же миграцию, что создавала таблицу)
- **`vitest.config.ts`** + **`vitest.setup.ts`** — настройка тестов
  бэкенда; `setup.ts` специально проверяет, что тесты запускаются
  именно на тестовой базе (`tasktracker_test`), а не по ошибке на
  реальной — это защита от катастрофы "тест случайно стёр продовые
  данные"

## Итого — как искать нужный файл

1. Хочешь понять **архитектурное решение** ("почему PATCH, а не PUT",
   "почему JSON-колонка, а не таблица") → `docs/ARCHITECTURE.md`
2. Хочешь понять **точное поведение фичи** ("что именно происходит,
   когда нажимаешь кнопку X") → `docs/requirements/`
3. Хочешь понять **конкретный файл конфигурации/инфраструктуры** → этот
   файл
4. Хочешь понять **продовую инфраструктуру дословно** (какие домены,
   какие конфиги nginx) → `docs/DEPLOYMENT.md`
5. Не нашёл ответ нигде из перечисленного — просто спроси, разберём
   вместе и, если пригодится на будущее, запишем сюда.
