# Архитектура проекта

Этот файл — техническое описание того, как устроено приложение и почему
именно так. Он существует отдельно от `LEARNING.md` (там — обучающий
глоссарий и журнал решений в стиле "что мы разбирали и когда"): этот файл —
справочник по системе целиком, для быстрого поиска ответа на вопрос "как
это устроено" без необходимости перечитывать историю разработки.

Если этот файл разошёлся с реальным кодом (например, описан паттерн,
которого уже нет) — значит, документация устарела и её нужно поправить,
а не доверять ей вслепую.

## Что это за приложение

Личный трекер задач, целей (с вложенными milestones) и привычек. Одна
страница "Today" (сегодняшние задачи + прогресс), отдельные разделы Tasks /
Goals / Habits / Calendar.

## Стек

- **Фронтенд**: React + TypeScript + Vite, архитектура — Feature-Sliced
  Design (FSD) v2.1
- **Бэкенд**: Node.js + TypeScript + Express 5 + Prisma ORM
- **База данных**: PostgreSQL
- **Деплой**: свой VPS (см. `docs/DEPLOYMENT.md`), без управляемых
  платформ (Vercel/Railway и т.п.) — осознанный выбор, "работает на наших
  мощностях, без посредников"

## Frontend: Feature-Sliced Design

Слои (от общего к частному): `app` → `pages` → `widgets` → `features` →
`entities` → `shared`. Слой выше может импортировать только из слоёв ниже
себя, никогда наоборот, и **никогда напрямую из соседнего слайса того же
слоя** (например, `features/habit-card` не может импортировать из
`features/delete-habit` — это разные фичи одного слоя).

Когда двум фичам одного слоя нужно скомпоноваться вместе (например,
показать карточку привычки + кнопки редактирования/удаления рядом) —
это делается на уровне `widgets`, который имеет право импортировать из
нескольких фич сразу. Пример: `widgets/habit-tracker-grid` собирает вместе
`features/habit-card` + `features/edit-habit` + `features/delete-habit`.

Соблюдение архитектуры проверяется линтером **Steiger**
(`steiger.config.js`) — см. `docs/../project_steiger_fsd_linter` в памяти
проекта. Два правила намеренно понижены до `warn`:
`fsd/insignificant-slice` и `fsd/segments-by-purpose` (для
`app/providers`) — осознанный компромисс на раннем этапе роста проекта.

### Repository<T> — абстракция хранения данных

Единый интерфейс, через который вся кодовая база (провайдеры,
компоненты) читает и пишет данные, не зная, что за ним стоит REST API:

```ts
interface Repository<T extends { id: string; updatedAt: string }> {
  list(): Promise<T[]>
  create(item: T): Promise<T>
  update(id: string, patch: Partial<T>, expectedUpdatedAt: string): Promise<T>
  remove(id: string): Promise<void>
  reorder(order: { id: string; order: number }[]): Promise<void>
}
```

`entities/task/api/taskRepository.ts` (и аналогично `goal`, `habit`)
создаёт конкретную реализацию через `createRestRepository`. Раньше
здесь был `localStorage` (`createLocalStorageRepository`, удалён как
неиспользуемый после перехода на бэкенд) и интерфейс был проще
(`list`/`save` — вернуть/сохранить **всю** коллекцию целиком); теперь
интерфейс — по одной операции на действие, см. раздел ниже про
гранулярный REST API.

Хук `usePersistedCollection` (`shared/lib/storage/usePersistedCollection.ts`)
— единая реализация паттерна "оптимистичное обновление + откат при
ошибке" поверх этого интерфейса, переиспользуется всеми тремя
провайдерами: применяет изменение локально сразу, шлёт один сетевой
запрос, и либо подтверждает результат версией с сервера, либо
откатывает + показывает `toast.error` (через `sonner`,
`app/providers/AppProviders.tsx`).

### Drag-and-drop: критичный gotcha с callback ref

Все хуки drag-and-drop (`useDragReorder`, `useDragItem`, `useDropTarget` в
`shared/lib/dnd/`) **обязаны** оборачивать возвращаемый ref-callback в
`useCallback`. Если этого не сделать, React будет отсоединять и заново
присоединять DOM-узел на каждый рендер — драг ломается прямо посреди
жеста (внешне выглядит как "текст просто выделяется" или "элемент
подхватывается, но при отпускании прыгает назад").

Это же правило касается любых обработчиков, которые передаются в эти
хуки — если создавать их инлайн внутри `.map()` без `useCallback`, они
тоже будут нестабильны на каждый рендер. Смотри как пример
`widgets/calendar-grid/ui/components/CalendarDayCell.tsx` — он сам
собирает свой стабильный обработчик через `useCallback`, а не получает
готовый инлайн-замыкание из родителя.

**Если где-то в будущем drag-and-drop снова "не работает через раз" —
первым делом проверяй именно это.**

### Тесты на drag-and-drop хуки

`shared/lib/dnd/*.test.tsx` — два разных вида тестов, каждый решает свою
задачу:

1. **Стабильность `ref`** (`useDragItem.test.tsx`,
   `useDropTarget.test.tsx`, `useDragReorder.test.tsx`) — рендерит хук
   через `renderHook` внутри настоящего `DndProvider` с **`TestBackend`**
   (официальный тестовый backend от команды react-dnd — HTML5-события
   ненадёжно работают в jsdom, поэтому для тестов используется не тот
   backend, что в проде). Проверяет, что `ref` не меняет идентичность
   между перерендерами без изменения пропсов — это прямой регресс-тест
   на исторический баг с нестабильными callback ref (см. выше)
2. **Бизнес-логика** (`useDragReorder.behavior.test.tsx`,
   `useDropTarget.behavior.test.tsx`) — здесь сам `react-dnd` **замокан**
   (`vi.mock("react-dnd")`), тест вызывает построенный хуком `spec`
   (`hover`/`drop`) напрямую и проверяет именно нашу логику (self-hover
   guard в `useDragReorder`, кому передаётся `onDrop`)

**Почему не через `TestBackend.simulateHover/simulateDrop` для обоих
видов**: у react-dnd ID хендлеров (`S0`, `T1`, ...) генерируются глобальным
счётчиком на весь процесс, а не с нуля на каждый тест — то есть
захардкодить конкретный ID в тесте нельзя, он не детерминирован между
тестами. Публичного способа узнать реальный присвоенный ID снаружи хука
нет. Поэтому для проверки именно нашей условной логики проще и надёжнее
подменить сам `react-dnd`, чем гоняться за его внутренними деталями.

Оба вида тестов проверены на то, что реально ловят регрессию (не просто
формально существуют) — переключил `useCallback` и guard-условие
обратно на "сломанную" версию, оба типа тестов упали как положено.

**Настройка тестов на фронтенде** — `vite.config.ts` → блок `test`
(через `vitest/config`, чтобы не дублировать alias `@` и React-плагин в
отдельном файле). **Важно**: `test.include` явно ограничен `src/**`.
Без этого при первой настройке `vitest` в корне случайно подхватывал и
запускал ещё и тесты бэкенда (`server/src/routes/*.test.ts`) — они
разрушительны (`deleteMany({})` в каждом тесте) и рассчитаны только на
отдельную тестовую базу, которую гарантирует `server/vitest.setup.ts` —
но эта защита относится только к конфигу бэкенда, корневой её не видит.
Итог того случая — стёрлась локальная dev-база (не прод, ничего ценного
не пострадало), но сама дыра требовала немедленного фикса.

## Backend

### REST API: гранулярный CRUD + защита от конфликтов через updatedAt

Роуты (`server/src/routes/tasks.ts`, `goals.ts`, `habits.ts`) — по одному
паттерну на каждую сущность (изначально была одна пара `GET`/`PUT`,
заменяющая всю коллекцию целиком — см. историю решений в
`docs/ROADMAP.md`, это был первый, сознательно упрощённый вариант):

- `GET /` — весь список, отсортированный по `order`, теперь включая
  `updatedAt` у каждой записи
- `POST /` — создать одну запись; `order` = текущий минимум минус 1 (не
  максимум плюс 1) — новые элементы должны появляться **первыми**,
  как и ожидает интерфейс
- `PATCH /:id` — частично обновить одну запись. Тело:
  `{ patch: {...}, expectedUpdatedAt: "..." }`. Реализовано через
  **атомарный** `updateMany({ where: { id, updatedAt: expectedUpdatedAt }, ... })`
  — если ни одна строка не подошла под условие, разбираемся отдельно:
  нет такой записи → `404`; есть, но `updatedAt` не совпал (кто-то
  успел изменить раньше) → `409` с актуальной версией записи в ответе
- `PATCH /reorder` — отдельный bulk-эндпоинт, меняет **только** колонку
  `order` для присланных `{id, order}` пар, никогда не трогает
  остальные поля — реордер с одного устройства физически не может
  затереть правку поля с другого
- `DELETE /:id` — удалить одну запись, `404` если её уже нет

**Конфликт-детекция на практике**: клиент при любом изменении посылает
`updatedAt`, который видел последним. Если сервер уже сохранил более
новую версию (кто-то поменял с другого устройства) — `PATCH` не
применяется, возвращается `409` с актуальной записью, а фронтенд
(`usePersistedCollection`) подменяет локальную версию версией с сервера
и показывает `toast` — вместо того, чтобы тихо затереть чужое
изменение, как было при whole-collection `PUT`.

Валидация тела запроса — через `zod`-схемы в `server/src/validation/`
(до этого была только проверка "это массив?"). Ошибки Prisma
"запись не найдена" (`P2025`) превращаются в `404` через
`server/src/lib/prismaErrors.ts`, остальные — в общий `500` через
`server/src/middleware/errorHandler.ts` (единственный
error-handling middleware, регистрируется последним в
`server/src/app.ts`).

### Модель данных (`server/prisma/schema.prisma`)

```mermaid
erDiagram
    Task {
        string id PK
        string title
        boolean completed
        string priority
        string category
        date dueDate
        int order
    }
    Goal {
        string id PK
        string title
        string description
        int progress
        string targetDate
        string color
        json milestones
        int order
    }
    Habit {
        string id PK
        string title
        string icon
        string color
        string_array completedDates
        int order
    }
```

Три независимые таблицы — **без внешних ключей друг на друга**, это не
случайность: сущности приложения сейчас никак не связаны между собой
(задача не привязана к цели, привычка не привязана ни к чему). Если
появится, например, "привязать задачу к цели" — тогда в `Task`
понадобится `goalId` со внешним ключом на `Goal.id`, и эту диаграмму
нужно будет обновить.

Три модели: `Task`, `Goal`, `Habit`. У каждой есть `order` (для
сохранения порядка после drag-and-drop, индексирован — `@@index([order])`,
`GET` всегда сортирует по нему) и `userId` (nullable, сейчас нигде не
используется — оставлено заранее, чтобы при добавлении логина не
пришлось болезненно мигрировать существующие строки).

`Task.dueDate` — настоящий SQL `date` (`@db.Date`, не `DateTime` — без
компонента времени суток, избегает сдвига по часовому поясу), тоже
индексирован (`@@index([dueDate])`). До 2026-09-17 хранился строкой;
на проводе для клиента формат не изменился (`"YYYY-MM-DD"` — конвертация
происходит на границе API, в `toClientTask`/валидации, а не проникает
дальше во фронтенд). Индекс пока не используется активно — Calendar
всё ещё фильтрует уже загруженный список на клиенте, а не запрашивает
диапазон дат у сервера, но задел под это уже есть.

`Goal.milestones` хранится JSON-колонкой, а не отдельной таблицей — чтобы
не усложнять сверх уровня, который уже был у `Task`. Можно
нормализовать в отдельную таблицу позже, если понадобится сложная
работа с milestones напрямую через SQL.

### Single-origin в продакшене

`server/src/app.ts` в продакшене не только отвечает на `/api/*`, но и
раздаёт собранный фронтенд (`express.static` + SPA fallback на
`index.html` для любых остальных путей). Один процесс, один порт, один
origin — браузер, обращаясь к своему же фронтенду, никогда не задействует
CORS вообще (same-origin запросы ему не подчиняются).

В деве всё точно так же работает благодаря `vite.config.ts` → `server.proxy`
(`/api` проксируется на `localhost:3001`), поэтому `VITE_API_URL=/api`
(относительный путь) — единственное значение, которое вообще когда-либо
нужно, и в деве, и в проде.

`cors()` в `app.ts` всё равно настроен (`origin: ALLOWED_ORIGINS`,
конкретно `https://mytracker.space` и `https://www.mytracker.space`) —
не потому что это нужно для обычной работы приложения, а на случай
прямого кросс-доменного запроса к API (например, с другого инструмента
или будущего клиента). Раньше был открыт полностью (`cors()` без
аргументов); сужен до конкретных доменов — cheap improvement, не
требует авторизации, чтобы иметь смысл.

### Security-заголовки и обработка неизвестных путей

`helmet()` подключен в `app.ts` — стандартный набор security-заголовков
(`Strict-Transport-Security`, `X-Content-Type-Options`,
`X-Frame-Options` и т.п.), без дополнительной настройки под конкретные
нужды приложения.

Любой путь под `/api/*`, не совпавший ни с одним роутом, теперь получает
JSON `{"error": "Not found"}` с кодом `404` — до этого падал в SPA
fallback и возвращал HTML-страницу приложения с кодом `200`, что
маскировало реальную ошибку.

## Философия проверки изменений

Прохождение тайпчекера/линтера — необходимое, но не достаточное условие
"работает". Пример: баг с нестабильными callback ref проходил
тайпчекинг без единой ошибки, но реально ломал drag-and-drop в браузере.
Правило: перед тем как считать функциональность готовой, проверять её
реальным взаимодействием (настоящий клик/драг мышью, реальный проход
через API curl'ом, реальная проверка данных в базе), а не только
статическим анализом.

## Известные ограничения / технический долг

**Актуальный план и полный список (Docker, дальнейшее логирование и
т.п.)** — `docs/ROADMAP.md`. Гранулярный REST API + конфликт-детекция
через `updatedAt` (были в списке ограничений здесь) — уже сделаны, см.
раздел про REST API выше.

- Нет авторизации/логина — `userId` в схеме есть, но не используется.
  Список разрешённых CORS-доменов (`ALLOWED_ORIGINS` в `app.ts`)
  прописан вручную по этой же причине — вернуться к этому вопросу
  вместе с логином, если появятся другие легитимные клиенты
- Индексы на `order`/`dueDate` есть, но фактически не используются
  запросами приложения активно (Calendar фильтрует на клиенте, `GET`
  всегда читает всю коллекцию целиком) — задел на будущее, не сразу
  дающий эффект
- Один большой JS-бандл на фронтенде (626 KB), Vite предупреждает про
  code-splitting — не критично при текущем размере приложения, но
  стоит учитывать при значительном росте функциональности
