# Конспект обучения — TaskTrackerNew

## Термины

- **компонент (component)** — переиспользуемый кусок интерфейса, оформленный
  как функция, которая возвращает разметку (JSX). Например, `TodayPage` и
  `AddTaskForm` — оба компоненты. (объяснено: 2026-08-13, при добавлении
  кнопки "Add task" на Today)
- **состояние (state)** — данные, которые компонент "запоминает" между
  перерисовками экрана и которые могут меняться со временем (например,
  "форма сейчас открыта или закрыта"). Создаётся через хук `useState`.
  (объяснено: 2026-08-13)
- **хук (hook)** — функция React, имя которой начинается с `use`
  (`useState`, `useTasks` и т.д.), и которая даёт компоненту дополнительные
  возможности — например, "память" между перерисовками. (объяснено:
  2026-08-13)
- **обработчик события (event handler)** — функция, которая выполняется в
  ответ на действие пользователя, например `onClick` — что делать по клику
  на кнопку. (объяснено: 2026-08-13)
- **условный рендеринг (conditional rendering)** — показ разной разметки в
  зависимости от состояния, например `{isAdding && <AddTaskForm />}` —
  показать форму, только если `isAdding` истинно. (объяснено: 2026-08-13)
- **импорт (import)** — способ подключить в файл код, который определён в
  другом файле или библиотеке, например `import { useState } from "react"`.
  (объяснено: 2026-08-13)
- **JavaScript / TypeScript / React / JSX-TSX — кто есть кто**: JavaScript
  (JS) — сам язык программирования; TypeScript (TS) — JS плюс типы (файлы
  `.ts`/`.tsx` в проекте); React — библиотека для интерфейсов, написанная на
  JS/TS (даёт нам компоненты, хуки, state, props); JSX/TSX — синтаксис,
  который позволяет писать HTML-подобную разметку внутри JS/TS-файла (TSX —
  то же самое, но в TypeScript-файле). (объяснено: 2026-08-13)
- **клиент / сервер** — клиент (браузер, наш React-фронтенд) и сервер (наша
  Express-программа) — два отдельных процесса, которые общаются по сети,
  даже если оба на одном компьютере. (объяснено: 2026-09-07, при разборе
  backend)
- **порт** — номер "двери", через которую конкретная программа принимает
  соединения на компьютере (5173 — фронтенд, 3001 — сервер, 5432 —
  PostgreSQL). (объяснено: 2026-09-07)
- **HTTP-запрос / метод** — сообщение от клиента к серверу по сети; `GET` —
  "дай мне данные", `PUT` — "замени данные на присланные". (объяснено:
  2026-09-07)
- **эндпоинт / роут (route)** — конкретный "адрес" на сервере, к которому
  можно обратиться, например `/api/tasks`. (объяснено: 2026-09-07)
- **JSON** — текстовый формат, в котором клиент и сервер пересылают друг
  другу данные. (объяснено: 2026-09-07)
- **ORM (Object-Relational Mapping)** — программа-переводчик (у нас —
  Prisma), которая превращает вызовы вроде `db.task.findMany()` в
  настоящий SQL-запрос к базе, чтобы не писать SQL руками. (объяснено:
  2026-09-07)
- **SQL** — язык запросов к реляционным базам данных (таким как
  PostgreSQL). (объяснено: 2026-09-07)
- **миграция (migration)** — файл с изменением структуры базы (например,
  "добавь таблицу Task с такими-то колонками"), который Prisma создаёт и
  применяет командой `prisma migrate dev` — как git-коммит, но для
  структуры базы данных. (объяснено: 2026-09-07)
- **SSH (Secure Shell)** — протокол для безопасного удалённого управления
  компьютером через командную строку; так мы будем заходить на VPS.
  (объяснено: 2026-09-15)
- **SSH-ключ (приватный / публичный)** — пара математически связанных
  файлов вместо пароля для входа на сервер: приватный (`id_ed25519`)
  никогда никуда не отправляется, живёт только на своём компьютере;
  публичный (`id_ed25519.pub`) можно свободно давать серверу — сам по себе
  для взлома бесполезен. Сервер проверяет, что у входящего есть подходящий
  приватный ключ, без передачи самого ключа по сети — в отличие от пароля,
  это невозможно подобрать перебором. (объяснено: 2026-09-15)
- **WHOIS** — публичная база данных о владельцах доменов (имя, адрес,
  email, телефон) — обязательная часть системы доменных имён, доступна
  всем. **WHOIS-приватность** — услуга регистратора, которая подставляет
  в эту базу свои контакты вместо настоящих владельца домена, чтобы
  личные данные не были видны публично. (объяснено: 2026-09-15)
- **Docker / контейнер / образ** — Docker упаковывает приложение вместе
  со всем нужным окружением (версия Node и т.п.) в один переносимый
  файл. **Образ** — "рецепт", что должно быть внутри; **контейнер** —
  уже запущенный экземпляр этого образа. Решает проблему "переезд на
  новый сервер = поставь Docker и запусти образ" вместо повторения всей
  ручной установки по `docs/DEPLOYMENT.md`. (объяснено: 2026-09-16)

## Решения по проекту

- **Кнопка добавления задачи на Today переиспользует `features/add-task`,
  а не создаёт новую форму** — форма уже существует и полностью работает,
  дублировать её нет смысла; ровно для такого переиспользования в FSD и
  существует слой `features`. (2026-08-13)
- **Бэкенд — Node.js + TypeScript** (Express + Prisma + PostgreSQL) — один
  язык на весь стек, типы (`Task`, `Goal`, `Habit`) можно переиспользовать
  между фронтендом и бэкендом без дублирования. (2026-09-07)
- **PUT заменяет всю коллекцию целиком**, а не отдельные ручки на
  create/update/delete — фронтенд и так уже был устроен вокруг
  `Repository<T>` (`list()`/`save(items)` — "отдай весь список"/"сохрани
  весь список"), поэтому свап на бэкенд не потребовал менять ни одного
  файла кроме самого `taskRepository.ts`/`goalRepository.ts`/
  `habitRepository.ts`. Минус: два устройства одновременно могут
  затереть правки друг друга — не страшно, пока нет синхронизации между
  устройствами; станет важно, когда до неё дойдём. **Заменено
  2026-09-16 на гранулярный API — см. ниже**, ровно по этой причине.
  (2026-09-07)
- **`Goal.milestones` хранится JSON-колонкой**, а не отдельной таблицей —
  чтобы не усложнять сверх уровня, который уже был у `Task`; можно
  нормализовать в отдельную таблицу позже, если понадобится. (2026-09-07)
- **`userId` — есть в схеме, но нигде не используется** — специально
  оставлено пустым (`nullable`) полем на будущее: когда будем делать
  логин, не придётся болезненно мигрировать уже существующие строки.
  (2026-09-07)
- **PostgreSQL поставили нативно через Homebrew, а не Docker** — Docker не
  был установлен, а Homebrew уже был; одной новой концепцией (контейнеры)
  меньше на этом этапе обучения. (2026-09-07)
- **Версии пакетов — "текущие стабильные", а не "самые новые из
  возможных"** — например, TypeScript 6.0.3, а не 7.0 (линтер проекта пока
  не поддерживает TS 7), Prisma 6.19.3, а не 7.x/8.0-rc (там нашлась
  уязвимость через неиспользуемый MySQL-драйвер, да и 8.0 — вообще ещё не
  стабильный релиз). Самое новое число — не всегда правильный выбор.
  (2026-09-07)
- **Свой VPS вместо управляемых платформ (Vercel/Railway)** — осознанный
  выбор: "работает на наших мощностях, без посредников". VPS — HipHosting,
  nginx (не Caddy — более стандартный и документированный инструмент)
  как reverse proxy, certbot для бесплатного HTTPS, GitHub Actions для
  автодеплоя при пуше в `main`. (2026-09-15 — 2026-09-16)
- **Гранулярный REST API вместо whole-collection PUT** —
  `POST`/`PATCH /:id`/`DELETE /:id`/`PATCH /reorder` на каждую сущность,
  плюс `'updatedAt'` в ответе для обнаружения конфликтов (если кто-то
  другой уже изменил ту же запись — `409` с актуальной версией, а не
  тихая перезапись). Понадобилось ровно тогда, когда предполагалось
  ("станет важно, когда до неё дойдём" — см. запись про PUT выше):
  начали активно пользоваться приложением с нескольких устройств.
  (2026-09-16)
- **Приложение и PostgreSQL — в Docker-контейнерах**, не установлены
  напрямую на VPS — переезд на новый сервер сводится к "поставь Docker,
  запусти `docker compose up`" вместо повторения всей ручной установки.
  Образ приложения собирается в GitHub Actions и хранится в GitHub
  Container Registry; Postgres — официальный образ с Docker Hub.
  Контейнеризация приложения и базы сделаны отдельными заходами
  (2026-09-16 и 2026-09-17) — осознанно не одновременно с рефакторингом
  API, чтобы при поломке было понятно, что именно её вызвало. Перенос
  базы включал реальную миграцию продовых данных (репетиция на копии,
  потом настоящее переключение с построчной сверкой количества записей).
  (2026-09-16 — 2026-09-17)
- **`Task.dueDate` — настоящая дата (`@db.Date`) в базе**, а не текстовая
  строка — нужно для нормальных SQL-запросов по диапазону дат в будущем
  (сейчас Calendar всё ещё фильтрует на клиенте, но фундамент готов).
  Миграция написана вручную (`ALTER COLUMN ... USING "dueDate"::date`),
  а не дефолтным способом Prisma (drop+recreate стёр бы существующие
  значения). На проводе для фронтенда формат не изменился — как был
  `"YYYY-MM-DD"` строкой, так и остался. (2026-09-17)
- **Тесты — и на бэкенде, и на фронтенде** — `vitest`+`supertest` для
  API (гоняются на отдельной тестовой базе, не на реальной), `vitest`+
  `@testing-library/react`+`TestBackend` от react-dnd для drag-and-drop
  хуков (того самого места, что три раза ломалось системно из-за
  нестабильных callback ref — теперь есть регресс-тест, который реально
  проверен на то, что ловит именно эту поломку). (2026-09-17)
- **Структурированная документация требований** (`docs/requirements/`) —
  по образцу корпоративного Confluence-стиля (FRONTEND/BACKEND-документы
  на каждую фичу, нумерация, обязательные секции) — чтобы можно было
  восстановить поведение приложения по одним только этим файлам, без
  необходимости перечитывать код или историю чата. (2026-09-15 — начато,
  2026-09-17 — дерево дописано полностью по всем фичам)
- **`Task.completedAt` — отдельное поле, а не переиспользование
  `updatedAt`** — нужно было понять, к какому дню отнести выполненную
  задачу (чтобы вкладка Tasks "All" не копила выполненные задачи вечно, а
  показывала только сегодняшние). `updatedAt` для этого не годится: он
  меняется при любом редактировании, а не только при отметке "выполнено"
  — переименование задачи неделю спустя после выполнения ложно "оживило"
  бы её в сегодняшнем дне. `completedAt` проставляется на клиенте ровно
  в момент переключения `completed`, сбрасывается в `null` при отмене.
  (2026-09-17)
- **Категории задач — отдельная сущность `Category` в базе, но БЕЗ
  внешнего ключа от `Task.category`** — раньше список категорий был
  просто зашитым массивом (`TASK_CATEGORIES`). Нужно было дать
  пользователю создавать свои категории, но полная нормализация
  (`Task.category` → `Category.id`) означала бы миграцию с риском для
  реальных данных задач ради фичи, которая по сути — просто "список
  того, что предлагать в выпадающем списке". Решение по той же логике,
  что раньше применили к `Goal.milestones` (JSON вместо таблицы) —
  не усложнять сверх того, что реально нужно сейчас. `Task.category`
  как был простой строкой, так и остался. (2026-09-17)
- **Светлая тема — через `next-themes`, а не свой велосипед** —
  библиотека уже была установлена (её неявно использовал `sonner.tsx`
  через `useTheme()`), просто `ThemeProvider` нигде не был подключён.
  Обнаружилось, что `:root` и `.dark` в `theme.css` были побайтово
  идентичны — реальной светлой темы не существовало вообще, несмотря на
  видимость переключателя тем в коде. Тёплая светлая палитра подобрана
  заново (тот же брендовый оранжевый акцент, что и в тёмной). (2026-09-17)
- **EN/RU — свой простой словарь, а не `react-i18next`** — обсудили с
  владельцем: библиотека дала бы больше возможностей (множественное
  число, интерполяция из коробки), но ради текущего объёма текста это
  лишняя зависимость и настройка. Свой механизм — `t(key, vars)` с
  подстановкой `{var}` в строку, два плоских словаря `en`/`ru`, язык
  хранится в `localStorage` (авторизации в приложении всё ещё нет).
  Переводятся только элементы интерфейса (кнопки, лейблы, пустые
  состояния, тосты) — названия задач/целей/привычек и категорий,
  введённые самим пользователем, никогда не переводятся. (2026-09-17)
- **`Button` (`shared/ui/button.tsx`) не оборачивал `React.forwardRef`**
  — баг того же класса, что уже был у `AccordionItem` (см. заметку в
  `qa-tester.md`): Radix-компоненты вроде `PopoverTrigger asChild`
  подключают свой `ref` к дочернему элементу через `Slot`, и без
  `forwardRef` этот `ref` тихо никуда не долетает — попап просто не
  открывался, без единой ошибки в консоли, кроме предупреждения React
  про "Function components cannot be given refs". Нашли это при
  подключении тематического date-picker (который использует
  `Popover`+`Button` как триггер). Исправлено один раз в самом `Button`
  — чинит разом все места, где он использовался с `asChild` через любой
  Radix-компонент. (2026-09-17)
- **Авторизация — Better Auth, а не самопис и не сторонний сервис** —
  обсудили с владельцем варианты (свой код с нуля, сторонний сервис
  вроде Clerk/Auth0, готовая self-hosted библиотека) и выбрали
  библиотеку поверх своей же PostgreSQL: не пишем security-критичный
  код (хэширование паролей, сессии) руками — слишком легко незаметно
  ошибиться, но и данные пользователей не отдаём наружу — тот же
  принцип, что выбор своего VPS вместо управляемых платформ. Вход по
  паролю, не по ссылке на почту (magic link обсуждали — меньше кода,
  но владелец предпочёл скорость входа привычным флоу). Email
  обязательно подтверждается перед первым входом. (2026-09-18)
- **Модели Better Auth (`User`/`Session`/`Account`/`Verification`)
  написаны в `schema.prisma` руками, не через `npx auth generate`** —
  у CLI-генератора библиотеки была история перезаписи существующих
  моделей в схеме (баг репортился, не всегда воспроизводился на разных
  версиях) — решили не рисковать четырьмя уже существующими моделями
  (`Task`/`Goal`/`Habit`/`Category`) ради удобства генерации. Саму
  миграцию тоже собрали не через `prisma migrate dev` (требует
  интерактивный терминал, недоступный в этой среде), а через
  `prisma migrate diff` (сравнение текущей базы со схемой) +
  `prisma migrate deploy` — тот же путь, что и продовый деплой уже
  использует. (2026-09-18)
- **Категории теперь привязаны к пользователю, `@@unique([userId, name])`
  вместо глобального `@unique` на `name`** — иначе после первого же
  пользователя никто другой не смог бы завести категорию "Work". Сид 4
  стандартных категорий (Work/Personal/Health/Learning) стал "ленивым"
  — создаётся при первом запросе списка категорий, если у пользователя
  их ещё нет, а не одним разом на всё приложение, как раньше. (2026-09-18)
- **Пароль пользователя хранится в таблице `account`
  (`providerId: "credential"`), не в `user`** — так устроена схема
  Better Auth; если когда-нибудь понадобится смотреть/чинить эти данные
  напрямую через SQL, искать не в `user.password` (такого поля нет
  вообще), а в `account.password` у строки с `providerId = 'credential'`.
  (2026-09-18)
- **Баг: клиентская навигация `navigate("/today")` после успешного
  входа оставляла на `/login`, хотя сессия была валидной** (прямой
  `fetch('/api/auth/get-session')` подтверждал куку/сессию рабочими) —
  `RootLayout`, монтируясь заново через SPA-навигацию, гонится с
  внутренней инвалидацией сессии клиентской библиотеки. Починили через
  `window.location.href = "/today"` (настоящая перезагрузка страницы)
  именно в этом направлении (логин → защищённая часть) — обратное
  направление (logout) не страдает, потому что там `RootLayout` уже
  смонтирован и просто реагирует на смену сессии как обычно. (2026-09-18)
- **Перенос продовых данных на владельца-пользователя — решили не
  делать вообще, просто удалили старьё** — перед выкаткой авторизации
  проверили, что реально лежит на проде: 0 задач, 0 целей, 1 привычка
  без важной истории, 4 дефолтные категории. Вся тяжёлая процедура из
  плана (репетиция на копии, построчная сверка) была рассчитана на
  случай реальных данных — раз их по сути не было, владелец сам
  предложил не переносить, а зарегистрировать чистый аккаунт и удалить
  старые "ничейные" записи. `userId` сделали `NOT NULL` сразу после
  удаления — без реальных данных это стало тривиальной миграцией, а не
  риском. Мораль: прежде чем планировать сложную миграцию — сначала
  проверь, сколько там вообще реальных данных. (2026-09-19)
- **Реальный инцидент: деплой без предварительной настройки сервера
  уронил прод на ~2 часа** — запушили код с новыми обязательными

- **Как отличить "первый вход после регистрации" от обычного повторного
  входа — без нового поля в БД** — Better Auth принимает `callbackURL`
  в `authClient.signUp.email(...)`, зашивает его в ссылку письма
  подтверждения и сам делает HTTP-редирект браузера туда после успешной
  верификации (подтверждено чтением исходников
  `node_modules/better-auth/dist/api/routes/email-verification.mjs`:
  `if (ctx.query.callbackURL) throw ctx.redirect(...)`). Передали
  `callbackURL: "/login?verified=1"` — `LoginPage` читает этот параметр
  и при успешном входе ведёт на `/today?firstLogin=1` вместо обычного
  `/today?welcomeBack=1`. Никаких изменений в схеме или доп. запросов к
  БД не потребовалось — только использование того, что библиотека уже
  умеет. (2026-09-19)

- **Баг "changed elsewhere" после reorder — batch-эндпоинт `PATCH
  /reorder` тоже бампает `updatedAt`, а клиент об этом не узнавал** —
  первое предположение по аналогии с уже известным багом
  `Goal.milestones` оказалось неверным (тот баг — про единую JSON-
  колонку и `update()`; `Habit`/`Task`/`Category` реордерятся через
  отдельный batch-роут, который в принципе не проверяет
  `expectedUpdatedAt`). Настоящая причина — в другом месте: Prisma's
  `@updatedAt` обновляет `updatedAt` у каждой строки при **любой**
  записи, включая `updateMany({data: {order}})` в reorder-эндпоинте, а
  `PATCH /reorder` отвечал голым `204` без данных — фронтенд продолжал
  считать актуальным старый (уже неверный) `updatedAt` для всех
  переставленных записей. Следующий точечный `PATCH /:id` (например,
  отметить привычку выполненной сразу после перетаскивания — самый
  частый сценарий) отправлял этот протухший `expectedUpdatedAt` и
  получал ложный `409`. Фикс — `PATCH /reorder` теперь возвращает `{id,
  updatedAt}[]`, `usePersistedCollection.reorder()` подмешивает свежие
  значения в локальный стейт сразу после успешного reorder. Урок: если
  один и тот же паттерн бага всплывает у нескольких похожих сущностей —
  не полагаться на аналогию с уже объяснённым случаем, перепроверять
  код каждой сущности отдельно, точная причина может отличаться.
  (2026-09-19)

- **Найден и закрыт общий корень давнего бага "changed elsewhere" у
  подцелей — не точечный фикс, а общая защита в `usePersistedCollection.
  update()`** — владелец заметил ту же ошибку при перетаскивании
  подцелей внутри цели и попросил не чинить точечно, а поискать, нет ли
  такой же проблемы в других местах. Оказалось, что причина — не
  особенность конкретно `Goal.milestones` (как предполагалось в
  `docs/BACKLOG.md` ещё с 2026-09-17), а системная дыра в самой функции
  `update()`: она не защищена от двух почти одновременных вызовов для
  одной и той же записи — второй вызов читает `expectedUpdatedAt` из
  React-стейта, который ещё не знает о результате первого. Перетаскивание
  подцелей вызывает `update()` на каждый шаг наведения (`onHoverMove`),
  поэтому гонка воспроизводится почти всегда, а не изредка. Фикс —
  очередь вызовов на уровне `id`: `usePersistedCollection.ts` хранит
  `Map<id, Promise>` последних вызовов и каждый следующий вызов для того
  же `id` дожидается предыдущего и берёт `updatedAt` из его
  подтверждённого сервером результата, а не из потенциально устаревшего
  стейта. Это чинит не только подцели, а вообще любые два быстрых подряд
  изменения одной записи (`create`/`remove`/`reorder` этой защиты не
  требуют — они либо не проверяют `expectedUpdatedAt` вообще, либо
  всегда работают с новым id). Написан регресс-тест с управляемой
  задержкой в фейковом репозитории, который сначала подтвердил баг на
  старом коде (падал с той же `ConflictError`, что видел владелец), а
  затем прошёл на исправленном. Урок: если баг с самого начала выглядит
  как "иногда бывает у одной конкретной сущности" — стоит подозревать
  общий код, которым эта сущность пользуется, а не только её саму;
  когда владелец сам подсказывает "поищи, не смежное ли это" — это
  правильный вопрос, и он тут привёл к более простому и общему фиксу,
  чем если бы чинили только `Goal.milestones` точечно. (2026-09-20)
