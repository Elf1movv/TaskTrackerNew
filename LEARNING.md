# Конспект обучения — TaskTrackerNew

## Термины

- **компонент (component)** — переиспользуемый кусок интерфейса, оформленный
  как функция, которая возвращает разметку (JSX). Например, `TodayPage` и
  `AddTaskForm` — оба компоненты. (объяснено: 2026-08-13, при добавлении
  кнопки "Add task" на Today)
- **состояние (state)** — данные, которые компонент "запоминает" между
  перерисовками экрана и которые могут меняться со временем (например,
  "форма сейчас открыта или закрыта"). Создаётся через хук `useState`.
  (объяснено: 2026-08-13)
- **хук (hook)** — функция React, имя которой начинается с `use`
  (`useState`, `useTasks` и т.д.), и которая даёт компоненту дополнительные
  возможности — например, "память" между перерисовками. (объяснено:
  2026-08-13)
- **обработчик события (event handler)** — функция, которая выполняется в
  ответ на действие пользователя, например `onClick` — что делать по клику
  на кнопку. (объяснено: 2026-08-13)
- **условный рендеринг (conditional rendering)** — показ разной разметки в
  зависимости от состояния, например `{isAdding && <AddTaskForm />}` —
  показать форму, только если `isAdding` истинно. (объяснено: 2026-08-13)
- **импорт (import)** — способ подключить в файл код, который определён в
  другом файле или библиотеке, например `import { useState } from "react"`.
  (объяснено: 2026-08-13)
- **JavaScript / TypeScript / React / JSX-TSX — кто есть кто**: JavaScript
  (JS) — сам язык программирования; TypeScript (TS) — JS плюс типы (файлы
  `.ts`/`.tsx` в проекте); React — библиотека для интерфейсов, написанная на
  JS/TS (даёт нам компоненты, хуки, state, props); JSX/TSX — синтаксис,
  который позволяет писать HTML-подобную разметку внутри JS/TS-файла (TSX —
  то же самое, но в TypeScript-файле). (объяснено: 2026-08-13)
- **клиент / сервер** — клиент (браузер, наш React-фронтенд) и сервер (наша
  Express-программа) — два отдельных процесса, которые общаются по сети,
  даже если оба на одном компьютере. (объяснено: 2026-09-07, при разборе
  backend)
- **порт** — номер "двери", через которую конкретная программа принимает
  соединения на компьютере (5173 — фронтенд, 3001 — сервер, 5432 —
  PostgreSQL). (объяснено: 2026-09-07)
- **HTTP-запрос / метод** — сообщение от клиента к серверу по сети; `GET` —
  "дай мне данные", `PUT` — "замени данные на присланные". (объяснено:
  2026-09-07)
- **эндпоинт / роут (route)** — конкретный "адрес" на сервере, к которому
  можно обратиться, например `/api/tasks`. (объяснено: 2026-09-07)
- **JSON** — текстовый формат, в котором клиент и сервер пересылают друг
  другу данные. (объяснено: 2026-09-07)
- **ORM (Object-Relational Mapping)** — программа-переводчик (у нас —
  Prisma), которая превращает вызовы вроде `db.task.findMany()` в
  настоящий SQL-запрос к базе, чтобы не писать SQL руками. (объяснено:
  2026-09-07)
- **SQL** — язык запросов к реляционным базам данных (таким как
  PostgreSQL). (объяснено: 2026-09-07)
- **миграция (migration)** — файл с изменением структуры базы (например,
  "добавь таблицу Task с такими-то колонками"), который Prisma создаёт и
  применяет командой `prisma migrate dev` — как git-коммит, но для
  структуры базы данных. (объяснено: 2026-09-07)
- **SSH (Secure Shell)** — протокол для безопасного удалённого управления
  компьютером через командную строку; так мы будем заходить на VPS.
  (объяснено: 2026-09-15)
- **SSH-ключ (приватный / публичный)** — пара математически связанных
  файлов вместо пароля для входа на сервер: приватный (`id_ed25519`)
  никогда никуда не отправляется, живёт только на своём компьютере;
  публичный (`id_ed25519.pub`) можно свободно давать серверу — сам по себе
  для взлома бесполезен. Сервер проверяет, что у входящего есть подходящий
  приватный ключ, без передачи самого ключа по сети — в отличие от пароля,
  это невозможно подобрать перебором. (объяснено: 2026-09-15)
- **WHOIS** — публичная база данных о владельцах доменов (имя, адрес,
  email, телефон) — обязательная часть системы доменных имён, доступна
  всем. **WHOIS-приватность** — услуга регистратора, которая подставляет
  в эту базу свои контакты вместо настоящих владельца домена, чтобы
  личные данные не были видны публично. (объяснено: 2026-09-15)
- **Docker / контейнер / образ** — Docker упаковывает приложение вместе
  со всем нужным окружением (версия Node и т.п.) в один переносимый
  файл. **Образ** — "рецепт", что должно быть внутри; **контейнер** —
  уже запущенный экземпляр этого образа. Решает проблему "переезд на
  новый сервер = поставь Docker и запусти образ" вместо повторения всей
  ручной установки по `docs/DEPLOYMENT.md`. (объяснено: 2026-09-16)

## Решения по проекту

- **Кнопка добавления задачи на Today переиспользует `features/add-task`,
  а не создаёт новую форму** — форма уже существует и полностью работает,
  дублировать её нет смысла; ровно для такого переиспользования в FSD и
  существует слой `features`. (2026-08-13)
- **Бэкенд — Node.js + TypeScript** (Express + Prisma + PostgreSQL) — один
  язык на весь стек, типы (`Task`, `Goal`, `Habit`) можно переиспользовать
  между фронтендом и бэкендом без дублирования. (2026-09-07)
- **PUT заменяет всю коллекцию целиком**, а не отдельные ручки на
  create/update/delete — фронтенд и так уже был устроен вокруг
  `Repository<T>` (`list()`/`save(items)` — "отдай весь список"/"сохрани
  весь список"), поэтому свап на бэкенд не потребовал менять ни одного
  файла кроме самого `taskRepository.ts`/`goalRepository.ts`/
  `habitRepository.ts`. Минус: два устройства одновременно могут
  затереть правки друг друга — не страшно, пока нет синхронизации между
  устройствами; станет важно, когда до неё дойдём. **Заменено
  2026-09-16 на гранулярный API — см. ниже**, ровно по этой причине.
  (2026-09-07)
- **`Goal.milestones` хранится JSON-колонкой**, а не отдельной таблицей —
  чтобы не усложнять сверх уровня, который уже был у `Task`; можно
  нормализовать в отдельную таблицу позже, если понадобится. (2026-09-07)
- **`userId` — есть в схеме, но нигде не используется** — специально
  оставлено пустым (`nullable`) полем на будущее: когда будем делать
  логин, не придётся болезненно мигрировать уже существующие строки.
  (2026-09-07)
- **PostgreSQL поставили нативно через Homebrew, а не Docker** — Docker не
  был установлен, а Homebrew уже был; одной новой концепцией (контейнеры)
  меньше на этом этапе обучения. (2026-09-07)
- **Версии пакетов — "текущие стабильные", а не "самые новые из
  возможных"** — например, TypeScript 6.0.3, а не 7.0 (линтер проекта пока
  не поддерживает TS 7), Prisma 6.19.3, а не 7.x/8.0-rc (там нашлась
  уязвимость через неиспользуемый MySQL-драйвер, да и 8.0 — вообще ещё не
  стабильный релиз). Самое новое число — не всегда правильный выбор.
  (2026-09-07)
- **Свой VPS вместо управляемых платформ (Vercel/Railway)** — осознанный
  выбор: "работает на наших мощностях, без посредников". VPS — HipHosting,
  nginx (не Caddy — более стандартный и документированный инструмент)
  как reverse proxy, certbot для бесплатного HTTPS, GitHub Actions для
  автодеплоя при пуше в `main`. (2026-09-15 — 2026-09-16)
- **Гранулярный REST API вместо whole-collection PUT** —
  `POST`/`PATCH /:id`/`DELETE /:id`/`PATCH /reorder` на каждую сущность,
  плюс `'updatedAt'` в ответе для обнаружения конфликтов (если кто-то
  другой уже изменил ту же запись — `409` с актуальной версией, а не
  тихая перезапись). Понадобилось ровно тогда, когда предполагалось
  ("станет важно, когда до неё дойдём" — см. запись про PUT выше):
  начали активно пользоваться приложением с нескольких устройств.
  (2026-09-16)
- **Приложение и PostgreSQL — в Docker-контейнерах**, не установлены
  напрямую на VPS — переезд на новый сервер сводится к "поставь Docker,
  запусти `docker compose up`" вместо повторения всей ручной установки.
  Образ приложения собирается в GitHub Actions и хранится в GitHub
  Container Registry; Postgres — официальный образ с Docker Hub.
  Контейнеризация приложения и базы сделаны отдельными заходами
  (2026-09-16 и 2026-09-17) — осознанно не одновременно с рефакторингом
  API, чтобы при поломке было понятно, что именно её вызвало. Перенос
  базы включал реальную миграцию продовых данных (репетиция на копии,
  потом настоящее переключение с построчной сверкой количества записей).
  (2026-09-16 — 2026-09-17)
- **`Task.dueDate` — настоящая дата (`@db.Date`) в базе**, а не текстовая
  строка — нужно для нормальных SQL-запросов по диапазону дат в будущем
  (сейчас Calendar всё ещё фильтрует на клиенте, но фундамент готов).
  Миграция написана вручную (`ALTER COLUMN ... USING "dueDate"::date`),
  а не дефолтным способом Prisma (drop+recreate стёр бы существующие
  значения). На проводе для фронтенда формат не изменился — как был
  `"YYYY-MM-DD"` строкой, так и остался. (2026-09-17)
- **Тесты — и на бэкенде, и на фронтенде** — `vitest`+`supertest` для
  API (гоняются на отдельной тестовой базе, не на реальной), `vitest`+
  `@testing-library/react`+`TestBackend` от react-dnd для drag-and-drop
  хуков (того самого места, что три раза ломалось системно из-за
  нестабильных callback ref — теперь есть регресс-тест, который реально
  проверен на то, что ловит именно эту поломку). (2026-09-17)
- **Структурированная документация требований** (`docs/requirements/`) —
  по образцу корпоративного Confluence-стиля (FRONTEND/BACKEND-документы
  на каждую фичу, нумерация, обязательные секции) — чтобы можно было
  восстановить поведение приложения по одним только этим файлам, без
  необходимости перечитывать код или историю чата. (2026-09-15 — начато,
  2026-09-17 — дерево дописано полностью по всем фичам)
