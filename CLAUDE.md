# CLAUDE.md — как работать в этом проекте

Этот файл Claude Code читает **автоматически** в начале каждой сессии в
этой папке — неважно, с какого компьютера и с какого аккаунта. Он
существует специально на случай, если предыдущий чат/сессия потеряны:
здесь — не что за проект (это `PROJECT_BRAIN.md`, читай его первым), а
**как именно мы вместе работаем**, чтобы новая сессия вела себя так же,
как предыдущие, а не начинала с нуля другим стилем.

## Порядок чтения для новой сессии

1. Этот файл — рабочие правила и договорённости
2. `PROJECT_BRAIN.md` — что за проект, стек, как всё развёрнуто,
   playbook на случай потери доступа к чему угодно
3. `LEARNING.md` — хронологический журнал решений и уроков (в конце
   файла — самое свежее). Проверяй его, прежде чем предполагать
   причину бага или заново изобретать решение — велика вероятность,
   что похожая проблема уже разбиралась
4. `docs/BACKLOG.md` — что уже сделано, что осознанно отложено и почему
5. `docs/ARCHITECTURE.md` — технические решения и их причины, известные
   гочи (gotchas)
6. `docs/requirements/` — что именно делает каждая фича, по пунктам

## Кто пользователь

Полный новичок в программировании — **не предполагай знание даже
базовых терминов** (переменная, функция, компонент, состояние, props,
hook). Строит этот проект специально чтобы научиться, а не просто
получить готовое приложение. Общайся **по-русски** — это не связано с
языком кода/коммитов (они остаются на английском), это про весь
текст, который видит пользователь, включая статусы по ходу долгой
работы и фоновых агентов.

Активен режим `.claude/skills/coding-mentor/SKILL.md` — объясняй
что/почему/как и предупреждай о "радиусе поражения" (сколько файлов
затронет правка и почему) перед нетривиальными изменениями, вводи
термины сразу с объяснением, веди `LEARNING.md`. **Важное уточнение по
факту того, как это реально работало на практике** (в отличие от
буквального текста скила, где предполагается, что пользователь
пробует писать код сам): на деле почти весь код в этом проекте пишет
ассистент напрямую, но **продолжает подробно объяснять** каждое
решение по ходу — это устоявшийся, осознанный стиль работы для этого
проекта на данном этапе, не отступление от режима наставника. Не
переключайся резко на "теперь пиши сам" без явной просьбы
пользователя.

## Как мы на самом деле работаем — сложившиеся правила

### Планирование

Для любой правки, которая заденет больше 2-3 файлов или требует
архитектурного решения — **сначала Plan Mode** (`EnterPlanMode`):
исследовать код через параллельные `Explore`-агенты, при реальной
развилке дизайна — `AskUserQuestion` (по возможности с наглядным
`preview`, а не просто текстом), написать план в файл, дождаться
подтверждения (`ExitPlanMode`) и только потом писать код. Для
маленькой точечной правки (одна строка, очевидный фикс) это лишнее.

### Проверка перед тем, как считать что-то готовым

Пройти тайпчек не означает, что фича работает. Обязательный набор
перед тем, как сказать "готово":
- `npm run typecheck` (фронтенд) и `cd server && npx tsc --noEmit`
- `npm run lint` и `npm run fsd-lint`
- `cd server && npm test` (бэкенд, vitest) и `npx vitest run` в корне
  (фронтенд, если есть релевантные тесты)
- **Реальная проверка в браузере** для любой видимой фичи — через
  `qa-tester` агента или напрямую `mcp__claude-in-chrome__*`
  инструментами (`ToolSearch` их подгружает по требованию). Если
  расширение Chrome не подключено — сказать об этом прямо, не
  утверждать, что всё работает, полагаясь только на код

### Документация — часть той же правки, не отдельный шаг потом

- `docs/BACKLOG.md` — отмечать `[x]` с датой и коротким объяснением,
  что реально сделано; новые отложенные идеи — записывать с датой и
  причиной "почему не сейчас"
- `LEARNING.md` — хронологический журнал: особенно если причина бага
  оказалась не такой, как думали сначала (см. записи про
  `Goal.milestones` и общий баг реордера как пример) — это самая
  ценная часть файла для будущей сессии
- `docs/ARCHITECTURE.md` — обновлять ER-диаграмму и раздел gotchas при
  изменении схемы БД или обнаружении нового скрытого поведения
- `docs/requirements/` — строгая посущностная спецификация, для этого
  есть агент `docs-writer` (запускать сразу после функциональных
  изменений, не откладывать)

### git push = деплой в прод

Пуш в `main` **автоматически деплоит** на `mytracker.space` (GitHub
Actions → сборка образа → SSH на VPS → `docker compose pull` + `prisma
migrate deploy` + `docker compose up -d`). Из-за этого:
- **Всегда спрашивать явное подтверждение перед `git push origin
  main`** — каждый раз заново, не считать одно одобрение действующим
  на будущее
- Если в изменении есть новые переменные окружения или нужна ручная
  настройка сервера — **сделать это на VPS до пуша**, не после. Один
  раз забыли — прод упал на ~2 часа (see `LEARNING.md`,
  2026-09-19) из-за `BETTER_AUTH_SECRET`, которого не было в
  `server/.env` на сервере
- После пуша — **активно следить за деплоем**, не считать, что раз
  запушилось — значит работает: сравнить хэш JS-бандла на проде
  (`curl https://mytracker.space/ | grep -o 'assets/index-[^"]*\.js'`)
  до/после, проверить `docker compose logs app` на ошибки и
  краш-луп через SSH (`deploy@185.65.202.121`), убедиться что
  `/api/health` отвечает `{"ok":true}`

### Минимализм в коде

Не добавлять абстракции "на будущее" и не чинить то, что не просили.
Переиспользовать уже устоявшиеся паттерны, а не изобретать новые для
похожей задачи:
- `Repository<T>` + `usePersistedCollection` (`src/shared/lib/storage/`)
  — единая точка для create/update/remove/reorder/refresh с
  оптимистичным обновлением и откатом. `update()` уже защищён от
  гонки при двух быстрых подряд изменениях одной записи (очередь по
  `id`) — см. `LEARNING.md`, 2026-09-20
- Кнопка-переключатель "текст меняется в зависимости от состояния"
  (см. `src/shared/ui/language-toggle.tsx`, `theme-toggle.tsx`,
  тоггл срока в `TaskForm`/`GoalForm`) — стандартный паттерн для
  бинарных настроек в этом проекте, не `Switch` + отдельная подпись
- `AlertDialog` — для любого нового деструктивного подтверждения
  (пример — удаление категории с задачами)
- Стейгер (`npm run fsd-lint`) — два правила (`fsd/insignificant-slice`,
  `fsd/segments-by-purpose`) намеренно понижены до `warn`, это осознанный
  задел на рост проекта, не чинить автослиянием слайсов без явной
  просьбы пользователя

### Агенты в `.claude/agents/`

- `qa-tester` — тестирование в реальном браузере, знает историю
  прошлых багов этого приложения (drag-and-drop, forwardRef и т.п.),
  запускать после любой видимой фичи
- `docs-writer` — обновляет `docs/requirements/` вслед за кодом,
  запускать сразу после функциональных изменений
- `project-guide` — отвечает на вопросы "почему это сделано так",
  ловит расхождение документации с реальным кодом

## Память между сессиями

У ассистента есть локальная файловая память (auto-memory) в
`~/.claude/projects/<project>/memory/` — но она **привязана к этому
конкретному компьютеру/сессии** и не переедет вместе со сменой
аккаунта или машины. Единственное, что реально переносится куда
угодно — то, что закоммичено в этот репозиторий: этот файл,
`PROJECT_BRAIN.md`, `LEARNING.md`, `docs/`. Если локальная память
подсказывает что-то важное и постоянное (не разовую деталь текущей
задачи) — переносить это сюда или в `LEARNING.md`, а не оставлять
только в памяти.
